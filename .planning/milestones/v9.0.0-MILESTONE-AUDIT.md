## Method and confidence

A 24-unit audit ran over the planning record and the repository. Seven parallel surveys established shared
facts (post-freeze commit history, live route/flag inventory, release record, requirement ledger,
open-issue state, operational risks, planning-record integrity). Each unit then reconciled its slice of the
plan against the code independently, and **every candidate finding faced two independent adversarial
verifiers** — one checking that the cited evidence actually exists and says what the finding claims, one
checking whether the gap had already been closed by post-freeze work. Verifiers defaulted to REFUTED.

|---|---|
| Candidate findings | 104 |
| Survived both verifiers | **81** |
| Refuted or materially corrected | 23 |

Refuted claims are listed in the last section rather than deleted, because two of them were drafted as
criticals and their death is itself a useful result.

## What actually happened

v9.0.0 set out to fold the SEED-029 corpus-wide same-work map into genizahsearch.com as a banded,
masked, honesty-gated discovery module, gated behind REL-01. It delivered that: the atlas preview, the
data spine, a measured precision certificate (0.9382, CI [0.9084, 0.9644]), the connections panel, the
findings page, the xlsx export, and a live public beta.

Then two things happened that the plan did not model. First, `DISCOVERY_ENABLED` was flipped on
2026-08-08 ahead of its own gate, and five REL-01 items were waived in writing after the fact. Second —
and this is the larger fact — **the planning record stopped on 2026-08-21 and the product did not.**
339 commits, a 98-commit branch merged via PR #324, and two tagged GitHub releases (v9.1.0
2026-08-28, v9.2.0 2026-09-06) landed with no phase number attached to any of them. `STATE.md` still
reads `completed_phases: 5, total_phases: 20, last_updated: 2026-08-21`.

The milestone's own roadmap anticipated this failure mode, created Phase 140 to stop it, sequenced
Phase 140 first, and then never ran it. The pattern it was built to prevent recurred at roughly ten times
the scale that created it.

## Critical

### C1 — The passage-search default flipped without the test built to license it
`divergence · now · Phase 144`

**Plan.** ROADMAP.md:1027-1076, Phase 144 SC4: *"The default flip is decided against pre-declared
endpoints: recall@50 primary, precision@k secondary, a one-sided 95% CI lower bound no worse than 3
points versus the incumbent in every named protected class (query-length band, genre, language,
page-CER band)… A class whose sample cannot support that precision blocks by insufficiency."* SC6:
*"not earning the flip is an acceptable result."*

**Reality.** The pre-registered instrument (`docs/specs/parallels-holdout-prereg.md`) was shelved unspent
on 2026-08-21 — commit `fc2a14ad`, *"the holdout split has never been scored."* Two days later the web
default flipped in `bee7d49c`, resting on *"the owner's own row-by-row grading of live GUI runs: precision
94%, recall parity with chunk-4 PLUS 7 novel verified witnesses, ~0.6s against minutes."* The desktop
default flipped on 2026-08-28 in `7c998627` citing *"Owner rulings, 2026-08-28"* about UX and badge
behaviour, with no new measurement at all. Neither commit references PASS-05, the holdout, a protected
class, or a CI bound. Protected-class awareness did exist in the pre-flip tuning work (JA query labelling,
equal-allocation sampling for the blinded deck) but never produced a scored per-class CI comparison.

**Why it matters.** The interim tuning evidence the roadmap itself records shows **overlapping intervals**
on recall@50 — passage 0.750 [0.666, 0.819] against the incumbent's 0.708 [0.622, 0.782] at
`chunk_size=3` (ROADMAP.md:86 and :1043) — and sweeping the incumbent's chunk size already
overturned the author's own conclusion once (`7cc50fe7`). Passage separates on ranking and speed
(recall@1 0.592 vs 0.467, MRR 0.639 vs 0.533, 391 ms vs 14,565 ms), not on retrieval. Shipping
default-on to every researcher without the protected-class check means a silent recall regression in one
class — most plausibly Judeo-Arabic or long queries, both flagged in the prereg's own power analysis — is
indistinguishable from an absence of evidence. That is precisely the failure mode SC6 named. Recall is
the entire point of the tool.

**To close.** Either spend the holdout against SC4's endpoints, or restate the default publicly as an owner
preference rather than a measured result and amend `/help`'s recommendation wording (see L65).

### C2 — Phase 140 never ran, and the failure it exists to prevent recurred at ~10x scale
`risk · now · Phase 140`

**Plan.** ROADMAP.md:72-74 — Phase 140 is *"sequenced FIRST because every other phase plans against
numbers this phase makes true."* Its own history note: *"the same thing happened twice in two weeks…
Phase 140 is the standing answer; whether it works is measurable the next time this section needs
writing."*

**Reality.** No directory, no PLAN.md, no commits beyond the 2026-08-20/21 bookkeeping pass. Since
then: `git rev-list 835addc4..HEAD --count` = 339 commits; merge commits `f3dc7726` and `e6a0ba46`;
tags v9.1.0 (2026-08-28) and v9.2.0 (2026-09-06). None appears in ROADMAP.md's phase list.

**Why it matters.** Any roadmap built by trusting `ROADMAP.md`/`STATE.md` as ground truth silently omits
two shipped, user-facing feature lines. GSD's own `init.manager` reads disk state and reports 5/20 complete.

### C3 — No gate exists against Track-1 non-monotonicity
`omission · next · Phase 148`

**Plan.** ROADMAP.md ~1186-1189, Phase 148 SC3 (OPS-02): *"The Track-1 non-monotonicity is fixed or
gated… every append diffs against live before ship, and the diff is a gate, not a report."*

**Reality.** `REF_DF_CAP = 128` stands unchanged at `same_work_spike/probe/scripts/track1_match.py:37`
(gitignored, zero commits since the freeze). The only automated preservation check in the repo —
`scripts/verify_rebuild_preservation.py` + `tests/test_rebuild_preservation.py` — is a Phase-136 rebuild
gate that diffs `discovery.db`'s six core tables column-by-column against an authorized-change allowlist. It
has nothing to do with detecting a reference append silently dropping identifications and does not consume
Track-1's posting-cap behaviour at all. The one-time analysis that found the 103-identification loss lives in
`discovery_builds/discovery_v4_2/removal_analysis/`, a static folder, not a repeatable check.

**Why it matters.** `docs/OPEN_ISSUES.md:161` records the owner's acceptance of that loss **on the
condition** that every future append is diffed first. That condition is unenforced code. A REF7+ append run
today repeats the same class of loss and nothing in CI or the build path catches it before ship. This is the
only finding in the audit where inaction destroys data.

### The ones that need expanding

**H5 — default-on is live.** `CHANGELOG.md:936-946` (v9.1.0) states in the project's own words that
`PASSAGE_PARALLELS_ENABLED` and `PASSAGE_MULTI_WITNESS_ENABLED` are both on in production and that
web selects letter-level by default when the index is available. An external third-party API prober
independently confirms it (`docs/OPEN_ISSUES.md:3`, 2026-09-08: *"witnesses[] returned 200 with 198
results"*). Yet `docs/guides/ENV_VARS.md:40` still carries `PASSAGE_PARALLELS_ENABLED=false` with none
of the "but ON in production since…" annotation `DISCOVERY_ENABLED` gets in CLAUDE.md's flag table. The
repo's most-consulted context file understates how live this unverified default is.

**H7 — the browse outage was a privacy bug.** `CHANGELOG.md:224-243`: anonymous browse requests
wrote into the **same process-wide recent-history store** used by signed-in users — *"recording every
viewed manuscript caused cross-user history leakage AND a backup plus multi-megabyte pickle rewrite on
the single event-loop thread."* It was live for an unknown period before a crawler triggered it hard enough
to cause an outage. The fix is partial by its own admission: *"the independent synchronous
connected-fragments fetch remains tracked in docs/OPEN_ISSUES.md and is NOT claimed as fixed here"* —
production mitigation is an nginx block on one crawler UA signature, which any other signature bypasses.
Nothing in the milestone's masking or discovery gates would ever have caught a defect in the browse-history
subsystem.

**H8 — Phase 145 SLOs.** `docs/specs/passage-index-build-measurements.md:163` states verbatim: *"Still
owed: cold-cache numbers (the decoy-read approximation in bench_passage_query.py --cold-touch-gb),
concurrency, and the web box."* §5 (:100): *"the acceptance table for warm and cold cache p50/p95/p99 is
still owed."* Only warm, single-process, dev-box latency was ever measured. No RSS/page-cache residency
budget, executor-saturation limit, or loop-lag ceiling exists for passage anywhere. This is not academic:
`docs/OPEN_ISSUES.md:207` logs *single-text passage exceeding its own 30s ceiling on 51-100 char inputs,
root cause unproven*, and :209 logs *multi-witness latency non-determinism — identical payload once
returned 198 results, once nothing in 120s*. A pre-deploy cold-cache/concurrency table is exactly the
artifact that catches that class before users do.

**H10/H16/H17 — the reviews feature is structurally unsound and live.**
`scripts/create_identification_reviews_beta.sql:64` puts `UNIQUE (identification_id, reviewer_key)` on the
base table; the submit RPC (:192-218) carries `ON CONFLICT … DO UPDATE SET … status='pending',
publish_comment=FALSE, moderation_note=NULL, reviewed_at=NULL, reviewed_by=NULL`. A revised vote
physically overwrites the prior judgment — relation chosen, comment, moderation state — with no trigger,
history table, or event log anywhere (grep for TRIGGER/history/audit/superseded/event: zero hits). There
is no band or confidence column at all; the nearest field is `displayed_relation`. Moderation
(`moderate_identification_review_beta_v2`, :348-428) is a plain `UPDATE … SET status = p_status`, and the
status CHECK (:53-54) allows only pending/approved/rejected — no hidden, no spam, no events table, no
aggregate-per-claim view. `IDENTIFICATION_REVIEWS_ENABLED` defaults true. **Every day this stays live,
more unrecoverable judgment history accrues**, and the loss cannot be quantified from the repository
because no row-count or telemetry for the table is checked in anywhere.

**H11 — a day of settled owner rulings is untracked.**
`.planning/phases/136.1-…/136.1-DISCUSS-CHECKPOINT.json` (git status `??`, dated 2026-08-22, one day
after the last commit to touch the planning docs) records the owner's reaffirmed ruling on PANEL-03's
licence gate: *"NO GATE — render whatever is staged. Staging a work in the reference corpus IS the
decision,"* applied retroactively including JA's 21 works. `grep -rn reuse_ok web/ shared/` returns zero
hits, so the code already matches the ruling. But ROADMAP.md:285 and :1300 still describe the gate as

that SC1 was deliberately **re-specified** to the shipped bake-time mechanism rather than fixed to the
original render-time spec, and that WORK-02 was ruled already met. Three of six SCs reshaped, in a file
that is not in git and would be lost on any workspace cleanup.

**H13 — the nightly artifact verify is not a gate.** It is a Windows Task Scheduler job on one personal
laptop (`Hillel-ROG`), not GitHub Actions — `.github/workflows/ci.yml` has no `schedule:`/`cron` trigger
anywhere. `schtasks /Query /TN GenizahSearch-VerifyReviewArtifact /V` shows Daily 03:00 but
**Logon Mode: Interactive only** (the script registers no `-Principal`/S4U credential). It did not fire at

**H14 — the Access export is untested.** `scripts/export_access_index.py` writes real R-source/M-source
provider basenames (`source_file.filename`, resolved from local `sourcekeys.json`) into an `.accdb` handed

`attach_review_cards`, `package_review_artifact`, `verify_review_artifact`, `attach_htr_realignment`,
`attach_gate_verdicts` — has a dedicated test file. This is the one script whose masking regression has an
external blast radius, and the one nobody tested.

**H19 — the atlas is inaccessible.** `web/pages/atlas.py`'s entire accessible surface for the graph is a
single static `aria-label` on the `<canvas>` ("The Visual Genizah Atlas", :261 and :350) plus per-control
labels in `atlas_decode.js`. No table, list view, or DOM structure exposes nodes, clusters or connections
independent of the Canvas 2D drawing. SC3/A11Y-02 requires a textual equivalent. The page is live and
**not behind the discovery beta flag** — a screen-reader user is fully blocked, not merely degraded.

**H22 — the caveat cannot reach the export.** `shared/discovery_panel_model.py:1139-1142` fires
`ds.low_coverage_note(lang)` on `low_coverage_marker`/`restored_by_human_confirmation`. But
`shared/discovery_surface_projection.py`'s `SURFACE_FINDING_FIELDS` (:233-260, the findings-page and
export allowlist) carries neither `low_coverage_marker` nor `routing_reason`; both exist only in
`SURFACE_CLAIM_FIELDS` (:160-178, the panel's allowlist). The identical identification with identical thin
evidence shows a caveat on `/browse` and none on `/computed-identifications` or its xlsx — the caveat
**cannot even be computed there**, because the data is not projected. BAND-04 requires the disclaimer on
all discovery surfaces. Worse, the two surfaces most likely to be shared outside the site are the two that
lose it. A second-order failure sits on top: `docs/OPEN_ISSUES.md:146` bundles this still-live gap with a
`relation_kind = min(claim_type)` overclaim sub-claim that **appears already fixed** by the relation matrix
(`findings_rows.py:1508-1516`, `discovery_service.py:960`, matrix commits 2026-08-12/13), so the entry

## Omissions, additions, divergences

**Omissions (24)** cluster in one place: everything downstream of the flag flip. Phase 139a (REL-01
closure), 139b (drill-down, observability, a11y, SEO) and 138 (leads) between them account for most of
them, and none of the three has a phase directory or a single post-freeze commit. The pattern is not that
the work was hard — it is that once `DISCOVERY_ENABLED=1` made the feature *look* delivered, the
obligations that were supposed to precede that state lost their forcing function.

**Additions (4, understated)** are the entire v9.1.0 and v9.2.0 release lines. Multi-witness RRF fusion, the
citation-authority overhaul, PGP links, the composition-sorting repair, the crawler outage fix — real,
valuable, user-facing work, none of it in any roadmap. The audit classes only four as formal additions
because most of the rest surfaced as record-drift against phases that claim the work is unstarted. The

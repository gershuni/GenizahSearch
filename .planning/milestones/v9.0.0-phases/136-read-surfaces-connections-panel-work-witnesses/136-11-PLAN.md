The first of two serial wiring passes into the build script: persist the two sort keys the surfaces
cannot compute at request time, materialize the identification grain and the manuscript display keys,
add the index set a corpus-wide query needs, and prove the budget is now met.

Purpose: the module work is done in parallel; this is where it lands in the bake. Splitting module
work from wiring work is what collapses eight sequential build-script plans into two. And the
performance case is measured, not theoretical: a representative findings ordering took 3.41–3.55 s
against a 1.5 s cap, and the deduped identification COUNT alone took 16 s.
Output: two new columns, two new tables, the index set, and a benchmark with a known failing baseline
it must now beat.
</objective>

    on some code paths.

    **Eligibility is `shipped` OR `human_confirmed`, not `shipped` alone.** This is the second half of
    the D-13g fix and it is easy to get wrong: the service restores review-only human-confirmed rows to
    the page query, then joins this table for the bucket and reason. If the table holds only shipped
    identifications, an inner join drops those rows a second time and a left join leaves them with no
    bucket and no reason — either way the fix is undone one layer down. Materialize every identification
    eligible under `routing_status='shipped' OR adjudication_status='human_confirmed'`, and carry a
    column recording which of the two admitted it so the surface can render the coverage note.

    **Resolve `display_work_id` deterministically.** `canonical_work_id` is NOT a unique key on `works`:
    15 duplicated groups exist, three with different titles and mixed source corpora, so joining the
    identification grain to `works` on it fans 64,509 rows out to 65,587. Apply the ordered, total
    selection rule from the schema amendment, store the result as `display_work_id`, and assert at build
    time that the identity join is exactly 1:1. Compute `main_pool` and `main_pool_reason` by calling
    `shared.discovery_main_pool.main_pool_decision` — never re-implement the gates here. Populate
    `best_band_rank`, `page_count`, `max_coverage_ppm` and `relation_kind` (the strongest claim type
    present). Leave `novelty_status`, `assertion_visibility` and `identity_visibility` for plan 136-12,
    which computes them.

    Derive `identification_id` as a deterministic content key over the canonical UTF-8 serialization of
    `sys_id` and `canonical_work_id`, following the id-recipe style already frozen in the schema.

    Because the grain is the CANONICAL work, this table is where the duplicate collapse becomes
    structural: two works recording the same `canonical_work_id` produce ONE identification row, so
    every count derived from this table is already deduplicated.

    Create and populate `manuscript_display` from `libraries.csv` only: `sys_id`, `library_code`,
    `library_sort_key`, `shelfmark_display`, `shelfmark_sort_key` (normalized so shelfmarks sort in a
    defensible order rather than raw lexical order). One row per `sys_id` carrying at least one shipped
    claim. This table exists because the paged result set today has no shelfmark, library sort key or
    total, which makes server-side sorting by library and a visible real total impossible.

    Add two build-time consistency assertions, so a grouping or join error fails the build instead of
    silently changing the corpus total:

    1. The number of distinct `(sys_id, canonical_work_id)` pairs across claims eligible under
       `shipped OR human_confirmed` equals the `discovery_identification` row count. Record the measured
       count and how it compares to the shipped-only figure, so the delta from the D-13g fix is visible
       rather than absorbed.
    2. `SELECT COUNT(*)` over `discovery_identification JOIN works ON display_work_id` equals the
       `discovery_identification` row count exactly. A fan-out here is the 65,587-row failure and it is
       invisible without this assertion.
  </action>

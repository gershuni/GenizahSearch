Make `_step`/`_record_verdict` async (or schedule via the show-loader pattern) so Prev/Next/verdict reload the candidate pane via `await ...update_content(...)`. NO naked `asyncio.ensure_future` for the loaders (this repo has NiceGUI client-context regressions from that pattern — Codex). **F-G5 (Codex):** `_fill_candidate` REPLACES the candidate `AnchorViewer` instance each step (`container.clear()` then a FRESH `AnchorViewer(...)` at :305-309) — so AnchorViewer's per-instance `_nav_gen` guard (anchor_viewer.py:514-546) does NOT make the modal latest-wins: an older in-flight viewer (built for the previous candidate) is a DIFFERENT object whose counter the new instance never bumps. Add a MODAL-LEVEL generation guard: `_fill_candidate` increments a modal-local `_cand_load_gen`, the candidate-reload coroutine captures its generation, and after `await update_content(...)` returns it no-ops if a newer `_fill_candidate` superseded it (mirrors the AnchorViewer pattern but at the modal scope, across instance replacement).
- **G1-compare (highlight in Compare):** `AnchorViewer.update_content` (anchor_viewer.py:604) calls `render_line_numbered_html(text=...)` with NO `highlight_html`. Add an optional `highlight_pattern` to `AnchorViewer.__init__` and pass a built `highlight_html` to `render_line_numbered_html(highlight_html=...)` (typography.py already accepts `highlight_html` — :66-68). **F-G1b (Codex):** do NOT pass `shared.joins_lab.htmlify(...)` directly — `htmlify` wraps its output in an outer `<div dir='rtl'>…</div>` (shared/joins_lab.py:706) AND emits `<br>` for newlines, while `render_line_numbered_html` SPLITS `highlight_html` on `\n` (after normalizing `<br>`→`\n`, typography.py:131-139) into per-line grid-row bodies — passing `htmlify` directly fragments the `<div dir='rtl'>` wrapper across numbered rows (the open tag lands in row 1, the close tag in the last row). Instead build a LINE-SAFE highlighter: escape `page.text` and inject the SAME `<b style='color:#dc2626'>…</b>` highlight span that `htmlify` uses (so the markup matches the rest of the app — F-G1a), but WITHOUT the outer `<div dir='rtl'>` wrapper, and keep `\n` as `\n` (do NOT pre-convert to `<br>`) so the per-line splitter counts lines correctly. The anchor pane and candidate pane each pass their candidate's `highlight_pattern`.
- **G3-compare (verdict-button state):** the Compare verdict buttons (compare_modal.py:404-419) are command-only — they never show which verdict is active for the current candidate. Add verdict-button refs and refresh their active/highlight style inside `_fill_candidate` (which already runs on open + every step), keyed by the current candidate's verdict from the shared `triage`. **F-G3c (Codex):** `_record_verdict` calls the pure `record_verdict(_state, ...)` helper which writes the verdict AND advances `_state` to the next candidate in ONE call (compare_modal.py:318-324) — so "refresh the just-recorded verdict before auto-advance" is NOT reachable as written (by the time `_fill_candidate` runs, `_state["current_candidate"]` is already the NEXT candidate). RESOLUTION: do NOT try to flash the recorded candidate's button; instead require active-state correctness only for the POST-ADVANCE candidate — `_fill_candidate(next_cand)` calls the verdict-button refresh keyed by `triage.get(next_cand.sys_id)`, so the buttons always reflect the candidate currently SHOWN. (The recorded verdict is persisted via `on_verdict` into the page triage and visible if the user navigates back.)

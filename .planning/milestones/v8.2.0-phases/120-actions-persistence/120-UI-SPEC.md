## Interaction Contracts

### Add-as-Join flow

1. User clicks "Add as Join" on a candidate card/row.
2. If anonymous: login-prompt dialog fires. On sign-in completion: dialog closes and the
   add-as-join action re-fires automatically (store pending action, invoke on auth complete).
3. If logged-in: confirmation dialog (see §2 above). On Cancel: no write, dialog closes.
4. On confirm: button enters spinner state (`props='loading'`). Supabase write fires off-loop.
5. On success: button shows transient success icon `check_circle` (500ms, then reverts to
   normal). Known-joins group re-fetches to reflect the new join. The triage for that
   candidate is NOT automatically set to "Yes" — the researcher decides triage separately.
6. On error: button reverts; inline `var(--error)` notice (12px) below the button:
   `tr('Could not add join. Check your connection.')`. Auto-dismiss after 8s.

### Remove-join flow (D-03)

1. User clicks `link_off` icon on their OWN join in the known-joins group.
2. Confirmation dialog (see §2 above). On Cancel: dialog closes, no change.
3. On confirm: icon enters spinner. Supabase delete fires off-loop.
4. On success: the join row is removed from the known-joins group. If the removed join was
   being used as the current anchor (re-anchored to that fragment), NO automatic re-anchor
   occurs — the anchor pane stays as-is.
5. On error: inline `var(--error)` notice (`tr('Could not remove join. Check your connection.')`)
   in the known-joins group; auto-dismiss after 8s; icon re-enabled.

### Add-to-Puzzle handoff (ACT-02, D-04)

**Staging mechanism (Claude's Discretion):** Server-side staging key via `safe_storage`.
Chosen over batched query params to avoid URL-length limits with large sys_id sets and to
keep the URL clean.

1. User checks ≥1 candidate in the TABLE view (the only view with multi-select — R2-H2; the bulk bar
   appears only on ≥1 table selection, so the anchor is always added IN ADDITION to ≥1 selected candidate).
2. User clicks "Add to Puzzle" in the bulk action bar.
3. The page writes a staging payload to `safe_user_set('puzzle_staging', {...})`:
   ```python
   {
     "schema_version": 1,
     "fragments": [anchor_sys_id, candidate_sys_id_1, ...],  # anchor always first
     "source": "joins_lab",
     "created_at": iso_timestamp,
   }
   ```
   Size cap: anchor + max 20 candidates (beyond 20: truncate + inline notice
   `tr('Only the first 20 selected candidates will be added to the Puzzle.')`).
4. Navigation: `ui.navigate.to('/puzzle')` (same tab; puzzle page reads the staging key
   on load and calls `_add_fragment_by_sys_id` for each entry sequentially).
5. The puzzle page MUST consume and clear the staging key on load to prevent stale
   handoff on next visit. If staging key is absent: puzzle page behaves as normal cold start.
6. No loading state on the Joins Lab side (navigation is immediate).

### Add-to-List flow (ACT-03, D-05)

1. User clicks "Add to List" in bulk action bar.
2. If anonymous: standard login-prompt dialog. No auto-retry on sign-in (user re-clicks).
3. If logged-in: a list-picker sub-dialog appears (simplified, single-level — "which list?"
   not "which fragment?" — since the selected candidates are already known):
   ```
   Add N candidates to list:
   [My Cairo Genizah Fragments  (23)]
   [Possible Joins — T-S 12.123  (8)]
   [+ Create new list…]
   [Cancel]
   ```
   On list selection: `add_list_item` fires for each selected candidate sys_id off-loop.
   Loading spinner on the dialog while writes are in flight.
4. On all-success: dialog closes, transient toast `tr('N candidates added to "{list_name}"')`.
5. On partial/full failure: dialog shows error summary; user can retry.

### Export flow (D-06)

1. User clicks "Export" menu item (CSV or XLSX).
2. If candidate count > 500: inline notice in the export menu (not a dialog).
3. Export dialog does NOT appear — export begins immediately with the progress bar shown
   below the toolbar (see §7 above).
4. Text fetches run off-loop, batched (e.g., 10 at a time), updating the progress bar.
5. On completion: file download triggers (`ui.download()` pattern). Progress bar disappears.
6. On Cancel click: fetches abort; progress bar disappears; no file downloaded.
7. On fetch error (network failure mid-batch): the progress card is replaced in-place by a
   dismissible `var(--error)` notice `tr('Export failed. Check your connection and try again.')`
   with a `[Retry]` flat button; no partial file is downloaded.
8. Export captures the candidate set as filtered and sorted at the time of export click
   (a snapshot — subsequent triage changes do not retroactively update the export).

### Persistence: save and restore (D-13/D-14/D-15)

**Schema extension (Phase 120 additions to the `joins_lab` `safe_storage` key):**

```python
{
    "schema_version": 1,              # UNCHANGED — Phase-120 keys are additive. CONTEXT D-16:
                                      # "extend v1; bump only on remove/retype". v1 blobs read
                                      # cleanly (missing keys default); bumping would DISCARD them
                                      # (read_joins_lab_state does an exact-match version check).
    "anchor_sys_id": "990001234",     # str | None (Phase 117)
    "anchor_fl_id": None,             # str | None (Phase 117)
    "anchor_volume_ie": None,         # str | None (Phase 117)

    # Phase 120 additions:
    "builder_rows": [                 # list of dicts, max 20 rows
        {
            "term": "...",            # str
            "gap_to_next": 0,         # int
            "modifiers": {},          # dict of bool flags
        }
    ],
    "builder_mode": "exact",         # "exact" | "variants" | "fuzzy"
    "text_position": "anywhere",     # matches search.py text_position values
    "flex_spacing": False,           # bool
    "bidirectional": False,          # bool
    "other_side_enabled": False,     # bool
    "other_side_rows": [],           # same shape as builder_rows
    "other_side_combine": "narrow",  # "narrow" | "widen"
    "triage": {},                    # dict[str, "yes"|"maybe"|"no"] keyed by sys_id; max 500 entries
    "active_filter": {},             # dict of filter state; mirrors FilterDialog state shape
    "view_mode": "grid",             # "grid" | "table"
}
```

**Cap enforcement:** `triage` dict capped at 500 entries (LRU eviction on overflow — evict
oldest untriaged entries first, preserve Y/? verdict entries). `builder_rows` capped at 20
(per builder widget max). `active_filter` JSON-serialized; must stay < 4KB.

**Schema version:** STAYS at `1` (unchanged from Phase 117). Phase-120 keys are additive and
non-breaking, so per CONTEXT D-16 ("extend v1; bump only on remove/retype") and the
`joins_lab_storage.py` docstring, the version is NOT bumped. Existing v1 blobs (anchor only) restore
cleanly — callers read the new keys with `.get(key, <default>)`. **Do not bump:** `read_joins_lab_state()`
discards on exact-version mismatch, so a 1→2 bump would wipe every user's persisted anchor. A future
*breaking* change (key removal or type change) is the only thing that bumps the version (to `2`),
and only then with explicit migration/discard handling.

**Save triggers:** Every state change writes the full `joins_lab` blob immediately
(`safe_user_set`). No debounce required (the payload is small and the write is off-loop).

**Restore flow:** On page load, if `joins_lab.anchor_sys_id` is non-None:
1. Show the restoring indicator (§8 above).
2. Load anchor (existing Phase-117 flow).
3. Restore builder state from the blob (populate the builder widget).
4. Auto-run the search (same as clicking "Run Search").
5. On results: restore triage (keyed by sys_id — orphan keys are harmless), filter state,
   and view mode.
6. Hide the restoring indicator.

### Clear / Reset (D-16)

On confirm in the Reset dialog:
1. `safe_user_set('joins_lab', None)` — clears the entire blob.
2. `safe_user_set('puzzle_staging', None)` — clears any pending puzzle staging key.
3. `ui.navigate.to('/joins-lab')` — full page reload to the cold-start state.
4. The test `tests/test_joins_lab_persistence.py` includes a case asserting that after
   `reset()` is called, `safe_user_get('joins_lab')` returns None.

### Hide VS Toggle when no VS data (D-12)

On anchor load:
1. An off-loop probe fires: `await run.io_bound(vs_service.get_suggestions, sid, 1)`.
2. If the result is empty (zero look-alikes): the VS toggle (`ui.switch`) is **hidden**
   via `.set_visibility(False)` (not disabled — absent entirely from the toolbar row).
3. If data exists: toggle renders normally (Phase-119 contract).
4. The toolbar reflows to fill the gap (the switch had `flex-shrink:0`; its absence
   simply closes that gap in the `ui.row` flex layout — no placeholder is needed).
5. If VS data later becomes available (re-anchor): the toggle is made visible again.

Note: when the toggle is hidden, the toolbar shape is:
```
[Candidates (N)] [Grid ● | Table] [Filters ▾] [← Prev page N/M Next →]
```
(The 👁 VS toggle position is simply empty — no gap, no placeholder text.)

### Sign-in route fix (D-18)

The "Sign in" button in the anonymous login dialog (`web/pages/joins_lab.py:1573`) is
changed from `ui.navigate.to('/settings')` to `open_login()` (the canonical sign-in
invocation from `web/pages/corrections.py:53`).

No visual contract change. The button label stays `tr('Sign in')`. The behavior change is:
the sign-in flow opens in-page (dialog or redirect, per existing `open_login` behavior)
rather than navigating away to /settings and losing the Joins Lab state.

## Off-loop Discipline (Phase-120 additions)

All new I/O operations obey the existing off-loop pattern (CI-guarded by
`tests/test_joins_lab_off_loop.py`):

| Operation | Off-loop call | Guard |
|-----------|---------------|-------|
| VS availability probe (D-12) | `await run.io_bound(vs_service.get_suggestions, sid, 1)` | generation counter; result ignored if anchor changed |
| Compare image prefetch (D-10) | `await run.io_bound(fetch_image, url)` per adjacent candidate | bounded 5-slot pool; SEED-008 `except RuntimeError: return` guard |
| Export text fetch (D-06) | `await run.io_bound(browse_text_fetch, sys_id, page)` batched | progress callback; cancel check after each batch |
| Add-to-List write (D-05) | `await run.io_bound(supabase.add_list_item, ...)` | SEED-008 guard |
| Add-as-Join write (D-01) | `await run.io_bound(supabase.create_fragment_join, ...)` | SEED-008 guard |
| Remove-join write (D-03) | `await run.io_bound(supabase.delete_fragment_join, ...)` | SEED-008 guard |

**SEED-008 guard pattern (D-20):** Every post-await UI mutation in fire-and-forget tasks
is wrapped in `except RuntimeError: return`. The SEED-008 hardening is a code correctness
requirement, not a UI affordance — no visual contract needed beyond what is already spec'd
for each operation's success/error states above.

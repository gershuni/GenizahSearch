## The three bugs and their fixes

### Bug 1 — Office temp files (`~$foo.docx`) polluting the indexer
**Symptom (from console):**
```
Phase 97 C-05: skipping c:\...\~$י ונכרי.docx — not a valid zip-container file
```
Word/Excel/PowerPoint create transient lock/owner files named `~$<name>.ext`
while a doc is open. They are not valid zip containers, so the docx/xlsx
zip-bomb pre-check (`shared/local_indexer.py` `_check_zip_bomb`, status path at
~line 1621-1655) logged them as `zip_bomb_suspected`, wrote rows to
`processed_files` + `local_files`, and they showed in the opt-out tree forever.

**Fix:** new `is_office_temp_file(filename)` helper (basename starts with `~$`),
applied at all THREE enumeration sites:
- `shared/local_indexer.py::_iterate_supported_files` (the indexer scan that builds `disk_files`)
- `shared/local_indexer.py::prescan_count` (the D-26 ceiling-dialog counter)
- `desktop/my_library_tab.py::FolderWalkWorker` (the opt-out tree walker; imports the helper)

### Bug 2 — `'SearchEngine' object has no attribute 'dynamic_rank_map'`
**Symptom (from console):**
```
MyLibraryTab._maybe_rebuild_lab_if_stale: rebuild_local_lab_index failed:
'SearchEngine' object has no attribute 'dynamic_rank_map'
```
**Architecture:** there are two engines. `LabEngine` (genizah_core.py class ~line 693)
owns `dynamic_rank_map` + `settings`. `SearchEngine` (class ~line 6769) does NOT —
this same split was already fixed under "CR-01" for `_current_lab_weights_hash`
(SearchEngine version at ~6960 uses `getattr` defaults; LabEngine version at ~808
uses the real attrs). But `SearchEngine.rebuild_local_lab_index` (~7015) still read
`self.dynamic_rank_map`/`self.settings` directly → crash.

The caller `MyLibraryTab._maybe_rebuild_lab_if_stale` (my_library_tab.py ~1037)
checks freshness on the **LabEngine** (`lab._check_local_lab_freshness()`) but
rebuilt on the **SearchEngine** (`search.rebuild_local_lab_index(...)`).

**Fix:** `rebuild_local_lab_index(self, local_indexer, lab_engine=None)`. Caller
passes `lab_engine=lab`. Weights are sourced from `lab_engine` (falling back to
`self` via `getattr`) and normalized **identically** to
`LabEngine._current_lab_weights_hash`:
```python
lab_weights = {
    "dynamic_rank_map": dyn_map if dyn_map else None,
    "use_dynamic_weights": getattr(settings, "use_dynamic_weights", False) if settings else False,
}
```

**Why the normalization matters (the load-bearing subtlety):**
- `build_lab_side_index` (shared/local_indexer.py ~3550) writes
  `weights_hash = sha256(json.dumps(lab_weights, sort_keys=True))` into `.meta.json`.
- `LabEngine._check_local_lab_freshness` recomputes
  `sha256(json.dumps({dynamic_rank_map if … else None, use_dynamic_weights}, sort_keys=True, default=str))`
  and compares to `.meta.json`.
- If these don't match byte-for-byte, the index is judged **perpetually stale**
  and rebuilt on every reload. A naive `getattr(self,…,None)` fix on SearchEngine
  would have written a None-map hash that never matches the LabEngine's real-map
  hash → infinite rebuild loop.
- Verified by hand: rebuild's `lab_weights` hash == LabEngine freshness hash for
  both a real JSON map and the None case. (`default=str` is a no-op because the
  map is JSON-native — loaded from `Config.LAB_WEIGHTS_FILE` JSON — and the other
  value is a bool.)

### Bug 3 — LOCAL search result counter "500 of 500", "486 of 500" (backwards)
**Symptom:** A LOCAL search returned 2247 results. Opening a result via the
per-row 👁 "View result" button showed "result 500 of 500"; the next file "486
of 500"; counting down by file. (Gap of 14 = the previous file had 14 pages.)

**Root cause:** `genizah_app.py::show_full_text_for_result` (~18376, called from
the 👁 button at ~16697 via `lambda _, r=res: self.show_full_text_for_result(r)`).
The loop that locates the clicked result in `_collect_sorted_results()` fell back
to matching on `display.id` **with no `break`**, so it kept overwriting
`target_index` and landed on the **LAST** row sharing that id. A LOCAL file's
pages all share one `display.id`, so every result of a file opened at that file's
last position → backwards-by-file counter.

NOTE: source order is correct (Tantivy returns LOCAL hits best-first via
`_query_local_index`, genizah_core ~7054). It was NOT a reversed list.

**Fix:** match exact per-page `uid` first (or object identity), then fall back to
the FIRST `display.id` match with a `break`.

## REVIEW CONCERNS — scrutinize these specifically

1. **Bug 2 hash parity & fingerprint consistency.** Confirm the rebuild's
   `lab_weights` dict serializes to the SAME `weights_hash` that
   `LabEngine._current_lab_weights_hash` computes (note one uses `default=str`,
   the other doesn't — argue why they still match, or find a case where they
   diverge, e.g. a non-JSON-native value ever entering `dynamic_rank_map`). ALSO:
   build-time fingerprints use `dyn_map` from the LabEngine; query-time LAB-mode
   composition uses LabEngine's `dynamic_rank_map`. Confirm these are the same
   object/source so fingerprints are consistent. Is there any caller of
   `rebuild_local_lab_index` that still passes no `lab_engine` and runs on a
   SearchEngine with a real (non-None) `dynamic_rank_map` that we'd now ignore?

2. **Bug 3 `uid` assumption.** Does every LOCAL hit dict actually carry a unique
   per-page `uid`? (See `_build_local_result_dict`, genizah_core ~7117, D-34
   "unique F-suffix per file".) If `uid` is missing/None for some hits, the code
   falls to first-id-match — is landing on the file's FIRST page acceptable when
   the exact page can't be identified? Any case where two DIFFERENT results share
   a `uid`? Does `_collect_sorted_results()` (genizah_app ~18313) preserve `uid`
   on the dicts it returns (it reads `UserRole` data from `COL_SYS_ID`)?

3. **Bug 1 enumeration completeness & deletion semantics.** Are there OTHER file
   enumeration sites that should also skip `~$` (e.g. `estimate_index_size` —
   probably not, it sums index-dir files, not source files)? More important:
   `scan_all` has a "detect deleted files" pass (cached-but-not-on-disk →
   `_delete_file`). A `~$` file indexed BEFORE this fix is now absent from
   `disk_files`, so it will be deleted from the index on next scan. Confirm that's
   harmless cleanup (it is intended), not a data-loss footgun. Case-sensitivity:
   `~$` is ASCII; fine on Windows. Any legitimate user file that starts with `~$`?
   (Effectively never — it's a reserved Office pattern.)

4. **Bug 3 scope.** `show_full_text_for_result` is the 👁-button path. The
   double-click path is `show_full_text` (~18358) which uses `currentRow()`
   directly and was NOT changed. Confirm the fix doesn't need to be mirrored
   there, and that the two paths stay consistent.

# Phase 97.3: Code Review Report

**Reviewed:** 2026-05-26T22:30:00Z
**Depth:** standard

## Summary

Phase 97.3 introduces three substantive deltas in `desktop/my_library_tab.py`
(Reset-guard simplification, Skip → suppress-auto-rescan one-shot flag, and the
big async-tree-worker refactor in `_UnifiedFileTreeWidget` + `FolderWalkWorker`)
plus an import-time PyMuPDF stderr-suppression block in `shared/local_indexer.py`.

The diff is internally consistent and well-commented (every block cross-references
its D-NN decision and the Codex critique that produced it). Threading
correctness is generally solid: generation tokens guard cross-thread queued
signals, the retention-list pattern for cancelled QThreads is sound, and
`os.walk` is correctly hardened against Windows reparse points and inaccessible
subdirs.

Two warnings worth fixing before v7.14.1 ships:

1. **WR-01 (race in `_on_tree_population_ended`)** — a stale-worker
   `finished_signal` from a superseded tree-worker can disable the Cancel
   button while a NEWER tree-worker is still running. User-visible symptom:
   rapid folder-switching leaves Cancel greyed out even though a walk is
   still progressing. Direct regression risk against the "broken Reset
   button" / "UI freezes" class of bugs the user already cares about.

2. **WR-02 (extension-set drift between tree and indexer)** — the tree
   pre-filter now imports `_SUPPORTED_EXTENSIONS = {.docx,.pdf,.txt,.html,.xlsx,.csv}`
   from `shared/local_indexer.py`, but only `.pdf`/`.docx`/`.txt` paths have
   real extraction code. The pre-Phase-97.3 `_populate_node` hard-coded the
   3-extension set. The tree now shows `.html`/`.xlsx`/`.csv` files with no
   way for them to ever index — they will all end up with `status=''` in the
   Status column. This is a behavioural change that crept in via a
   "single source of truth" cleanup, and the comment ("closes R97.3-N")
   reads as if it were intentional, but the user-facing effect (tree shows
   files that can never be indexed) is not signposted anywhere in the plan
   summaries.

Info items cover defensive cleanups, doc-comment drift, and one mild
performance worry (`_invalidate_prior_status_cache` does N synchronous DB
calls and is fired on six code paths).

## Warnings

### WR-01: Cancel button can be disabled while a newer tree-worker is still running

**File:** `desktop/my_library_tab.py:1626-1637` (`_on_tree_population_ended`)
**Issue:**
When the user rapidly clicks Folder A then Folder B, this sequence occurs:

1. Click A → tree_worker_A starts → `_on_tree_population_started()` enables `_btn_cancel`.
2. Click B → `populate_for_folder` calls `_cancel_existing_tree_worker()` →
   worker_A moved to `_retired_tree_workers`, `_tree_worker = None`.
3. New tree_worker_B is created, `_tree_worker = worker_B`,
   `_on_tree_population_started()` re-enables `_btn_cancel` (no-op, already on).
4. worker_A eventually exits and emits `finished_signal` with its stale token.
5. `_on_tree_finished` → `_release_finished_worker(worker_A)` → removes from
   retention list, sees `self._tree_worker is worker_B (not worker_A)` and
   correctly skips clearing `_tree_worker`. Good so far.
6. `_release_finished_worker` then calls `_on_tree_population_ended()`,
   which checks ONLY the scan worker: `if not (self._worker is not None and
   self._worker.isRunning())`. Scan worker is None → it disables `_btn_cancel`
   even though tree_worker_B is still walking the filesystem.

User-visible symptom: rapid folder-switching leaves Cancel greyed out while a
walk is still progressing, contradicting the very invariant the Codex Critique
#3 HIGH fix was added to enforce. Also raises mild risk under R97.3-A
acceptance "Cancel button always reflects whether SOMETHING is cancellable".

**Fix:**
Make `_on_tree_population_ended` also short-circuit when a current tree
worker is still running:

```python
def _on_tree_population_ended(self) -> None:
    try:
        # Don't disable while a NEWER tree worker is still active.
        tree_worker = getattr(self._unified_tree, "_tree_worker", None)
        tree_still_running = (
            tree_worker is not None
            and hasattr(tree_worker, "isRunning")
            and tree_worker.isRunning()
        )
        scan_running = self._worker is not None and self._worker.isRunning()
        if not scan_running and not tree_still_running:
            if hasattr(self, "_btn_cancel") and self._btn_cancel is not None:
                self._btn_cancel.setEnabled(False)
    except Exception:  # noqa: BLE001
        pass
```

The same pattern (check both `_worker` AND `_unified_tree._tree_worker`)
should be applied wherever the cancel button's lifetime is decided. A
regression test that walks two large folders back-to-back and asserts Cancel
stays enabled until both workers exit would pin this.

### WR-02: Tree pre-filter now includes `.html`/`.xlsx`/`.csv` — extensions that have no extraction path

**File:** `desktop/my_library_tab.py:62, 858` (import + filter site);
`shared/local_indexer.py:110` (set definition)
**Issue:**
Pre-Phase-97.3, `_populate_node` hard-coded `SUPPORTED = {'.pdf','.docx','.txt'}`
for the tree. Phase 97.3 unified the filter to import
`_SUPPORTED_EXTENSIONS` from `shared/local_indexer.py`, which is
`{".docx", ".pdf", ".txt", ".html", ".xlsx", ".csv"}` (Phase 97 D-NEW set).

Effect: clicking a folder now shows `.html`, `.xlsx`, and `.csv` files in
the tree alongside the indexable formats. But `LocalIndexer.scan_all` only
has extraction codepaths for `.pdf` / `.docx` / `.txt`. Per `_ERROR_STATUSES_KEPT`
in `shared/local_indexer.py:112-116`, these will land with `status='unsupported'`
(or be dropped entirely), and the user will see them in the tree forever
with no Pages count and no clear Status. The "Help" page (per CLAUDE.md
v7.14.0 entry) tells users they can index `.docx` / `.pdf` / `.txt`.

The comment in the worker docstring (`my_library_tab.py:741`) reads
"Pre-filters by _SUPPORTED_EXTENSIONS imported from shared.local_indexer
(single source of truth — closes R97.3-N)" — phrased as a quality
improvement, but the new behaviour appears to silently broaden what the
tree advertises beyond what the indexer can actually process.

**Fix:**
Either (a) narrow the worker filter to the actually-indexable set, e.g.:

```python
# In FolderWalkWorker.run():
_INDEXABLE_EXTENSIONS = {'.pdf', '.docx', '.txt'}  # mirrors _ERROR_STATUSES_KEPT
# Or import from a clearly-named constant in shared.local_indexer that
# only contains formats with real extraction codepaths.
...
if ext not in _INDEXABLE_EXTENSIONS:
    continue
```

or (b) keep the broader filter but split `shared/local_indexer.py` into two
constants — `_SUPPORTED_EXTENSIONS` (kept as the I/O surface) and a new
`_EXTRACTABLE_EXTENSIONS = {'.pdf','.docx','.txt'}` — and import the latter
into the tree-walker. The current single-source-of-truth optimisation
sacrifices a behaviour invariant the user already lived with for ~2 weeks.

If the broader set IS deliberate (e.g. a feature flag for upcoming
xlsx/csv extraction), the CHANGELOG entry for v7.14.1 should call it
out so users do not misread the new rows as "the tree is broken".

## Info

### IN-01: `_invalidate_prior_status_cache` does N synchronous DB calls on the UI thread

**File:** `desktop/my_library_tab.py:2376-2404`
**Issue:**
`_invalidate_prior_status_cache` iterates `self._indexer.list_folders()` and
issues a `get_file_status_for_folder(path)` for each. It is called on six
code paths (per the CLAUDE.md / Codex Critique #3 plan):
constructor end, `_on_worker_finished`, `_on_worker_error`,
`_on_cancel_finished_drain`, `_perform_reset`, `_on_add_folder_clicked`,
`_on_remove_folder_clicked`. For a power user with 30+ folders this could
introduce a perceptible UI hitch on the post-scan completion path.

Out of scope per "v1 performance is not in scope," but worth noting as a
follow-up.

**Fix:**
Either move the rebuild into a `QThreadPool.globalInstance().start(...)`
worker, or rebuild only the touched folder's slice (the click path is
already protected by D-12 — the cache for the just-selected folder is what
matters).

### IN-02: `_canonical_filepath` recursion in `_ensure_dir_node` is unbounded

**File:** `desktop/my_library_tab.py:304-331`
**Issue:**
`_ensure_dir_node` recurses with `os.path.dirname(canonical_dirpath)`. For
pathologically deep folder trees (e.g., a Junction-loop the prune step
missed, or a path approaching MAX_PATH limits) this could approach Python's
default recursion limit (1000). The reparse-point pruning at
`my_library_tab.py:840-852` covers the common Windows-junction case, but
the recursion has no depth ceiling of its own.

**Fix:**
Convert `_ensure_dir_node` to an iterative loop. Walk up to the cached
ancestor while pushing un-cached paths onto a stack, then create from the
top down. This also avoids the small overhead of repeated `normcase/normpath`
calls per level.

### IN-03: Bare `except Exception:` in `_release_finished_worker` swallows real bugs

**File:** `desktop/my_library_tab.py:412-426`
**Issue:**
The `try/except (ValueError, RuntimeError):` on `_retired_tree_workers.remove(sender)`
is correct (`remove` raises ValueError on missing). But the outer
`except Exception: pass` around `_on_tree_population_ended` call is broad
enough to swallow `AttributeError` if the tab is partially-constructed or
a future refactor renames `_on_tree_population_ended`. The current
`# noqa: BLE001` acknowledges this; in practice the `logger.debug` /
`logger.exception` pattern used elsewhere in the file would surface
genuine bugs without breaking the slot.

**Fix:**
Replace `pass` with `logger.debug("_release_finished_worker: tab notify failed: %s", exc)`
so a regression in the tab callback signature does not silently fail.

### IN-04: `_walk_onerror` callback runs on worker thread but logs without thread-id

**File:** `desktop/my_library_tab.py:801-805`
**Issue:**
The `os.walk(..., onerror=_walk_onerror)` callback fires on the worker
thread. The `logger.warning(...)` it emits is thread-safe (Python logging
handles its own locking) but the log line does not include a thread name
or worker token, making post-hoc debugging of "which walk failed where"
harder than necessary.

**Fix:**
Include the token in the log line:
```python
def _walk_onerror(exc: OSError) -> None:
    logger.warning(
        "FolderWalkWorker[token=%d]: os.walk failed for %s: %s",
        token, getattr(exc, "filename", "?"), exc,
    )
```
The closure already has access to `token` (line 795). Same suggestion
applies to the `_canonical_filepath` and `os.stat` failure paths below it.

### IN-05: Phase 97.3 R97.3-C comment in `shared/local_indexer.py` references "Codex Critique #2" rather than the SPEC line

**File:** `shared/local_indexer.py:70-80`
**Issue:**
The docstring above the `fitz.TOOLS.mupdf_display_warnings(False)` /
`mupdf_display_errors(False)` block reads:

> Broad except Exception per Codex Critique #2 — suppression is
> non-critical; a future PyMuPDF API change must NOT crash module import...

For a future maintainer who does NOT have the Codex critique handy, this
prose justifies the `except Exception` but does not say WHAT the SPEC
acceptance criterion is. A one-line cross-reference to the spec section
(e.g., "SPEC R97.3-C acceptance: zero MuPDF error: lines on stderr") would
make the block self-documenting.

Not a code defect; just a docstring-drift note for the inevitable future
PyMuPDF upgrade that breaks `fitz.TOOLS.mupdf_display_errors`.

**Fix:**
Add a single line at the top of the block:
```python
# SPEC R97.3-C acceptance: "zero MuPDF error: lines on stderr"; D-11.
```

**Confirmed root cause (commit 829cd7cf, 2026-03-27 — NOT Phase 74):**

1. User searches `"שלום"` on `/`. The search executes successfully.
2. At `web/pages/search.py:4176`, `history.replaceState(null, '', '/search?q=שלום')` stamps the URL bar.
3. `persist_search_snapshot(search_state)` at `search.py:4184` writes `app.storage.user['search_results'] = [...]` and related snapshot keys — but NOT `search_query` (excluded by design per `search_state.py:345-351`).
4. User clicks Browse on a result → navigates to `/browse?sys_id=...`.
5. User hits browser **Back** → browser restores `/search?q=שלום`.
6. `search_page_route(q='שלום', ...)` at `main.py:901` receives `q='שלום'`, passes it as `initial_query` into `create_search_page`.
7. `resolve_search_bootstrap` at `search_bootstrap.py:35` computes `has_route_context = True` because `initial_query='שלום'` is non-empty.
8. Line 39: `restore_saved_state = not has_route_context` → **False**.
9. Line 64: `'restore_saved_results': restore_saved_state` → **False**.
10. Back in `search.py:240`: `if restore_saved_results and 'search_results' in app.storage.user:` → guard fails → saved results never hydrated → user sees an empty page → a fresh search fires (via auto-execute or user retry).

**Why this is hypothesis (a) from the prompt:** URL contains query params on Back → has_route_context=True → restore_saved_state=False → snapshot ignored.

**Why Phase 74 was suspected but ISN'T the origin:** Phase 74 did not modify `web/search_bootstrap.py` (verified by `git log 56facc3d..HEAD -- web/search_bootstrap.py` → empty). The gating logic dates to `829cd7cf` on 2026-03-27, 3 weeks before Phase 74 landed. The 75-UAT.md Gaps entry's Phase-74 attribution is incorrect but the gap itself is real.

**Why 829cd7cf's intent was legitimate and must be preserved:** The March 27 fix was protecting against "stale saved mode/filters/results from prior sessions" when a user navigates to `/search?q=X` via a shared link or homepage nav. In that scenario, saved state is genuinely stale and should not leak into the new search. The Back-from-browse case is different: the URL's `q=` was written by THIS session's own `history.replaceState`, so the saved snapshot IS the authoritative state for that query.

**The distinguishing signal:** When URL `q` matches saved `search_query` AND a non-empty `search_results` cache exists in `app.storage.user`, this is back-navigation, not a fresh URL-driven search. Use this signal to restore.

**CRITICAL secondary finding — saved_query storage-write hole (MUST be fixed by Task 2 Edit 2):** The distinguishing signal above only works if `app.storage.user['search_query']` actually holds the query that was last searched. In the current code, `search_query` is written:
- On query input `blur` (web/pages/search.py:401) — fires only if the input loses focus
- On "New Search" reset (search.py:2016) — wipes it to ''

It is NOT written at search-execute time. If a user types `שלום` and presses **Enter without clicking away first**, the input never blurs, and `search_query` holds the PREVIOUS query (or ''). Then the back-nav guard `initial_query == saved_query` fires incorrectly (or not at all). **The fix is a silent no-op for Enter-to-search.** Plan 75-03 Task 2 Edit 2 closes this hole by writing `app.storage.user['search_query'] = clean_query` at the same site where `history.replaceState` stamps the URL (~search.py:4184, alongside `persist_search_snapshot`). This makes `saved_query` an authoritative mirror of the URL the browser will restore on Back.

<objective>
Extend `genizah_core.lab_composition_search` to record per-chunk attribution in `results_map[uid]['chunk_hits']`. This implements **D-13 Path A** (the locked decision in Plan 01) so the Phase 77 parallels JSON export can emit `matches: [{chunk_index, source_chunk_text, manuscript_snippet, score}, ...]` truthfully — without this change, per-chunk identity is collapsed into `total_score`/`hits_count` integers and D-13 cannot be satisfied (RESEARCH §Pitfall 3).

Purpose: Unblock Plan 03's `serialize_parallels_payload(...)` from being able to emit truthful `matches[]` arrays. Without this, Plan 03 would have to fall back to Path B (degenerate single-element matches) and document the loss — which violates D-13's intent and makes Phase 80 `/api/parallels` ship with the same lossy shape later.

Why this is its own plan (not folded into Plan 01): the change is to `genizah_core.py` (~12k lines, the sensitive search engine) — it deserves a focused review pass and its own commit. The change itself is small (~10 lines added inside an existing block) but the file is load-bearing.

Output:
- `results_map[uid]` initialization gains `'chunk_hits': []`
- Inside the per-chunk loop, an `append((i, chunk_text, match_score, ms_snip))` call is added at the same site that increments `total_score`/`hits_count`
- One new test file `tests/test_lab_composition_chunk_hits.py` proving the extension works on a synthetic input
- ZERO behavioral change for existing callers reading `total_score`/`hits_count`/`ms_matches`
</objective>

## Open question 1 — How to bridge FolderWalkWorker's flat batch signal to the tree's hierarchy + canonical-path + prior-status needs

The pre-existing `FolderWalkWorker` emits flat `(filepath, mtime_ns, size)` tuples in batches of 100 OR 0.5s. The tree population needs THREE things per leaf:
1. Hierarchy (which parent `QTreeWidgetItem` does this file go under?) — reconstructible from the path string by splitting on `os.sep` and walking from the folder root.
2. Canonical filepath (via `_canonical_filepath()`) — needed as the LOOKUP KEY into `prior_status` (a dict that the slot has from a prior scan).
3. The actual `prior_status[canonical]` — `{pages, status}` overlay for the leaf's Pages and Status columns.

The current synchronous `_populate_node` does all three on the main thread per file. The fix moves the walk off-thread; the open question is where canonicalization happens and how the slot consumes the worker's output without re-introducing main-thread waste.

**Option A: Reuse `FolderWalkWorker` as-is; UI slot canonicalizes + builds hierarchy as it consumes batches.**

Pros: zero new classes, existing AST guard valid, minimal blast radius.
Cons: canonicalization (`Path.resolve` → `os.path.realpath`) runs on the UI thread per leaf. Codex's own critique noted both tracebacks (in `Path.resolve` and `os.path.isfile`) — moving `os.path.isfile` off-thread by using `os.scandir`/walk in the worker fixes one cost; but `_canonical_filepath` is the other. The user's repro was 100K+ files at ~1ms/resolve on Windows = 100s of main-thread work. Even chunked with `QApplication.processEvents()` between every 20 items, the bar still ticks at <100ms responsiveness only if each chunk is ≤100 resolves ≈ ≤100ms. Borderline.

**Option B: Extend `FolderWalkWorker` signal to emit `(filepath, canonical, mtime_ns, size)` — canonicalize in the worker.**

Pros: pushes the entire walk + canonicalize cost off-thread. UI slot does only widget construction and `prior_status[canonical]` lookups. The walk's signal batching (100 files / 0.5s) already throttles the UI work to a known ceiling.
Cons: changes the public signal signature. The existing AST guard `test_folder_walk_worker.py::test_no_widget_mutation` doesn't pin the signal arity, but other tests might. Also, `_canonical_filepath` does the Windows `\\?\` long-path prefix — that's safe in a worker (no Qt calls), so the only concern is whether `Path.resolve()` is thread-safe on Windows. (It should be — it's just stat-like syscalls.)

**Option C: Write a new `FolderTreeBuildWorker` that wraps the same `os.walk(followlinks=False)` and emits tree-shaped records.**

Pros: maximum decoupling. Could emit records like `(rel_parts: tuple[str, ...], canonical: str, pages: int, status: str, checked: bool)` — the slot just creates leaves and sets columns. Pre-resolves prior_status in the worker too (looking up the dict is cheap).
Cons: two parallel walkers in the codebase. Duplication. `FolderWalkWorker` was added in Phase 97 U-03 for a different use case (the eventual indexer pre-scan, presumably) — having both is fine but the boundary needs to be clear.

**Critical extra constraint:** `_unified_tree.populate_for_folder(folder_path)` is called with ONE folder path per click, not a list. `FolderWalkWorker.__init__(folder_paths: list)` takes a list of folders; we'd pass `[folder_path]`. Trivial adaptation. The current `_populate_node` also walks ONE folder per click.

**Codex's own prior recommendation** (in `.planning/debug/post-97.2-uat-bugs-codex-critique.md`): Option C (`FolderTreeBuildWorker` with `os.scandir(follow_symlinks=False)` and tree-shaped records). Now that you have the actual `FolderWalkWorker` to look at, do you stand by C, or revise toward B?

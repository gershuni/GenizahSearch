# Phase 97.3: My Library UAT Stability — Specification

**Created:** 2026-05-26
**Ambiguity score:** 0.12
**Requirements:** 6 locked

## Goal

Eliminate the four post-Phase-97.2 UAT failures that make the desktop "My Library" tab unusable on real-world folders: the UI-thread freeze on folder selection (Bug A), the Reset button being disabled precisely when users need it after a crash (Bug B), recovery-Skip silently re-launching the broken scan (Bug D), and the "stuck at 0%" mystery during scan enumeration (Bug E). Also bundle two truly-free adjacent fixes: silence 624× MuPDF stderr noise (Bug C) and expose the indexer's full supported-extensions set in the opt-out tree (Bug N3).

## Background

Phase 97.2 shipped 2026-05-26 (25 commits, all 8/8 R97.2-* requirements MET, REVIEWS HIGH #3/#5/#6 closed). On the same day, the user smoke-tested by adding a small folder and then a mega-heavy folder. Four distinct failures surfaced:

**Bug A — UI-thread freeze on folder selection.** `desktop/my_library_tab.py::_on_folder_selection_changed` (line 968, a Qt slot on the main thread) calls `_unified_tree.populate_for_folder` → `_populate_node` recursively. Every directory hits `os.listdir` + `os.path.isdir` (follow_symlinks=True by default — can escape the tree via junctions); every file hits `os.path.isfile` + `_canonical_filepath` (which calls `Path.resolve(strict=False)` → `os.path.realpath`, expensive on Windows). Mega folders freeze the UI for minutes; Cancel is unreachable because it shares the main thread. Both UAT tracebacks land in this recursion (one at `_canonical_filepath`, one at `os.path.isfile`). This code path was introduced by Phase 96 plan 96-08 ("Phase 96 D-F1: folder selection handler"), NOT Phase 97.2 — the traceback line numbers shifted because Phase 97.2-02 added the Reset button code below, but the recursion is unchanged. A pre-existing `FolderWalkWorker` skeleton exists in the codebase with tests but is unwired into `_UnifiedFileTreeWidget`.

**Bug B — Reset button blocked when stale `scan_runs` rows exist.** `_update_reset_button_state` (line 1317) disables `_btn_reset` if EITHER (a) a worker is running OR (b) `start_recovery_probe()` returns non-empty (orphan `scan_runs.status='running'` rows). After a crash, orphan rows exist — and orphan rows are precisely the symptom Reset is supposed to clean up. The guard was added as a Phase 97.2-02 REVIEWS Codex MEDIUM recommendation for proactive button state, but the corner case "user just crashed, opens app, wants to reset" was not exercised.

**Bug D — Recovery-Skip silently re-runs the broken scan.** Constructor at line 714–733: `start_recovery_probe()` → if non-empty, `_show_recovery_modal()` → user clicks Skip → `_end_scan_run(run_id, 'canceled')` flips orphan to canceled → then `_auto_rescan_on_startup()` at line 729 (D-25 silent background rescan) immediately spawns a worker on the same registered folders, which then re-enters the same mega-folder that just froze the app. From the user's POV: "I clicked Skip but the scan is running anyway."

**Bug E — "Stuck at 0%" during scan enumeration.** `shared/local_indexer.py::scan_all()` builds the full `disk_files` dict (recursive `os.walk` across all registered folders) before emitting the first `progress_updated` signal. For mega libraries this takes long enough that the progress bar shows 0% indefinitely — but the worker IS alive, it's discovering. UI gives no signal.

**Bug C — MuPDF "unknown keyword: 'TF'" × 624.** PyMuPDF logs a stderr warning when parsing the `Tf` (SetFont) operator in malformed PDF streams. 624 = one warning per PDF page across the user's test folder. Pure stderr noise, no crash, but clutters logs and looks alarming. Silenceable via `fitz.TOOLS.mupdf_display_warnings(False)`.

**Bug N3 — UI tree extension mismatch.** `shared/local_indexer.py:81` declares `_SUPPORTED_EXTENSIONS = {.docx, .pdf, .txt, .html, .xlsx, .csv}`. The UI tree at `desktop/my_library_tab.py:227` declares only `SUPPORTED = {.pdf, .docx, .txt}`. Newer formats (`.html`, `.xlsx`, `.csv`) get indexed but are invisible in the opt-out tree, so users can't selectively skip them.

**Codex full analysis:** `.planning/debug/post-97.2-uat-bugs-codex-critique.md` (called out one additional pre-existing defect: `os.path.isdir(full)` in `_populate_node` follows symlinks, unlike the indexer's `os.walk(followlinks=False)` — can recurse into junctions outside the selected tree).

## Requirements

1. **R97.3-A — Folder-selection UI must stay responsive regardless of folder size.**
   - **Current:** `_on_folder_selection_changed` → `populate_for_folder` → `_populate_node` does a recursive synchronous walk on the Qt main thread, calling `os.listdir` + `os.path.isdir` (follow-symlinks=True) + `os.path.isfile` + `_canonical_filepath` (which calls `Path.resolve`) for every entry, then `expandAll()`. UI freezes for minutes on mega folders. Cancel button is also on the main thread and is unreachable during the walk.
   - **Target:** Folder selection moves the recursive walk + canonicalize off the main thread (worker thread, with cancellation). The Qt UI thread paints within 100ms of the click. The tree fills progressively as the worker emits batches. The walk uses `os.scandir` with `follow_symlinks=False` to match the indexer's `os.walk(followlinks=False)` semantics so it cannot escape into junctions. `expandAll()` is bounded — applied only if the populated tree has ≤ a configurable item count (default 500) to avoid blocking on Qt's layout pass for huge trees.
   - **Acceptance:** With a synthetic test folder containing ≥ 10,000 files (mix of supported + unsupported extensions across nested subdirs), clicking the folder in the registered-folders list (a) returns control to the Qt event loop within 100ms (verifiable by a Qt test driver that checks the cancel button's responsiveness via `QApplication.processEvents()`), (b) the Cancel button is enabled and clickable while the tree fills, (c) clicking Cancel stops the walk and aborts the tree population without crashing, (d) repeating the click on a junction-containing folder does not recurse into the junction target.

2. **R97.3-B — Reset My Library is available whenever no worker is actively running.**
   - **Current:** `_update_reset_button_state` (my_library_tab.py:1317) disables `_btn_reset` when EITHER `self._worker.isRunning()` is True OR `start_recovery_probe()` returns non-empty. After a crash, the second condition leaves Reset disabled exactly when it's needed.
   - **Target:** The guard collapses to a single condition: `worker_running = self._worker is not None and self._worker.isRunning()`. If True → disabled with the "Stop the active scan first" tooltip. If False → enabled with the "Reset deletes LOCAL/LAB index data only…" reassuring tooltip. The `start_recovery_probe()` probe is removed from this code path — `LocalIndexer.reset_my_library()`'s own 7-step protocol (path-safety pre-check + handle-close + retry-rename + fail-loud + deferred-GC) is the load-bearing safety; the UI guard does not duplicate it.
   - **Acceptance:** With orphan `scan_runs.status='running'` rows in the DB and no active worker, the Reset button is enabled and clicking it opens the typed-confirmation dialog. The Phase 97.2 test `test_reset_my_library_full_cycle` and `test_reset_my_library_lab_rename_failure_rolls_back_local` still pass (no regression in the 7-step protocol). A new test pins the new guard semantics: with orphan rows + no worker → enabled; with active worker → disabled.

3. **R97.3-C — MuPDF stderr warnings are silenced at indexer init.**
   - **Current:** PyMuPDF emits `MuPDF error: syntax error: unknown keyword: 'TF'` (and similar parse warnings) to stderr for every malformed PDF text-formatting operator. The user's smoke-test folder generated 624 lines of such noise, which clutters logs and looks alarming to users running the desktop EXE.
   - **Target:** `shared/local_indexer.py` calls `fitz.TOOLS.mupdf_display_warnings(False)` once at module import (or at `LocalIndexer.__init__`, whichever Codex's recommendation favors). Process-wide stderr is NOT redirected (that would hide unrelated failures); only PyMuPDF's own warning channel is suppressed. A subsequent commit may add an optional debug-level summary if warnings are later needed for diagnostics, but this is NOT in scope for Phase 97.3.
   - **Acceptance:** A test that imports `shared/local_indexer` and then runs `extract_pdf_pages` on a fixture PDF with a known malformed `Tf` operator produces zero lines on stderr matching `MuPDF error:`. Pre-existing PyMuPDF tests still pass.

4. **R97.3-D — Recovery-Skip suppresses the same-launch auto-rescan.**
   - **Current:** Constructor order at my_library_tab.py:714–733: recovery probe → `_show_recovery_modal` (Resume/Restart/Skip) → `_auto_rescan_on_startup` (D-25 silent background rescan). If user clicks Skip, the orphan row is canceled but `_auto_rescan_on_startup` immediately spawns a worker on the same registered folders.
   - **Target:** `_show_recovery_modal` sets a one-shot flag (`self._skip_startup_rescan_once = True`) when Skip is clicked. `_auto_rescan_on_startup` checks this flag at entry and, if set, returns early after surfacing a non-blocking status-bar message ("Recovery skipped. Use Refresh to rescan My Library." / Hebrew equivalent). The flag is consumed after one read so a subsequent manual Refresh works normally. D-25's default behavior (silent rescan when no recovery modal was shown) is unchanged. Resume and Restart paths are NOT affected (those intentionally trigger a fresh scan).
   - **Acceptance:** Simulating a launch with orphan `scan_runs` rows + user clicks Skip → `_auto_rescan_on_startup` does NOT call `_start_worker`. A status-bar message appears. Clicking Refresh manually after the Skip works normally and triggers a worker as expected. Existing D-25 silent rescan continues to fire when there are no orphan rows / no modal shown.

5. **R97.3-E — Scan progress shows "Discovering files…" during enumeration.**
   - **Current:** `LocalIndexerWorker` emits `progress_updated` signals during the indexing phase but not during the enumeration phase (`scan_all` builds the full `disk_files` dict before yielding the first signal). UI shows "0%" for the entire enumeration window. On mega folders this can be tens of seconds with no visual feedback.
   - **Target:** Worker emits a `status_updated(text)` signal (or reuses an existing one) when entering the enumeration phase with bilingual text "Discovering files…" / "מאתר קבצים…". The progress bar may stay at 0% (or switch to indeterminate / busy mode) during enumeration; once enumeration completes, the bar becomes determinate again and shows real percent. UI status label reflects the active phase.
   - **Acceptance:** When `_start_worker` runs on a folder large enough that enumeration takes ≥ 500ms (test fixture forces a delay via a monkeypatched `os.walk`), the UI status label is observed in the "Discovering files…" state before transitioning to indexing progress. A test asserts the signal-emission order: enumeration-start → enumeration-end → first indexing progress.

6. **R97.3-N — UI tree shows the indexer's full supported-extensions set.**
   - **Current:** `desktop/my_library_tab.py:227` declares `SUPPORTED = {'.pdf', '.docx', '.txt'}` (UI tree). `shared/local_indexer.py:81` declares `_SUPPORTED_EXTENSIONS = {".docx", ".pdf", ".txt", ".html", ".xlsx", ".csv"}` (indexer). `.html`, `.xlsx`, `.csv` files get indexed but are invisible in the opt-out tree.
   - **Target:** UI tree imports `_SUPPORTED_EXTENSIONS` from `shared/local_indexer` (single source of truth) so the two sets cannot drift. A quick AST/grep check confirms no opt-out cascade logic (filter chips, status overlay, Pages-column rendering) assumes only the old 3-extension set — if such an assumption exists, it is either lifted or a documented test gap is logged.
   - **Acceptance:** A folder containing one of each supported extension (`.pdf`, `.docx`, `.txt`, `.html`, `.xlsx`, `.csv`) is selected — all 6 files appear as leaves in the opt-out tree. A static AST test pins that `_populate_node` imports the extension set from `shared.local_indexer` rather than declaring its own literal.

## Boundaries

**In scope:**
- All six requirements above (R97.3-A through R97.3-N).
- Workerized tree population using `os.scandir(follow_symlinks=False)` (closes Bug A's symlink-recursion side-defect at the same time).
- A `_skip_startup_rescan_once` one-shot flag in `MyLibraryTab`.
- A new `status_updated(text)` signal (or reuse of existing) on `LocalIndexerWorker`.
- Single source of truth for supported extensions (import from `shared/local_indexer`).
- `fitz.TOOLS.mupdf_display_warnings(False)` at indexer init.
- Tests for each requirement (RED-before-fix where the failure is reproducible without the fix).
- Documentation closeout: CHANGELOG `[Unreleased]` entry, CLAUDE.md "Recently Changed" one-liner, OPEN_ISSUES.md bump, no version bump.

**Out of scope:**
- N1 — `prescan_count_all()` synchronous on UI thread — separate code path from Bug A, not in user's repro. Worth fixing in v7.15+ but not here. Phase 97.3 keeps `prescan_count_all` unchanged.
- N2 — `_show_recovery_modal` multi-orphan ordering — edge case (multiple stale running rows are rare in practice). Adding `ORDER BY started_at DESC` to `start_recovery_probe` and looping over all rows is left for v7.15+.
- Resume button real behavior — currently `_show_recovery_modal` Resume just marks the run completed; full resume is deferred to v7.15+ per the Phase 97 R-01 comment. We do NOT relabel the button in 97.3 (UX change deferred until real resume ships).
- New `gsd-fast`-style hotfix or version bump — Phase 97.3 rides the v7.14 internal-hotfix chain (Phase 97.1 → 97.2 → 97.3) with no public release.
- Refactor of `_canonical_filepath` itself — moving it off-thread (R97.3-A) is in scope; rewriting it for speed is not.
- Aggregate enumeration progress (file-count progress bar during discovery) — only a text status is required for R97.3-E. Indeterminate / busy progress bar may be used but is not mandated.
- OCR, side-by-side PDF rendering — these were already deferred at v7.14 (D-F2/D-F3) and remain out.

**Deferred to v7.15+** (named here to prevent rediscovery): N1 prescan threading, N2 multi-orphan recovery, real Resume behavior, aggregate enumeration progress bar.

## Constraints

- **Phase 97.2 invariants must hold.** `LocalIndexerError`, `_ensure_writer`, R97.2-H short-circuit, the 7-step `reset_my_library` must not regress. New tests for R97.3-B may not weaken the existing `test_reset_my_library_full_cycle` / `test_reset_my_library_lab_rename_failure_rolls_back_local` coverage.
- **Phase 96 D-F1 wiring must keep working.** `_unified_tree`, `_displayed_paths`, `_leaf_by_path`, opt-out `ItemIsUserCheckable`/`ItemIsAutoTristate` flags, opt-out persistence via `flush_pending()` on `closeEvent`, prior_status overlay (Phase 96 fix-2) — all must continue to populate correctly after the tree refactor.
- **D-25 silent auto-rescan stays the default.** Only the Skip path suppresses it (R97.3-D); Resume and Restart keep triggering scans; the "no orphan rows" path keeps firing the silent rescan as before.
- **`reset_my_library()` internal safety is the load-bearing layer for R97.3-B.** The simplified UI guard does not duplicate path-safety / handle-close / retry-rename — `reset_my_library()` already does them.
- **No version bump.** Phase 97.3 is internal hotfix on the v7.14 chain. CHANGELOG goes in `[Unreleased]`; `version.py`/`version_info.txt`/`.iss`/`README.md`/`tests/test_release_artifacts.py` are NOT touched.
- **Platform:** Windows 11, Python 3.11, PyQt6, PyMuPDF, tantivy-py 0.25.1.
- **No new external dependencies.** All fixes use existing libraries (`QThread`, `os.scandir`, `fitz.TOOLS`).
- **Branch:** stays on `phase-98-nli-resilience` (Phase 97.2 already lives here; branch rename is a separate concern).

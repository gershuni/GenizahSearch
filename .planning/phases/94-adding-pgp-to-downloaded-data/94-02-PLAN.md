Wave 2 of Phase 94: plumb the 3 enrichment signals (`transcription_sys_ids`, `printed_ids`, `result_domains`) through the web session payload + extend the JSON envelope's per-item shape with the 3 additive flags (`has_pgp`, `is_printed`, `domains`).

This plan is web-only by construction — desktop reads the analogous fields directly at the call site (`self._pgp_transcription_sys_ids`, `self._printed_sys_ids`, `self._result_domain_map`) and has no JSON export.

Three distinct deliverables:

1. **Extend `web/export_state.py`** — `set_search_export(...)` gains 3 optional kwargs; new sibling helper `update_search_export_enrichment(...)` patches the 3 fields without touching `results`. Both honor Phase 88 D-11 (isinstance guard) + D-12 (copy-on-update) invariants. Sets cast to sorted lists internally for JSON-safety.

2. **Wire `web/pages/search.py`** — 3 existing `set_search_export` call sites pass the new kwargs (initial empty); 2 new `update_search_export_enrichment` call sites (one after Stage-1 visible-page enrichment, one after Stage-2 background-chunk enrichment) propagate the live enrichment data into the export payload.

4. **Wire `web/api.py`** — `export_excel` reads + passes new payload fields to the export service (kwarg activation comes in Wave 3); `export_json` reads + passes to `serialize_search_payload`.

Purpose: by the end of this plan, the JSON download already returns `has_pgp` / `is_printed` / `domains` per item; the xlsx restructure (Wave 3) and desktop parity (Wave 4) can both rely on the session payload carrying the enrichment data. CRITICAL: when this function calls `_serialize_item(...)` it does NOT pass `transcription_sys_ids` or `printed_sys_ids`. The defaults (None -> empty set) mean `has_pgp` and `is_printed` are both `False` for every parallels item. BUT: the parallels envelope contract per CONTEXT D-10 is that these keys should NOT appear at all in the parallels item shape. The regression test will assert the keys' absence — see Task 5 below for the right place to enforce this (either via `_serialize_item` accepting an explicit "omit these keys" flag, OR via `_to_parallels_envelope_item` post-processing to strip the keys, OR via a separate parallels item builder that does not include them).

**Design decision for Task 5:** the cleanest approach is to have `_serialize_item` ALWAYS emit `has_pgp` and `is_printed` (with default False when sets not provided), and have `_to_parallels_envelope_item` strip them before returning (since parallels-specific items have their own shape). This keeps the search-item shape uniform (always boolean, never missing per D-06) and isolates the parallels deviation in one place. Document the strip in the parallels function with a D-10 comment.

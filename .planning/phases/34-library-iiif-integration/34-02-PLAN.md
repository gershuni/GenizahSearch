  <name>Task 1: Create JTS/Princeton DPUL import script</name>
  <files>scripts/import_jts_dpul.py</files>
  <action>
Create scripts/import_jts_dpul.py following the pattern of import_nli_crossref.py:

1. **Table schema** -- Create `jts_dpul` table in nli_crossref.db:
   ```sql
   CREATE TABLE jts_dpul (
       shelfmark TEXT PRIMARY KEY,
       ark_suffix TEXT NOT NULL,
       manifest_url TEXT,
       dpul_url TEXT NOT NULL,
       thumbnail_url TEXT
   )
   ```
   With index: `CREATE INDEX idx_jd_ark ON jts_dpul(ark_suffix)`

2. **Gather unique shelfmarks** -- Query crossref for distinct JTS shelfmarks:
   ```sql
   SELECT DISTINCT Shelfmark FROM nli_images WHERE LibraryAbbrev = 'JTS' AND Shelfmark != ''
   ```
   Expected ~43K unique shelfmarks. Remove leaf suffix (e.g., "ENA 2573.1" -> "ENA 2573") to avoid duplicate searches? No -- the DPUL catalog distinguishes leaf-level items. Keep full shelfmarks.

   IMPORTANT: Many shelfmarks map to the same manuscript. Deduplicate by stripping the last `.N` leaf suffix to get the base shelfmark. Use the base shelfmark for DPUL search, then map all leaf variants to the same ARK. This reduces ~43K to ~20K unique searches.

   Actually, looking at the research more carefully: DPUL search "Works with exact shelfmarks including leaf number (e.g., 'ENA 2573.1')". So leaf-level shelfmarks DO return results. But we should check if the same item is returned for both "ENA 2573.1" and "ENA 2573.2" (likely yes, same ARK). To be efficient:
   - Group shelfmarks by base (strip trailing `.N`)
   - Search DPUL once per base shelfmark
   - Store result for base shelfmark, map all leaf variants

3. **Two-step DPUL lookup** -- For each unique base shelfmark:
   Step A: Search DPUL catalog:
   ```
   GET https://dpul.princeton.edu/cairo_geniza/catalog.json?search_field=all_fields&q={shelfmark}
   ```
   Parse response: `response_json["data"]` is an array. Take the first item.
   Extract `id` field which contains the ARK suffix (last path segment of the item URL).
   Construct dpul_url: `https://dpul.princeton.edu/cairo_geniza/catalog/{ark_suffix}`

   Step B: Fetch item details:
   ```
   GET https://dpul.princeton.edu/cairo_geniza/catalog/{ark_suffix}.json
   ```
   Extract:
   - `content_metadata_iiif_manifest_field_ssi` -> manifest_url (Figgy manifest)
   - `thumbnail_ssim[0]` -> thumbnail_url

4. **Rate limiting** -- Add 0.3 second delay between API calls (conservative for ~40K+ calls).
   Use requests with timeout=15 and retry on 5xx (max 3 retries with exponential backoff).
   Total estimated time: ~20K searches x 2 calls x 0.3s = ~3.5 hours. Consider parallelism:
   - Use ThreadPoolExecutor with 3 workers and 0.1s delay each to reduce to ~1.2 hours
   - Or accept the long runtime and use checkpointing

5. **Checkpointing** -- Save progress every 100 shelfmarks to a JSON checkpoint file:
   `nli_data/jts_dpul_checkpoint.json` with format: `{"completed": ["shelfmark1", ...], "results": {...}}`
   On restart, skip already-completed shelfmarks. Delete checkpoint after successful full import.

6. **Idempotent** -- Drop and recreate table on each run (but respect checkpoint).
   Update meta table: add `source_jts` key with value "DPUL catalog API".

7. **Match stats** -- After import, report:
   - Total unique base shelfmarks searched
   - Found in DPUL (with ARK)
   - Not found (no results)
   - With manifest URL

8. **CLI interface** -- Use argparse:
   - `--db-path` (default: nli_data/nli_crossref.db)
   - `--delay` (default: 0.3)
   - `--workers` (default: 1, max 5)
   - `--limit` (optional: process only first N shelfmarks for testing)
   - `--resume` (resume from checkpoint)
   - `--dry-run` (search DPUL but don't write to DB)

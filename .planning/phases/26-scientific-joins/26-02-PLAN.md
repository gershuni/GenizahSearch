Fix FJMS join deduplication for manuscripts belonging to multiple join groups.

Purpose: When a manuscript belongs to multiple FJMS join groups, get_join_group() currently returns raw duplicate rows for partner AlmaIds that appear in more than one group. The web app's first-encountered-wins dedup drops richer metadata (join_type), and the desktop app has no intra-FJMS dedup at all, showing duplicates. Fixing at the service level (get_join_group) eliminates the bug for both consumers at once.

Output: Deduplicated get_join_group(), updated tests proving the fix.
</objective>

In `shared/fjms_service.py`, rewrite the SQL in `get_join_group()` to return each unique partner AlmaId exactly once, preferring rows with non-NULL JoinType.

Replace the current query (lines 213-218):
```sql
SELECT AlmaId, JoinGroupId, ScholarName, Comment, JoinType
FROM joins
WHERE JoinGroupId IN (SELECT JoinGroupId FROM joins WHERE AlmaId = ?)
AND AlmaId != ?
```

With a query that groups by AlmaId and picks the best row. Use a subquery or window function approach. The simplest correct approach:

```sql
SELECT AlmaId,
       MAX(JoinGroupId) as JoinGroupId,
       MAX(ScholarName) as ScholarName,
       MAX(Comment) as Comment,
       MAX(CASE WHEN JoinType IS NOT NULL AND JoinType != '' THEN JoinType END) as JoinType
FROM joins
WHERE JoinGroupId IN (SELECT JoinGroupId FROM joins WHERE AlmaId = ?)
  AND AlmaId != ?
GROUP BY AlmaId
```

This ensures:
- Each AlmaId appears exactly once
- JoinType prefers the non-NULL/non-empty value (MAX of the CASE returns the actual value, or NULL if all are NULL/empty)
- ScholarName, Comment, JoinGroupId take a reasonable value (MAX picks a non-NULL when available)

Update the method docstring to document the deduplication behavior: "If the same partner appears in multiple groups, it is returned once with the richest metadata (non-NULL join_type preferred)."

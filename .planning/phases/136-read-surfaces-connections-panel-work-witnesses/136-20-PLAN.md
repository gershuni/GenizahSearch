<objective>
Close the deployment-step hole in VIS-01: make the loader itself refuse to serve a private asset to a
public route, and extend the startup readiness contract so a partial or pre-rebuild sidecar cannot pass
`discovery_available()`.

Purpose: the projection logic is correct and the exclusion is structural inside the artifact — but the
runtime resolves ONE manifest-named database and deliberately ignores siblings, with no notion of
audience at all. With the flag on, public routes would therefore read the private asset, defeating
VIS-01 at the very last step, after every earlier control did its job. Separately, `_REQUIRED_TABLES`
still lists only the v1 tables and the schema marker is unchanged, so an old or half-deployed sidecar
passes readiness, exposes the nav entry, and then fails the first query that touches
`discovery_identification` or `manuscript_display`.
Output: an audience boundary and a readiness contract that both fail closed.
</objective>

  <behavior>
    - An asset whose `meta.audience` is `public` loads and readiness proceeds as before.
    - An asset whose `meta.audience` is `private` is REFUSED by the public loader: readiness stays False and `discovery_available()` returns False.
    - An asset with a MISSING or unrecognised `audience` value is refused — the default is closed, never open.
    - The refusal is logged with the reason but WITHOUT echoing any row content.
    - Pointing `manifest.json` at a private-audience database leaves every public route unable to resolve it; a test asserts this end to end rather than only at the predicate.
  </behavior>
  <action>
    Write the tests first, one per behavior, over fixture databases built at each shape.

    Add an audience check to the readiness path: read `meta.audience`, compare against a module-level
    closed enum, and require the value the PUBLIC loader is allowed to serve. Anything else — private,
    missing, empty, unrecognised — fails closed exactly the way an incompatible schema version already
    does, using the same reject-incompatible idiom rather than a new one.

    Belt and braces, deliberately. The deploy (plan 136-13) will point production's `manifest.json` at
    the PUBLIC projection and keep the private database off the web box entirely, so this check should
    never fire in a correct deployment. It exists because "never fires in a correct deployment" is
    exactly the property that stops being true under a rushed rollback or a mistyped path, and because
    VIS-01's exclusion is supposed to be structural rather than procedural. A control that only works
    when everyone is careful is a procedure, not a control.

    Do NOT relax `_resolve_versioned_db`'s sibling-ignoring behaviour — that is the rollback-safety
    property, and it is what makes the manifest the single selection point. This task adds a second,
    independent gate on the CONTENT of whatever the manifest selected.

    Expose the resolved audience through the module's existing state accessor so a later diagnostic or
    admin surface can report which artifact is live without opening the database again.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| deployed artifact → public route | The last point at which a private row could reach an unauthenticated reader |
| manifest selection → loaded content | The manifest says which file; nothing today says what that file is allowed to contain |
| partial deployment → availability predicate | A half-copied or rolled-back asset deciding whether a nav entry appears |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-136-20-01 | Information disclosure | A public route serving the private asset because the manifest named it | mitigate | Audience enum enforced on loaded content, independent of which file the manifest selected; end-to-end refusal test across every public read path |
| T-136-20-02 | Elevation of privilege | A missing or unrecognised audience value treated as public | mitigate | Fail-closed default with a dedicated test; same reject-incompatible idiom as the schema check |
| T-136-20-03 | Denial of service | A nav entry exposed by a sidecar that then errors on the first query | mitigate | Both new tables and their release-contract counts added to startup validation; partial-asset tests |
| T-136-20-04 | Denial of service | A rollback to the pre-rebuild asset half-enabling the surfaces | mitigate | Explicit rollback test asserting the pre-rebuild shape leaves availability False |

| T-136-20-06 | Tampering | Sibling-file resolution loosened while adding the audience gate | mitigate | Acceptance criterion asserts `_resolve_versioned_db`'s resolution logic is unchanged |

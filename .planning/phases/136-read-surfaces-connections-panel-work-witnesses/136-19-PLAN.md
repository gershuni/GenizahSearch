output, JSON payloads, copy and export paths, and error paths — prove it can fail on each, and publish
the flag-on readiness attestation.

Output: a sweep proven able to fail, and one attestation the release gate can read.

  </read_first>
  <action>
    Build ONE sweep that drives the existing DATA-05 gate over captured output from both surfaces,
    rather than reimplementing the pattern set. Cover four path classes, because a sweep that covers
    only the first is the usual shape of this gate and the usual reason it misses:

    1. **Rendered output** — the panel and the findings page, in both languages, across every service
       state and every row unit. Capture to a path OUTSIDE the repo working tree, or make sure the
       capture path is ignored by a gitignore GLOB: a stray capture that is untracked-but-not-ignored
       trips `--scan-repo` itself and produces a confusing failure.
    2. **JSON payloads** — every payload either surface emits or consumes, including the enveloped
       service responses.
    3. **Copy and export paths** — any clipboard or export output a reader can produce from either
       surface. If neither surface has one yet, assert that explicitly and record it, so the absence is
       a documented finding rather than an untested assumption.
    4. **Error paths** — force each failure mode (sidecar absent, timeout, overload, malformed row,
       unknown provenance code, missing work title) and scan the resulting message, log line and
       rendered error state.

    Then the positive controls, one per path class: seed a restricted marker into a rendered row, into
    a JSON payload, into a copy/export output, and into an exception message, and assert the sweep
    fails in each case. A sweep observed failing on rendered output but never on an error path has not
    been shown to cover error paths.

    Generate the seeded marker at test time from the pattern file. Never hardcode a restricted name into
    a committed test — that would be the leak the test exists to prevent.

    **An unavailable pattern file BLOCKS flag-on readiness — it is not a recorded skip.** Earlier
    drafts of this plan allowed the sweep to complete with a noted skip while still claiming readiness;
    that is precisely how a masking gate becomes decorative. If `MASKING_SCAN_PATTERNS_FILE` is unset or
    unreadable, the sweep FAILS, the attestation records the masking item as NOT met, and flag-on
    readiness is not claimed. The fail-closed exit is the feature; treating it as a skip discards it.

    Scan every database with BOTH modes — `--strict --scan-repo --scan-asset <db> --scan-sqlite <db>` —
    for the same reason the projection does: a SQLite file needs a cell-by-cell pass to cover schema,
    column names and overflow content.
  </action>

  </verify>

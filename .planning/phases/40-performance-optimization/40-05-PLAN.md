<objective>
Unify variant generation across Tantivy and regex search phases so variants are computed once at the maximum limit and sliced for smaller requests.

Purpose: Currently, `_build_tantivy_query` calls `get_variants(term, mode, limit=200)` and then `_build_regex_pattern` calls `get_variants(term, regex_mode, limit=8000)` for the same term. When the mode is the same, this generates variants twice — once with limit=200 and once with limit=8000. The cache keys differ because the limit is part of the key. By computing at the larger limit first and slicing for the smaller, we avoid duplicate generation.

Output: Modified VariantManager that recognizes when a smaller-limit request can be served from a larger-limit cached result.
</objective>

The current cache key is `(term, mode, limit, pairs_count)`. When the Tantivy phase requests 200 variants and then the regex phase requests 8000 for the same term+mode, both compute independently.

**Modify the cache lookup in `get_variants`** (around lines 2260-2266) to check for a cached superset:

After the existing exact cache check fails:
```python
# Check cache (include pairs_count for proper invalidation)
cache_key = (term, mode, limit, pairs_count)
if cache_key in self._cache:
    return self._cache[cache_key]

# Check if a larger-limit result exists that we can slice from
for cached_key, cached_value in self._cache.items():
    if cached_key[0] == term and cached_key[1] == mode and cached_key[3] == pairs_count:
        if cached_key[2] >= limit:
            # Larger result exists; slice to our limit
            sliced = cached_value[:limit]
            self._cache[cache_key] = sliced
            return sliced
```

This way:
- First call with `limit=200` computes and caches at key `(term, mode, 200, pairs_count)`.
- Second call with `limit=8000` computes and caches at key `(term, mode, 8000, pairs_count)`.
- If the ORDER is reversed (8000 first, then 200), the 200-limit call finds the 8000-limit result and slices.

**However**, in practice the Tantivy phase (limit=200) runs first, then regex (limit=8000). So the superset optimization kicks in when the SAME search term appears in multiple searches. For the first search, both still compute.

**Better approach — also handle the same-search case**: Modify `_build_tantivy_query` to pre-compute variants at the maximum limit that will be needed. Add a helper method:

```python
def _precompute_variants_for_search(self, terms, mode, regex_mode):
    """Pre-compute variants at the larger limit for each term.

    This ensures the regex phase can slice from the cached result
    instead of recomputing.
    """
    max_limit = Config.REGEX_VARIANTS_LIMIT  # 8000
    for term in terms:
        if term.upper() in ['AND', 'OR', 'NOT', '(', ')']:
            continue
        # Pre-compute at the larger limit for both modes
        # The Tantivy phase will then slice from this cached result
        self.var_mgr.get_variants(term, mode, limit=max_limit)
        if regex_mode != mode:
            self.var_mgr.get_variants(term, regex_mode, limit=max_limit)
```

Call this method once at the start of the search flow — in `execute_search` or `_build_tantivy_query`, before the per-term variant loop. Then the Tantivy phase's `get_variants(term, mode, limit=200)` hits the superset cache and returns a slice, and the regex phase's `get_variants(term, regex_mode, limit=8000)` hits an exact match.

**Important**: The `regex_mode` differs from `mode` when `mode == 'fuzzy'` (regex_mode becomes `'variants_maximum'`). In that case, pre-compute for both modes. When mode is `'variants'`, `'variants_extended'`, or `'variants_maximum'`, the regex_mode is the same, so only one pre-computation needed.

**Ensure the superset lookup is efficient**: The cache iteration is O(cache_size) but cache_size is typically small (≤100 entries per search). This is negligible compared to variant generation cost.

Do NOT change the cache eviction logic or the `clear_cache` method. Do NOT change any method signatures. The optimization should be invisible to callers.

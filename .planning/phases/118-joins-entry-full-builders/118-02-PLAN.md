<objective>
Deliver the multitenant-safe, four-source known-joins data path (ANC-04/ANC-05) and a
reusable known-joins group renderer. Extend `fetch_connected_fragments` with a
`confirmed_only` flag that (1) filters the user joins to `status='confirmed'` via the
existing `get_fragment_joins` param — the PRIMARY ANC-05 mechanism — and (2) uses an
ISOLATED cache key so the confirmed-only result can never poison the full-joins cache
used by the browse joins dialog. On the same Lab path, merge published community
puzzle joins into the connected group as `sources=['community']` so ANC-04's
PGP+FJMS+user+community group is genuinely complete. Build
`web/components/known_joins_group.py` as a pure render component (source badges +
re-anchor + open-in-browse) that the Joins Lab anchor pane (Plan 04) drops in.

Purpose: ANC-04 (known joins as a connected, source-attributed group spanning all four
sources) and ANC-05 (Codex BLOCKER 3 / threat T-118-01 — no cross-user join leak). The
fix follows D-17: `status='confirmed'` (canonical column, already-supported filter) on
the process-global path is structurally leak-proof, with the accepted trade-off that a
logged-in scholar's own not-yet-confirmed (proposed) joins do not appear in the Lab
group. The `fragment_joins.status` column exists (`supabase_setup.sql:162`) and
`get_fragment_joins(..., status='confirmed')` is a fully-supported existing call
(`web/supabase_client.py:1593-1594`), so this is the clean primary fix — not a
workaround.
Output: extended `joins_panel.py` (confirmed filter + isolated cache key + community
merge), confirmation that `supabase_client.py` already supports the filter, new
`known_joins_group.py`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| logged-in scholar (User A) → process-global `_joins_cache` → other session (User B) | The cache is module-level in the Python process; without isolation a cached payload from one user's request serves another's |
| browser/client → public `fragment_joins` RLS path | RLS policy `USING (true)` makes every row publicly readable to all roles; the app-layer `status='confirmed'` filter is what enforces confirmed-only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-118-01 | Information Disclosure | `fetch_connected_fragments` process-global `_joins_cache` + `get_fragment_joins` public RLS | mitigate | The Lab path calls `get_fragment_joins(fragment_sys_id=…, status='confirmed')` — the app-layer confirmed-only QUERY FILTER (the existing supported param) excludes any user's not-yet-confirmed `proposed` joins from the process-global group, so a creator-only/unconfirmed join structurally cannot reach another user's Lab session (D-17). The ISOLATED cache key `doc:{id}:pgp:{pgpid}:confirmed` additionally prevents the Lab fetch and the browse dialog's full-joins fetch from sharing a cached payload. Proven by `tests/test_joins_anc05_rls.py::test_confirmed_path_passes_status_confirmed_to_get_fragment_joins` + `::test_no_cross_user_poisoning` |

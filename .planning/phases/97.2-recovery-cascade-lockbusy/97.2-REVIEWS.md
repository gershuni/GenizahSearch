# Cross-AI Plan Review — Phase 97.2 Recovery Cascade

## Codex Review

**Summary**

**97.2-01:** Strong root-cause focus and mostly correct dependency ordering. The plan targets the right bugs first: missing schema marker detection, redundant writer ownership, discard consistency, and fail-loud writer guards. Main weakness: several RED tests are not deterministic or do not actually prove the Windows/Tantivy lock bugs they claim to cover.

**97.2-02:** Good product shape for recovery: bounded reset scope, active-scan guard, typed confirmation, bilingual UX, and a real `LocalIndexer.reset_my_library()` helper. The risky part is the destructive filesystem workflow: it needs stricter path validation, better failure handling, and should avoid long synchronous `rmtree` on the UI thread.

**97.2-03:** Good closeout intent. It updates the right docs and explicitly avoids release/version churn. Main issue is verbosity: the proposed `CLAUDE.md` and changelog entries are too implementation-heavy for long-term maintainability.

**Overall:** The phase goals are well understood and mostly covered. I would approve the direction, but I would tighten the tests and reset safety before execution.

**Strengths**

- Correctly identifies Bug 6, missing `.schema_version`, as the actual root cause.
- Good sequencing: schema-marker/rebuild ownership before discard fixes, discard consistency before reset UX.
- `LocalIndexerError` + `_ensure_writer()` moves failure from silent logs to actionable UI errors.
- `discard_run` short-circuit before SQLite deletion is the right integrity model.
- Reset UX has appropriate friction via typed confirmation.
- Reset scope is intentionally LOCAL-only and preserves reference data/source files.
- Plans include regression checks for Phase 97 and Phase 87 invariants.

**Concerns**

- **HIGH:** `test_rebuild_does_not_leak_writer_lock` does not prove the stated invariant. It only asserts `indexer._writer is not None`. A second independent writer should usually fail while `_writer` is live, so the plan's "subsequent writer acquisition succeeds" claim is conceptually off.
- **HIGH:** The discard Phase 95 fallback test is ambiguous. Monkeypatching `delete_documents("scan_run_id")` to raise does not exercise the planned schema-introspection branch unless `schema.field_names()` is also patched to omit `scan_run_id`.
- **HIGH:** The per-uid fallback draft catches per-uid delete failures and continues, then can still set `_tantivy_delete_ok = True`. That reintroduces the orphaned-docs risk R97.2-H is meant to prevent.
- **HIGH:** `_ensure_writer()` does not actually "lazy reopen" if `self._index is None`; it just calls `self._index.writer(...)`. Either reopen the index after marker validation or change the requirement to fail-loud only.
- **HIGH:** `reset_my_library()` needs hard path-safety checks before rename/rmtree. Instance attributes should be resolved and verified as the expected LOCAL directories, not root, not equal to each other, and preferably under the configured index base.
- **HIGH:** Plan 02 continues if LAB rename fails. That can leave main reset but lab stale or locked. A reset should fail/rollback unless the LAB dir is absent.
- **MEDIUM:** Direct `shutil.rmtree(..., ignore_errors=True)` removes most of the quarantine recovery value and can freeze the PyQt UI for large libraries.
- **MEDIUM:** The active-scan guard is specified as "button disabled with tooltip," but the task only checks on click and shows a message.
- **MEDIUM:** Plan 02 modifies `genizah_core.py` translations but does not list it in `files_modified`.
- **MEDIUM:** Several verify commands use `pytest tests/test_phase_97_2_ -x`, which is not a valid path. Use explicit files, `pytest tests/test_phase_97_2_*.py`, or `pytest tests -k phase_97_2`.
- **MEDIUM:** Monkeypatching methods on `tantivy.Index` / Rust extension objects may fail if attributes are readonly. Prefer wrapper seams or real fixture indexes.
- **LOW:** `gc.collect()` is acceptable in these recovery paths, but avoid spreading it into normal hot paths.
- **LOW:** Plan 03's proposed `CLAUDE.md` entry is too long for a "Recently Changed" note.

**Suggestions**

- Replace Test 2 with a deterministic check: assert `rebuild_main_index_atomic` returns without `LockBusy`, then close `_writer`, force GC, and reacquire; add a static/AST guard that `del fresh_writer` and `del fresh_index` are gone.
- Build a real pre-Phase-97 schema fixture for discard fallback, or patch schema field-name introspection directly.
- In per-uid fallback, any delete failure should raise and leave `_tantivy_delete_ok = False`; do not log-and-continue.
- Update `_ensure_writer()` to handle `self._index is None` by reopening `tantivy.Index(build_local_schema(), path=self._index_dir)` after marker validation.
- Add reset path guards: resolved absolute paths, expected basename, same volume for atomic rename, not root, not missing unexpectedly.
- Treat LAB rename failure as fatal unless the LAB dir does not exist.
- Prefer rename-aside + deferred cleanup via `pending_dir_cleanup` or a background worker. Keep the UI responsive after the atomic rename/reinit path.
- Add tests that reset does not touch reference DBs, source files, or the main `Genizah_Index`.
- Add a UI-state helper for reset button enablement/tooltip and call it after worker start/finish and recovery-probe changes.
- Keep docs concise: changelog can hold the narrative; `CLAUDE.md` should summarize and link to the phase summary.

**Risk Assessment**

Overall risk: **MEDIUM-HIGH**.

The technical direction is sound and targets the right failure chain, but the current plans have two high-risk areas: nondeterministic Tantivy/Windows tests that may pass without proving the fix, and a destructive reset helper that needs stronger safety and failure semantics. With the test fixes and reset hardening above, risk drops to **MEDIUM**.

## Gemini Review

# Implementation Plan Review: Phase 97.2 Recovery Cascade

This review evaluates the three-plan sequence for **Phase 97.2**, designed to resolve the LOCAL index recovery cascade and implement the "Reset My Library" feature.

---

## 1. Summary Assessment

### Plan 97.2-01 (Wave 1 — Logic Fixes)
This plan is a highly surgical and technically rigorous approach to fixing the 8 interacting bugs identified in the recovery cascade. It correctly prioritizes the root cause (Bug 6 — schema marker absence) over the symptoms (`LockBusy`). The TDD approach, using 4 distinct RED-test files as gates, ensures that each fix is empirically verified. The strategy for releasing Windows file handles (explicit nulling + `gc.collect()`) is the correct defensive maneuver for Tantivy's Rust-backed memory mapping.

### Plan 97.2-02 (Wave 2 — Reset UX)
This plan delivers the user-facing recovery mechanism. The design of `reset_my_library` is robust, using a 6-step atomic teardown protocol. By utilizing a "rename-aside" (quarantine) strategy before `shutil.rmtree`, it minimizes the window of inconsistency where the app might be stuck without any index directory. The UI implementation features high-quality safety guards, including an active-scan probe and a two-step typed confirmation token, which is appropriate for a destructive operation.

### Plan 97.2-03 (Wave 2 — Documentation)
A standard closeout plan that effectively bundles the recent Phase 97.1 hotfix with the 97.2 work. It ensures the `CHANGELOG.md` and `OPEN_ISSUES.md` stay current, which is critical for maintaining project velocity and assisting future AI sessions. The inclusion of a retroactive hotfix note in the Phase 97 verification record is a helpful touch for long-term auditability.

### Overall Assessment
The phase design is **excellent**. It moves the LOCAL indexer from a "hope for the best" recovery model to a "fail-loud and recover-safely" model. By addressing both the underlying handle-management defects and providing a manual "nuclear option" (Reset), the system becomes significantly more resilient for power users at the 50GB scale.

---

## 2. Strengths

*   **Root Cause Focus:** Correctly identifies that the missing `.schema_version` marker on Phase 95 upgrades was the primary trigger for the entire cascade.
*   **Windows Reliability:** Uses the "null + `gc.collect()`" pattern to bypass the "weak `del`" behavior on Windows, which is the most reliable way to ensure Tantivy releases its `.tantivy-writer.lock`.
*   **Atomic Reset:** The use of `_retry_windows_rename` to move old indices into a `.reset-quarantine-<ts>` directory before deletion is a superior strategy; it makes the "data-gone" state nearly instantaneous, even if the subsequent `shutil.rmtree` takes several seconds.
*   **Fail-Loud Semantics:** Replacing silent retry loops with the `LocalIndexerError` exception ensures that UI users receive actionable feedback (the Reset CTA) rather than experiencing mysterious hangs or "ghost" results.
*   **TDD Rigor:** Each fix is paired with a specific RED test, following the project's established pattern for high-stakes core logic changes.

---

## 3. Concerns

*   **`shutil.rmtree` Latency (Severity: LOW):** On a 50GB index with 50K files, `shutil.rmtree` on a magnetic or slow SSD can take significant time. While the plan uses a non-modal `QProgressDialog`, the actual deletion still happens on the UI thread via `processEvents`.
    *   *Mitigation:* The rename-aside happens first, so the system is "clean" almost immediately; the latency is only in the progress bar.
*   **Tantivy Schema Introspection (Severity: LOW):** The plan assumes `index.schema` is a property and `.field_names()` is a method. If the installed `tantivy-py` version deviates, Task 7 might require a `try/except` fallback.
    *   *Mitigation:* The plan already includes a note for the executor to use a `ValueError` probe if needed.
*   **`LocalIndexerError` Import Race (Severity: LOW):** Test 4 (Task 9) attempts to import a class that isn't created until Task 10.
    *   *Mitigation:* The plan explicitly acknowledges this and directs the executor to accept the `ImportError` as a "RED" state, which is valid.

---

## 4. Suggestions

*   **Reset Button Tooltip:** Ensure the tooltip for the Reset button (`Delete all LOCAL index data...`) explicitly mentions that it **does not** touch source files, to further reduce user anxiety during recovery. (Plan 02 Task 3 already has this in the dialog, but adding it to the tooltip is helpful).
*   **Connection Cleanup:** In `reset_my_library` Step 1, consider adding a `gc.collect()` *immediately after* `conn.close()` and `self._thread_local._conn = None` to ensure the SQLite file handle is truly released before the rename-aside.
*   **Validation check:** During Task 11 of Plan 01, ensure that `_ensure_writer` is used for **all** steady-state write operations (`_delete_file`, `remove_folder`, etc.) but never for the initial `__init__` acquisition, which has its own legacy retry loop. The plan currently identifies the correct sites.

---

## 5. Risk Assessment

**Overall Risk: LOW**

### Justification:
1.  **Surgical Changes:** The fixes in `local_indexer.py` are targeted and do not attempt to refactor the entire architecture, minimizing regression surface.
2.  **Exhaustive Testing:** The use of 5 new integration tests covering the exact failure trace seen in production ensures the cascade is truly broken.
3.  **Safe Recovery:** The "Reset My Library" feature is scoped strictly to the `LocalIndex` and `LocalLabIndex` directories. It cannot accidentally delete PGP data, NLI cross-references, or the user's primary research files.
4.  **Windows Awareness:** The plan explicitly accounts for Windows-specific file-locking quirks that are the usual source of "impossible" bugs in Tantivy-based applications.

## Bug A — Redundant `tantivy.Index(...)` reopen

**CONFIRMED, but my fix is INCOMPLETE.**

- `rebuild_main_index_atomic` reopens a writer at `shared/local_indexer.py:2799` (step 6 — `_reopen_internal_writer_index`).
- `LocalIndexer.__init__` **always** opens another at `:1164` — removing my proposed line `:1147` alone still double-opens.
- `:1140` can itself raise on a Phase 95 index (the `tantivy.Index(schema, path=index_dir)` call before rebuild may fail because the on-disk meta.json has the old schema).
- **Correct fix:** either (a) skip the writer-acquisition retry loop entirely when rebuild already set `self._writer`, or (b) make `rebuild_main_index_atomic` *not* reopen the writer (leave that to the caller).
- **Additional:** in `genizah_core.py:6879`, constructing a `LocalIndexer` solely for the recovery rebuild is suspect — its `__init__` acquires a writer **before** running its own rebuild path. After `:6884`, that temporary indexer must be closed before `_open_local_searcher` opens `self.local_searcher` itself.

## Bug B — `.tantivy-writer.lock` carried through os.rename

**PARTIALLY CONFIRMED — but my proximate cause is wrong.**

- The actual problem is **not** "lockfile carried by rename" — it's that `del fresh_writer` / `del fresh_index` at `:2747` is **weak on Windows** because Python GC may delay the Rust drop, so the writer/searcher handles aren't actually released before the rename.
- **Codex's preferred fix:** explicit nulling + GC:
  ```python
  fresh_writer.commit()
  fresh_writer.wait_merging_threads()
  fresh_writer = None
  fresh_index = None
  gc.collect()
  ```
  Then verify the lock can be removed/renamed before the swap.
- **Hard warning:** do NOT blindly `os.remove(.tantivy-writer.lock)` while a writer might still exist — risk of corrupting an active write.
- **Deterministic test path:** monkeypatch a fake writer whose lock release is observable, OR on Windows hold an open file handle to `.tantivy-writer.lock` and assert that rebuild retries fail cleanly (no silent corruption).

## Bug C — Unconditional `delete_documents("scan_run_id", ...)` in discard_run

**CONFIRMED — and there's a SECOND bug inside it I missed.**

- My fix (detect schema, fall back to per-`unique_id` deletion) is right.
- **NEW bug C2:** `_del_writer` at `:2955` is **not closed** after failure or after commit. The writer-reopen at `:3012` immediately hits `LockBusy` against its **own still-live `_del_writer`**.
  - **Fix:** use a single writer through the whole `discard_run`, OR explicitly `_del_writer = None; gc.collect()` before reopen.
- **NEW bug C3:** `discard_run` currently logs the Tantivy delete failure at `:2958-2960` and **continues to the SQLite deletion** at step 3 — risking orphaned Tantivy docs (rows gone from SQLite but still in the index, searchable).

## Missed Bug 6 — Phase 95 indexes with no `.schema_version` marker bypass rebuild

**Codex found this independently.**

Both `shared/local_indexer.py:1108` and `genizah_core.py:6858` use:
```python
schema_mismatch = (actual_marker is not None and actual_marker != expected)
```

A Phase 95 index that has `meta.json` but **no `.schema_version` file** (because Phase 95 never wrote one) satisfies `actual_marker is None` → `schema_mismatch = False` → no rebuild → schema-error crash later.

**Fix:** if `meta.json` exists AND `.schema_version` is absent → treat as schema mismatch and trigger rebuild. This explains the user's original symptom — their pre-Phase-97 LOCAL index never had a `.schema_version` marker, so the schema-mismatch detection was skipped, and the crash came from `tantivy.Index(new_schema, path=old_dir)` itself raising.

This is actually the **root** of the cascade — the schema-marker detection should have caught this at startup before any of the lock-busy mess.

## Codex's recommendations beyond my brief

### Defensive stale-lock cleanup — YES, but conservative

- Only on Windows.
- Only triggered on writer `LockBusy`.
- Attempt rename/delete of `.tantivy-writer.lock` with retries.
- If Windows reports access-denied → assume a live holder exists; keep + backoff.
- **Do NOT** do POSIX-style unlink-under-lock (that risks corrupting an active writer).

### Shared helper — YES, urgent

The `SearchEngine._open_local_searcher` mismatch/rebuild path and the `LocalIndexer.__init__` mismatch/rebuild path are **duplicated** and currently interact badly (both call rebuild, both reopen writers, both can deadlock against each other if the same dir is shared).

**Codex recommends:** centralize marker detection + atomic rebuild in `shared/local_indexer.py`, with an `open_writer` / `reopen_writer` option so `SearchEngine` can rebuild **without** creating a persistent writer.

### Ordering — CRITICAL

Codex prescribes a strict ordering for the fix plan:

1. **Bug 6** (schema marker missing → bypass) + **Bug A** (constructor/rebuild ownership) — fix together first.
2. **Bug C** + **C2** + **C3** (discard writer lifecycle + fallback + don't-continue-on-failure).
3. **Bug D** (`_ensure_writer`).
4. Stale-lock cleanup.
5. **Bug E** (Reset UI).

Reasoning: fixing A without C still crashes on discard; fixing C without A still leaves startup recovery blocked; fixing both without Bug 6 still allows fresh installs with stale Phase 95 indexes to hit the crash.

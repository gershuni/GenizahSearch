**Rollback semantics (NEW-M1 wording per round-2 cross-AI review):**
- `set_auth`: **SYMMETRIC user/profile rollback (2 keys: USER_KEY + PROFILE_KEY).** set_auth never owns `auth_session` — that key belongs to the outer caller. On profile-write failure after a successful user-write, BOTH auth_user AND auth_profile are popped.
- `do_login` / `_oauth_complete_login` (callers): **DEFENSIVE 3-key cleanup (auth_session + auth_user + auth_profile).** When set_auth returns False, the caller best-effort pops ALL 3 keys — defensive against the case where set_auth's own SYMMETRIC 2-key rollback also failed during a prune race.

The plan repeatedly distinguishes these two cases. Do NOT collapse "SYMMETRIC 2-key" + "DEFENSIVE 3-key" into a single "SYMMETRIC 3-key" formulation — that would mislead a future contributor into adding an `auth_session` pop INSIDE set_auth, which is incorrect.

**Purpose:** Closes the multi-key auth-write atomicity gap that survives Phase 90 — `safe_user_set` returns `False` on prune-race, so multi-write boundaries (set_auth, do_login, _oauth_complete_login) must check return values AND roll back appropriately on partial failure. Codex's HIGH catch in round-1 91-REVIEWS.md surfaced that the original D-04 rollback only popped USER_KEY, leaving stale auth_profile data observable to `GlobalAuthState.get_role()/is_admin()/is_editor()` (which read profile independently of user) — a real security/correctness issue. Symmetric set_auth rollback + defensive caller-side 3-key cleanup closes this. After this plan ships, the Phase 87 lint scanner enforces ZERO raw `app.storage.user` accesses anywhere under `web/`, and a prune-race during OAuth login surfaces a user-visible error instead of a silent 500 / half-state / stale-role-leak.

```python
def safe_user_get(key: str, default: Any = None) -> Any:
    """Read app.storage.user[key], returning default on any failure.
    Swallows AssertionError (debug-logged) and other Exception (warning-logged)."""

def safe_user_set(key: str, value: Any) -> bool:
    """Write app.storage.user[key] = value. Returns True on success, False on
    AssertionError (prune race, debug-logged) or other Exception (warning-logged).
    CALLERS WITH MULTI-KEY ATOMICITY NEEDS MUST CHECK THE RETURN VALUE."""

def safe_user_pop(key: str, default: Any = None) -> Any:
    """Pop app.storage.user[key], returning default on any failure.
    Same exception-swallow contract as safe_user_get."""
```

`web/main.py:1455-1462:show_error` closure body (full audit):

**Disposition:** `show_error` is NOT pure ("just sets label.text + label.visible"). It encapsulates 6 UI/observability ops. Passing `show_error` directly as `show_error_fn` to `_oauth_complete_login` is SAFE — the entire UI-recovery transition (spinner/status hide; error/home show; posthog event) fires atomically within the existing closure. No additional closure wrapping needed.

**Observed double-posthog risk (NEW-L1 — round-2 polish, deferred):** `_oauth_complete_login` ALSO calls `posthog_capture('login_failed', {'reason': 'session_storage_unavailable'|'auth_state_storage_unavailable', 'method': 'google_oauth'})` BEFORE calling `show_error_fn`. Since `show_error_fn === show_error` and `show_error` itself emits `posthog_capture('login_failed', ...)`, the resulting trace will have TWO `login_failed` events per partial-write failure — one with `reason='session_storage_unavailable'` (rich) and one with `reason='Session storage unavailable. Please try again.'` (truncated message text). This is acceptable for Phase 91 (the rich reason is the operational signal; the truncated message-text event is a duplicate but not harmful), and matches the existing behavior pattern of show_error firing posthog for ALL OAuth error paths.

**Future consolidation option (NEW-L1 polish, DEFERRED to Phase 92 / future telemetry-polish phase):** A future refactor could route the rich reason through `show_error_fn` as an extra argument so only ONE `login_failed` event fires per partial-write failure — for example, signature `show_error_fn(message, posthog_reason='session_storage_unavailable')`. The closure would then emit the rich reason instead of the truncated message text, and `_oauth_complete_login` would drop its direct `posthog_capture('login_failed', ...)` call. This is a non-blocking polish item: Plan 91-01 acceptance criteria do NOT require single-event behavior. PostHog dashboard consumers can filter on the rich `session_storage_unavailable` / `auth_state_storage_unavailable` reason tags today; the inflation is bounded and observable. Disposition: NOT addressed in Phase 91; reaffirmed as acceptable.

**Future-contributor guidance:** If a future refactor adds spinner/status restoration logic to a NEW UI element on the OAuth callback page, that element MUST be added to `show_error`'s body. The `_oauth_complete_login` helper is intentionally UI-agnostic — it only knows about `status_label` (which it mutates on happy-path) and `show_error_fn` (which it invokes on failure). All other UI state recovery lives inside `show_error`.

```python
        Now:        `profile is None` triggers a best-effort pop of the
```

```python
    failing during a prune race is covered by the outer DEFENSIVE cleanup.

            'refresh_token': session.get('refresh_token'),

            posthog_capture('login_failed', {
                'reason': 'session_storage_unavailable',
                'method': 'google_oauth',
```

```python
_PRUNE_MSG = (

def _build_pruned_storage():
    """Storage stub where every access raises the NiceGUI prune AssertionError.

    Used by T-A and T-C. Each test calls this fresh to avoid shared state.

    storage = MagicMock()

class _RoutingStorage(dict):
    """Dict subclass that routes writes by key.

    Used by T-D and T-E. A subset of keys can be configured to raise
    AssertionError on write; all others behave as a normal dict. Reads
    (get / __getitem__) are normal dict semantics. Pop semantics are
    normal dict semantics — the stale-key cleanup paths (SYMMETRIC
    rollback in set_auth, DEFENSIVE cleanup in _oauth_complete_login)
    pop using safe_user_pop which calls .pop with a default.

    Constructor signature (verified against NEW-H4 + NEW-H5 canonical
    AFTER blocks in 91-CODEX-HFIXES.md):
        _RoutingStorage(initial_dict={}, fail_writes_for={'key1', ...})

    Example NEW-H4: `_RoutingStorage({'auth_profile': {'role': 'admin'}},
                                     fail_writes_for={'auth_profile'})`
    pre-seeds a stale admin profile from a prior session, then raises
    AssertionError when set_auth tries to write a new auth_profile.

    Example NEW-H5: `_RoutingStorage({'auth_user': {...}, 'auth_profile':
                                     {...}}, fail_writes_for={'auth_user'})`
    pre-seeds stale prior-session user + profile, then raises
    AssertionError when set_auth tries to write a new auth_user.
    """
    def __init__(self, *args, fail_writes_for=None, **kwargs):
        super().__init__(*args, **kwargs)
        self._fail_writes_for = set(fail_writes_for or ())

    def __setitem__(self, key, value):
        if key in self._fail_writes_for:
            raise AssertionError(_PRUNE_MSG)
        super().__setitem__(key, value)
```

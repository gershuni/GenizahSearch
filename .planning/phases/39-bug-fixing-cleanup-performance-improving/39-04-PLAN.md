<task type="auto">
  <name>Task 1: Optimize search result card rendering</name>
  <files>web/pages/search.py</files>
  <action>
Profile the result card creation and fix the top bottlenecks:

**Fix 1: Hoist per-card imports to page-level**

In `create_result_card()`, there are imports inside the loop body:
```python
from genizah_core import get_library_display, LIBRARY_CODES  # Line ~2273
from web.components.catalog_dialog import show_catalog_dialog  # Line ~2312
```

These run for EVERY card (50 per page). Move them to the top of the `search_page()` function (or module level), before the render loop. Python import caching makes repeated imports cheap but not free — the import machinery still has to check sys.modules, acquire the import lock, etc. For 50-200 iterations this adds measurable overhead.

Search the entire `create_result_card` function and `render_results` function for any `from X import Y` statements and hoist them all to page setup level.

**Fix 2: Reduce NiceGUI element count per result card**

Each result card creates many UI elements (checkbox, labels, badges, buttons). Look for opportunities to:

1. Skip the domain badge entirely when `search_state.result_domains` is empty (common case: no FJMS data)
2. Skip the PGP badge when `search_state.transcription_sys_ids` is empty
3. Skip the catalog button when `search_state.catalog_source_counts` is empty
4. Use conditional rendering: only create UI elements when data exists, not create-then-hide

**Fix 3: Batch-prepare display data before rendering**

Before the render loop, pre-compute a dict of display data per result to avoid repeated dictionary lookups inside create_result_card:
```python
# Before render loop
prepared = []
for i, res in enumerate(results):
    display = res.get('display', {})
    sys_id = display.get('id', '')
    prepared.append({
        'index': i + global_offset,  # global offset for pagination
        'shelfmark': display.get('shelfmark', 'Unknown'),
        'title': display.get('title', ''),
        'snippet': res.get('snippet', ''),
        'library_code': display.get('library_code', ''),
        'sys_id': sys_id,
        'has_pgp': sys_id in search_state.transcription_sys_ids,
        'domains': search_state.result_domains.get(sys_id, []) if search_state.result_domains else [],
        'cat_count': search_state.catalog_source_counts.get(sys_id, 0),
    })
```
Then pass prepared data to create_result_card instead of raw result dicts for the display portion.

This is a refactor of the inner loop — implement it only if the existing create_result_card structure allows clean separation. If the function also needs the raw result dict for click handlers, pass both.

Examine browse.py for performance issues and apply targeted fixes:

**Fix 1: Check for per-render imports**

Search browse.py for any `from X import Y` statements inside frequently-called functions (render loops, event handlers). Hoist to module or page level.

**Fix 2: Defer expensive metadata enrichment**

If the browse page loads FJMS, PGP, NLI metadata synchronously during initial page render, move it to an async callback that fires after the page is visible. Use NiceGUI's `ui.timer(0.1, callback, once=True)` pattern or `asyncio.get_event_loop().call_soon()` to defer non-critical enrichment.

Look for:
- FJMS service calls in browse page init
- NLI crossref lookups on page load
- PGP metadata fetch on page load

If these are already deferred (called on user interaction, not page load), no changes needed — document this finding.

**Fix 3: Lazy-load heavy components**

If the browse page creates catalog dialogs, bibliography dialogs, or other heavy components on page load, convert to lazy creation (create on first use).

Look for patterns like:
```python
# Eager (slow)
catalog_dialog = create_catalog_dialog()

# Lazy (fast)
_catalog_dialog = None
def get_catalog_dialog():
    nonlocal _catalog_dialog
    if _catalog_dialog is None:
        _catalog_dialog = create_catalog_dialog()
    return _catalog_dialog
```

Only apply this pattern where it's clearly beneficial (dialog or component creation is expensive). If browse.py already uses lazy patterns, document this finding.

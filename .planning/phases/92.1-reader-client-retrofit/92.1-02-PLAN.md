The fix MUST be at the call-site / context-binding layer, NOT a log-level downgrade in `web/safe_storage.py` (downgrading would mask the bug; the new list still wouldn't be created because `get_user_client()` would still fall back to the anonymous singleton with no `auth_session`, and the Plan 92.1-01 RLS migration depends on a valid `auth_session` being readable).

Purpose: After Plan 92.1-01 migrates the readers, Symptom 1 (lists not loading) and Symptom 2 (new list from /lists silently failing) are gone — the migrated readers now build authenticated clients and the writes have always used `get_user_client()`. But Symptom 3 is independent: it's a NiceGUI context-loss bug, not an RLS-reachability bug. The async `create_and_add` handler in `add_to_list_dialog.py` calls `await lists_mgr.create_list(...)` which (in `web/user_lists.py:218-244`) calls the SYNCHRONOUS `sb_create_list(...)` directly inside the async function body — no `run.io_bound()`, no thread offload. So the error is NOT a thread-context loss. Most likely root cause: the dialog's button on_click fires in a NiceGUI client context that is detached from the page's slot stack (typical for buttons inside `ui.dialog()` containers that outlive the parent page navigation, OR the await suspends to a callback context that NiceGUI's `app.storage.user` accessor cannot bind). Verify before fixing.

**Hypothesis A — Dialog opened from a search-result card callback that's been detached from the slot stack:**
`add_to_list_dialog.show_add_to_list_dialog` is called from `web/components/add_to_list_dialog.py:create_add_to_list_button.show_dialog()`. The button is created INSIDE a search-result card. If the search results page uses lazy-render or virtualized scrolling that disposes-and-recreates the card containers, the button's on_click may execute against a client context whose slot stack no longer includes the dialog's parent. When `dialog.open()` runs in a re-rendered card, the dialog may be parented to a stale client.

**Hypothesis B — NiceGUI async on_click + await re-entry losing context:** **TRIMMED per Revision Info 11 (2026-05-17)** — supabase-py uses sync httpx (no `httpx.AsyncClient`), so `await lists_mgr.create_list(...)` does NOT yield to the event loop and the call frame stays on the original task. Context-loss across a non-suspending await is implausible. Hypothesis B is retained as a label in the resume-signal vocabulary for completeness but is not a serious candidate; Task 1 should not spend instrumentation cycles disproving it. Focus on A and D.

**Hypothesis C — Project lookup branch fires `_get_cached_data()` which calls `get_user_lists` AGAIN (re-entrancy through the same migrated reader):**
When the user picks a project from the project dropdown in the "Create new list" form, `project_id` is non-None. `UserListsManager.create_list` then calls `self._get_cached_data()` which calls BOTH `get_user_lists(user_id)` AND `get_projects(user_id)`. After Plan 92.1-01 migration, these readers now call `get_user_client()` which calls `safe_user_get('auth_session')`. If the dialog button on_click is somehow running in a context where the NiceGUI request context for `app.storage.user` is unavailable (e.g., a coroutine scheduled via `asyncio.create_task` that survived past its originating request), `safe_user_get` would emit the UI-context error. But this would also affect the existing `add_item` and `_get_cached_data` calls.

**Hypothesis D (MOST LIKELY) — `dialog.open()` followed by button-press creates a new client-less context via NiceGUI auto-modal dispatch:**
NiceGUI 2.x dialogs (`ui.dialog()`) use overlay rendering; when the user clicks "Create and Add" inside the dialog, the button's on_click handler may dispatch on a slot stack that NiceGUI cannot bind to the originating request's user-storage. The first symptom — the `safe_user_get` warning — is the canary for this. Verify by adding a single line of diagnostic logging at the top of `create_and_add` to capture the bound client identity and slot-stack depth before the failing call.

**Diagnostic approach (Task 1):** Add temporary `logger.warning(f"[READER-03 DIAG] context.client.id={ui.context.client.id if ui.context else 'NO_CONTEXT'}, slot_stack_depth={len(ui.context.slot_stack) if ui.context else -1}")` (or equivalent NiceGUI introspection) at the top of `create_and_add`. Run the failing path. Confirm whether the client/slot context is intact or lost. Then choose the fix.

**Likely fix (assuming Hypothesis A or D):** Capture the request-bound storage values BEFORE the dialog defines its inner async handlers — read `auth_session` once at `show_add_to_list_dialog` entry and pass it through closures, OR use `ui.context.client.run_async(...)` to ensure the create_and_add runs bound to the page's client, OR (simpler) explicitly bind the handler via `client = ui.context.client; on_click=lambda: client.run_async(create_and_add())`.

**Fallback (if no fix works clean):** Wrap the safe_user_get call in `get_user_client` with a re-entry safety net that, when the UI-context error fires, reads the auth_session from a request-scoped variable that `show_add_to_list_dialog` captured at entry. This is more invasive but provably correct.

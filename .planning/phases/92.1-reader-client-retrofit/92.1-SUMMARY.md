## What This Phase Closed

A P0 reader-client RLS-reachability regression introduced by Phase 90 D-09/D-10 (singleton-anonymous-only invariant). Phase 90 correctly closed the multitenant SIGNED_IN-event-listener leak (Codex F3 catch) by routing all five bootstrap helpers through throwaway clients — but Phase 90 did not migrate the ~12 reader functions in `web/supabase_client.py` that still called `get_client()`. The anonymous singleton role failed RLS policies of the form `TO authenticated USING (auth.uid() = user_id)`, so logged-in users saw empty lists, projects, and recent items.

**Smoking-gun planning artifact:** `.planning/phases/90-auth-caching-rewrite-no-set-session/90-DISCUSSION-LOG.md:147` recorded the false assumption "`get_user_lists` reads work anonymously; only writes need auth." The `user_lists` SELECT policy was `TO authenticated` — anonymous role got 0 rows.

## Symptom-3 Resolution (NO-REPRO branch)

Plan 92.1-02 was planned with a case-driven decision tree (cases a/b/c/d per Reviews R2-2) covering different `request_contextvar` capture patterns: case-a (all three points None → upstream rediagnosis), case-b (P1 bound, P3 None → `copy_context()` at dialog entry + awaited `asyncio.create_task(coro, context=ctx)` around BOTH `create_and_add` and `do_add` handlers per Reviews M-R2-1/M-R2-2), case-c (P1+P2 bound, P3 None → same fix but capture at button registration), case-d (P3 bound but storage still raises → retry-on-AssertionError fallback in `get_user_client`).

**Outcome: NO-REPRO branch authorized by `<resume-signal>` Revision Blocker 3.** When Hillel ran the reproduction protocol on 2026-05-17 (09:01-09:21 UTC), all three required evidence pieces materialized:

1. **3 successful list creations** at 09:01:37 / 09:20:07 / 09:21:26 UTC — lists `92.1-diag-1`, `92.1-norepro-2`, `92.1-norepro-3` all created end-to-end without the console error
2. **Zero `safe_user_get('auth_session') unexpected failure` WARNING lines** in server log; the 4 diagnostic capture points (P1 dialog-entry / P2 button-registration / P3 handler-firing / P3.5 pre-create_list-traceback) all logged `request_contextvar=bound:<same id>` within each click — contextvar binding STABLE across the dialog/handler boundary, NOT lost
3. **Supabase `user_lists` rows 279/280/281** persisted with `user_id=f8371f69-b7b8-49e9-bbd9-d79dfeecd7b8` confirming the RLS-authenticated write path is functioning end-to-end

**Conclusion:** Symptom 3 is GONE. The bug was eliminated as a side-effect of Plan 92.1-01's reader migration — the `user_lists.py` / `supabase_client.py` reader path now consistently uses `get_user_client()` which binds correctly through the dialog/click lifecycle in the Phase 90 architecture. None of cases a/b/c/d apply, so the case-driven binding fix was correctly SKIPPED (adding speculative `copy_context()` wrapping or retry/wrap logic without evidence would constitute Rule 4 architectural change and could MASK future regressions by hiding the precise Symptom 3 WARNING signal under fallback logic).

**Revision Blocker 2 refactor applied unconditionally.** Even with no live bug to fix, the `_create_and_add_handler` module-level helper was extracted from the inline `async def create_and_add()` closure per the plan's explicit "regardless of diagnosis outcome" lock-in. The refactor is what makes the 5-test regression suite testable — without it, the handler is buried inside a closure that requires the full NiceGUI dialog harness to instantiate. The READER-03 closure is structurally sound for future regression detection: any future appearance of the `'safe_user_get' in msg AND "'auth_session'" in msg AND 'unexpected failure' in msg` log-message signal will be caught by `test_create_and_add_with_unbound_contextvar_does_not_warn`'s warning-count assertion.

**Rejected candidates (documented for posterity):**
- **Captured-`auth_session` snapshot strategy** (Reviews H-AGREED-1, both Gemini + Codex round 1): stale-token / logout-after-dialog-open footgun. Rejected.
- **`context.client.run_async(...)` / `with _dialog_owner_client:` slot-stack rebind** (Reviews C2, Codex source-citation): operates on slot stack only; `request_contextvar` is unaffected (verified at `venv/Lib/site-packages/nicegui/storage.py:109-113`). Rejected.
- **`asyncio.ensure_future(...)` fire-and-forget** (Reviews M-R2-1): drops exceptions and prevents NiceGUI from awaiting the handler. Rejected in favor of awaited `asyncio.create_task(coro, context=ctx)` (Python 3.11+).
- **Not done:** Did NOT downgrade safe_storage.py log level (would mask future bugs). Did NOT touch `get_user_client` signature with an `auth_session_override` kwarg (would enable the rejected snapshot pattern). Did NOT apply case-b/c `copy_context()` wrapping or case-d retry/wrap fallback (NO-REPRO branch — would mask future regressions). `web/supabase_client.py` is UNCHANGED relative to Plan 92.1-01 baseline.

## Lessons / Patterns Reinforced

1. **Cross-AI review is necessary but not sufficient.** Phase 90 went through 4 rounds of Gemini + Codex review and all 23 findings were addressed — but the scope of the review was "does the no-set-session refactor preserve the public contract?" Nobody asked "do the readers still build authenticated clients?" because the readers weren't in the diff. Lesson: when a phase changes WRITE-PATH semantics with downstream READ-PATH implications, add a "downstream read-path RLS reachability" review prompt.
2. **Add live cross-user smoke tests at phase boundaries with auth changes.** Phase 87 lint scanner + Phase 90 AST scanner caught a lot of static issues, but RLS reachability is an end-to-end concern. A live smoke test between Phase 90 ship (2026-05-14) and Phase 92-01 closeout (2026-05-17) would have caught this in days, not weeks.
3. **`get_user_client()` falling back to the anonymous singleton is the right default.** It means "use the strongest available auth context" — anonymous browsers reading `TO public` tables stay anonymous; logged-in users get authenticated reads. No call-site logic change needed; the migration is a verbatim substitution.
4. **Cross-AI review of the FIX plan caught additional gaps the planner+checker missed — across MULTIPLE rounds.** Round 1: Reviews C1 (count contradiction), C2 (slot-stack vs request_contextvar mechanism), H-AGREED-1 (stale-token footgun), and H1 (mock bypasses failing chain) were all real fix-side issues. Round 2: Reviews R2-1 (`get_feed_items` admin path RLS evidence missing — resolved Option C with explicit evidence cite), R2-2 (3-point `request_contextvar` capture mandatory — without it, `copy_context()` could capture None and be a silent no-op), R2-3 (regression test must control `request_contextvar` directly, not simulate downstream RuntimeError). The 3-point diagnostic instrumentation Plan 92.1-02 mandated PROVED the no-repro by yielding stable `request_contextvar=bound:<same id>` readings at all 4 capture points; without those readings, "the bug is gone" would have been a hypothesis instead of an evidenced conclusion.
5. **No-repro branch closure pattern.** When checkpoint reproduction yields evidence that a P0 bug has been eliminated by an upstream plan, the closeout still requires (a) the mandatory refactor so future tests can exist, (b) the permanent CI regression guard exercising the real failing chain with the precise Symptom-3 WARNING string anchor, and (c) documentation of the specific log-message signal so any future regression has a precise log anchor. Adding speculative binding-fix code under the no-repro state would constitute Rule 4 architectural change AND could mask future regressions by hiding the symptom-3 signal under retry/wrap fallback.
6. **Status-flag wording matters for P0/P1 issues (Reviews M4).** "Fixed in code; verification pending SWEEP-05 smoke run 2" is the correct status until end-to-end browser verification ships. Premature ✅-Fixed-with-date marking violates the invariant that production regressions stay Open until proven fixed against real-world conditions.

### MR-01: `discoveries` mis-categorized as a partial-auth table in SUPABASE_GUIDE.md BANNED_TABLES protocol

**File:** `docs/guides/SUPABASE_GUIDE.md:545`
**Issue:** The BANNED_TABLES extension-protocol paragraph reads: *"Partial-auth tables (`corrections`, `comments`, `discoveries`) — those with both a `TO public USING (<filter>)` AND a `TO authenticated USING (auth.uid()=<owner>)` SELECT branch — are deliberately NOT in `BANNED_TABLES`..."*. However, the RLS evidence in the SAME file at lines 498-515 documents only ONE SELECT policy on `discoveries` (`TO public USING (is_hidden = false)`) and TO authenticated INSERT / UPDATE policies — there is NO `TO authenticated` SELECT branch on `discoveries`. This was the entire substance of Reviews R2-1 Option C in Plan 92.1-01: the strengthened KEEP rationale for `get_feed_items` rests on `discoveries` having NO admin/authenticated SELECT branch. Calling `discoveries` a "partial-auth table" in the protocol paragraph contradicts that finding and could mislead a future maintainer into thinking `get_user_client()` was needed to surface additional rows from `discoveries`.

`fragment_joins` (TO public SELECT with no authenticated SELECT branch) is structurally the same as `discoveries` and is correctly omitted from the partial-auth list. `discoveries` belongs in the same omitted category.

**Fix:** Change the partial-auth list to `(corrections, comments)` only. Optionally add a sentence noting that `discoveries` is a TO-public-only SELECT table (no authenticated SELECT branch) and is therefore similar to `fragment_joins` — both surface the same rows under both client roles. Suggested patch:

```markdown
Partial-auth tables (`corrections`, `comments`) — those with both a `TO public USING (<filter>)` AND a `TO authenticated USING (auth.uid()=<owner>)` SELECT branch — are deliberately NOT in `BANNED_TABLES` because their `get_client()` reads remain valid for the public branch. The per-function migration in `web/supabase_client.py` switches to `get_user_client()` for those readers so the authenticated branch becomes reachable. If a future schema change extends such a table to a user-private-only filter (no public branch), add it to `BANNED_TABLES`. Tables with ONLY a `TO public` SELECT branch (`discoveries`, `fragment_joins`, `profiles`) return identical rows under both anon and authenticated client roles; the per-function migration for `discoveries` and `fragment_joins` is for forward-compat (e.g., `auth.uid()` available for downstream votes/ownership checks), not for surfacing additional rows.
```

This is documentation-only; no production-code change is needed. The actual `BANNED_TABLES` set in the scanner is correct.

### LR-01: Module-level `_client` singleton in `web.supabase_client` is not reset between tests, leaking `MagicMock` state across the suite

**File:** `tests/test_add_to_list_dialog_ui_context.py:200-317` (also `tests/test_supabase_client_reader_rls.py:104-127`)
**Issue:** Tests `test_create_and_add_with_unbound_contextvar_does_not_warn` and `test_create_and_add_with_bound_contextvar_no_auth_session` exercise the anonymous-fallback path: `get_user_client()` → `return get_client()` → `_client = create_client(...)` at `web/supabase_client.py:62`. Because `create_client` is monkeypatched to return `fake_supabase_client` (a `MagicMock`), the module-level `_client` global is assigned the `MagicMock` and persists after the test exits — `monkeypatch.undo()` restores the `create_client` attribute but does NOT roll back the assignment that already happened to `_client`. A subsequent test in any later-collected file that calls `get_client()` will receive the stale `MagicMock` instead of a fresh real client (or its own mocked client).

This is a pre-existing pattern in the codebase (`tests/test_auth_revocation_and_headers.py` has the same shape), but the new tests double the number of sites where it can happen.

The negative-control test in `tests/test_supabase_client_reader_rls.py:104` (`test_reader_falls_back_to_anonymous_when_no_auth_session`) monkeypatches `get_client` directly to a `MagicMock` — that's correctly restored — so it doesn't suffer this leak, but the dialog UI-context tests do.

In practice this has not caused failures because the new tests both monkeypatch `create_client` before any production code reads `_client`, but the leak is a footgun for any future test added in collection order between these tests and a test that checks `_client is None`.

**Fix:** Add an autouse fixture (in `tests/conftest.py` or a module-scoped fixture in each affected test file) that resets `_client` to `None` before/after each test:

```python
@pytest.fixture(autouse=True)
def _reset_supabase_client_singleton():
    import web.supabase_client as mod
    mod._client = None
    yield
    mod._client = None
```

Or, less invasively, call `mod.reset_client()` (which already exists at `web/supabase_client.py:66-69`) at the start of each test that monkeypatches `create_client`.

### LR-02: Contradictory comment + assertion pair in `test_create_and_add_with_unbound_contextvar_does_not_warn`

**File:** `tests/test_add_to_list_dialog_ui_context.py:284-305`
**Issue:** Two adjacent comment blocks make inconsistent claims about what is expected:

- Lines 288-294 say: *"Under the no-repro state confirmed 2026-05-17, the handler does NOT reach safe_user_get('auth_session') in a way that triggers the WARNING... The expected behavior post-fix: ONE WARNING from safe_user_get('auth_session') because the safe_storage backend stub raises RuntimeError on access."*
- Lines 295-298 then assert: `assert capture.get('get_user_client_called') is True`
- Lines 299-305 assert: `assert capture.get('apply_user_auth_called') is False`
- Lines 306-315 assert: `assert len(symptom_3_warnings) <= 1`

The first comment block toggles between "does NOT reach safe_user_get('auth_session') in a way that triggers the WARNING" and "ONE WARNING ... because the safe_storage backend stub raises RuntimeError" within the same paragraph — these are not actually contradictory once you parse them carefully (the production WARNING is unwanted; the test's stub-injected WARNING is expected), but the prose makes it hard to verify the intent at a glance.

The actual assertions are correct (`<= 1` permits the one expected stub-induced WARNING while still catching any amplification regression), but a reader of the test will spend time disentangling the comment from the assertion.

**Fix:** Rewrite the comment block to clearly separate "what we WANT (production-side)" from "what the test stub HAPPENS to emit (expected, just plumbing)". Suggested:

```python
# The test deliberately makes the safe_storage backend raise so safe_user_get
# emits exactly ONE WARNING (that's the stub doing its job).
# The fix's correctness contract: that's the ONLY safe_storage WARNING that should
# fire — production code must not amplify it or call safe_user_get('auth_session')
# from any unprotected site downstream of the dialog. If a future regression adds
# such a site, this count goes >1 and the test fails with the exact smoke-run-1
# message in the diagnostic.
```

### LR-05: `_violations` reports the `aliased_client` seed-trap pattern by formatting the alias name back into the violation message — but the variable name is captured by reference to the AST node, not by a stable string lookup, so highly nested aliases would lose fidelity

**File:** `tests/test_no_anonymous_reads_on_authenticated_tables.py:151-156`
**Issue:** Pass 2 in `_violations` formats the violation pattern as `"%s = get_client(); %s.table('%s')" % (receiver.id, receiver.id, table_name)`. This is correct for the simple `client = get_client(); client.table('user_lists')` case (the seed-trap pattern), but a reader of the failure message might assume the scanner correctly tracks alias-of-alias (`a = get_client(); b = a; b.table(...)`). It does NOT — `_collect_get_client_aliases` only walks `Assign` nodes whose `.value` is a direct `get_client()` call. The known-blind-spot xfail covers `wrapper_helper` and `module_level_alias`, but not alias-of-alias.

In practice this is unlikely to matter (alias-of-alias for a Supabase client is pathological code), but the scanner's documented invariants would benefit from a third xfail-strict snippet documenting it explicitly:

```python
('alias_of_alias',
 "def f():\n    a = get_client()\n    b = a\n    return b.table('user_lists').select('*').execute()"),
```

**Fix:** Either add the third blind-spot xfail-strict snippet OR add a sentence to the file docstring's "Known scanner blind spots" list acknowledging alias-of-alias. Low priority; alias-of-alias is so unusual that it falls into the "code review remains the second line of defense" bucket the file docstring already calls out.

## Patterns Worth Highlighting (positive)

These are deliberate good practices in this phase worth preserving in future phases:

- **Inline `READER-XX (Phase 92.1)` migration anchors at every migration site** (12 occurrences in `web/supabase_client.py`). Makes `grep`-driven archaeology trivial.

- **Forward-looking KEEP-caveat comments that name the exact future condition that would force re-migration** (e.g., `get_profile`: *"MUST migrate to get_user_client if private fields (e.g., email, settings) are ever added to this SELECT"*; `get_feed_items`: full RLS-evidence cite + admin-policy-addition trigger). A maintainer who edits the SELECT clause of `get_profile` will see exactly the condition that should make them re-evaluate the KEEP decision.

- **AST scanner blind-spot documentation via `xfail-strict`** (lines 225-245 of `tests/test_no_anonymous_reads_on_authenticated_tables.py`). When a future scanner upgrade detects either of the documented bypass patterns, the test flips to `XPASS` and forces a docstring update — a clean way to encode "this is a known limitation, please document the day you fix it."

- **Stronger negative-control assertion** in `tests/test_supabase_client_reader_rls.py:123-127` — asserting `get_client_mock.called is True` in addition to `apply_mock.call_count == 0` prevents vacuous passes where the reader crashes before reaching the anon fallback. Reviews L1 catch implemented cleanly.

- **Real-chain regression tests in `tests/test_add_to_list_dialog_ui_context.py`** that exercise the actual `get_user_client → safe_user_get('auth_session')` failure surface under controlled `nicegui.storage.request_contextvar` state. The two-test pairing of `test_create_and_add_happy_path_with_bound_contextvar` (proves auth applied) and `test_create_and_add_with_unbound_contextvar_does_not_warn` (proves anon fallback path is clean) is a principled way to anchor a no-repro outcome: future regressions will fail one of the two tests with a precise diagnostic.

- **`request_contextvar` token capture + `try/finally: request_contextvar.reset(_token)`** in all four tests that set the contextvar — prevents test-ordering leakage of contextvar state to subsequent tests. Clean discipline.

- **Refactor-fidelity preservation**: the `_create_and_add_handler` extraction faithfully preserves every observable behavior of the original closure — `if not name` early return, `ui.notify` strings, `dialog.close()` placement, `on_success` callback timing, kwarg threading (`note=new_list_note_value` → `note=note` inside the helper), and `is_logged_in` evaluation at click time. No behavior drift.

- **Rejected-pattern audit is clean** — grep verifies zero occurrences of `_captured_auth_session`, `context.client.run_async`, `with _dialog_owner_client:`, or `READER-03 DIAG` anywhere in `web/`. The rejected captured-token-snapshot strategy left no residue.

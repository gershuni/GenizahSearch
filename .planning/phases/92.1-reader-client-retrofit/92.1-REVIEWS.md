### NEW Critical Concerns from Round 2 (Codex)

#### CRITICAL-R2-1 (HIGH) — `get_feed_items` KEEP rationale is incomplete for admin path

The M2 revision flipped `get_feed_items` (line 1579) from MIGRATE to KEEP, on the grounds that "every branch is public-filtered." **This is true ONLY when `include_hidden=False`.** The actual function signature is:

```python
def get_feed_items(..., include_hidden: bool = False) -> ...:
    query = get_client().table('discoveries')...
    if not include_hidden:
        query = query.eq('is_hidden', False)
    ...
```

(`web/supabase_client.py:1586-1587`)

And the actual callers pass `include_hidden=is_admin`:

```python
# web/pages/discoveries.py:423
items = get_feed_items(..., include_hidden=is_admin)
# web/pages/discoveries.py:588-593
items = get_feed_items(..., include_hidden=is_admin)
```

When `is_admin=True` and `include_hidden=True`, the `discoveries` table is queried WITHOUT the `is_hidden=False` filter. If the RLS policy for `discoveries.is_hidden=true` rows is `TO authenticated` (admin-only), then the anon singleton returns 0 rows for hidden items — silently breaking the admin moderation feed.

**Fix options:**
- **(A)** Migrate `get_feed_items` to `get_user_client()` unconditionally. Count returns to **13 MIGRATE / 5 KEEP** — accepting the round-1 reconciliation. Update disposition table line 183, summary line 871, READER-01 wording at line 224, Plan 03 SUMMARY template.
- **(B)** Keep `get_client()` BUT branch internally: `client = get_user_client() if include_hidden else get_client()`. Reviewer's preferred fix per "If keeping it anonymous, add an explicit proof that hidden/admin feed is not intended" — this is the conservative path.
- **(C)** Verify the RLS policy on `discoveries.is_hidden=true` rows: if the policy is `TO public USING (is_hidden=true OR auth.uid()...)`, then anon admin reads return the same rows as authenticated admin reads, and KEEP is genuinely safe. **This verification is missing from the current plan** and would be a SHOULD-FIX for traceability even if the answer is "anon is fine."

The plan should pick one explicitly and document the evidence. Option A is the simplest and matches round-1 Codex's verdict; Option B is the minimum safe change.

#### CRITICAL-R2-2 (HIGH) — `copy_context()` fix may capture `None` at dialog open

Plan 02's proposed fix at lines 379-389 captures the request context at dialog-entry time:

```python
_captured_ctx = contextvars.copy_context()
```

If `show_add_to_list_dialog` is invoked from an event that itself runs with `nicegui.storage.request_contextvar=None`, then `_captured_ctx` ALSO has `request_contextvar=None`. Replaying the captured context later does NOT magically reconstitute the request — the fix becomes a silent no-op, and Symptom 3 reproduces unchanged.

**Fix:** Plan 02 Task 1 (diagnosis) must explicitly log `request_contextvar.get()` at THREE points (not just the failing handler):
1. At `show_add_to_list_dialog(...)` function entry — proves the OPENER context state
2. At button registration time (when `ui.button(...).on_click(handler)` is called) — proves the REGISTRATION context state
3. At handler firing — proves the FAILURE context state (already in plan)

If signal (1) shows `request_contextvar=None`, then `copy_context()` cannot help and a different fix is required (e.g., re-binding via `request_contextvar.set(some_request)` at button construction, OR moving the storage read to a different lifecycle hook).

#### CRITICAL-R2-3 (HIGH) — H1 regression test does not control `request_contextvar`

The H1 rewrite was supposed to replace the round-1 mock-based test with an integration-style test exercising the real failing chain. The new test:

- DOES call real `get_user_client()` (line 526)
- DOES monkeypatch `web.safe_storage.app` to a `SimpleNamespace` (line 477-489)
- DOES stub `lists_mgr.create_list` with a wrapper (line 499-543)

But it DOES NOT manipulate `nicegui.storage.request_contextvar` directly. The `_RaisingStorage` stub (line 596+) simulates a NiceGUI RuntimeError from `app.storage.user`, but that's not the SAME mechanism — `safe_user_get` would catch and log that error, returning the default. The real failure path is `request_contextvar.get() is None` causing storage to raise UI-context errors that bubble up through `app.storage.user` access.

**Fix:** Either (a) use a real NiceGUI test harness (pytest-nicegui if installed; check `tests/` for any `with Client(...)` patterns), OR (b) explicitly call `nicegui.storage.request_contextvar.set(fake_request)` in the test setup and assert behavior differs vs `request_contextvar.set(None)`.

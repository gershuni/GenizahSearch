## Gemini Review

### 1. Plan Assessments

**Plan 92.1-01: Reader Migration & Guards.** Addresses the core RLS-reachability regression by migrating 13 reader functions from the anonymous singleton to the authenticated `get_user_client()`. Establishes a robust defense-in-depth strategy using an alias-aware AST scanner to enforce the invariant at compile-time and behavioral monkeypatch tests for runtime validation. The explicit disposition table provides high clarity for both execution and future audits.

**Plan 92.1-02: Symptom 3 Fix (UI Context Error).** Adopts a disciplined "Diagnose-then-Act" approach to a complex NiceGUI context-binding failure. The mandatory refactor to extract the dialog handler into a module-level function is an architectural win that transforms an opaque bug into a testable unit. The strict evidence requirements for the "no repro" branch provide a high degree of confidence that intermittent failures won't be prematurely dismissed.

**Plan 92.1-03: Closeout Docs.** A standard reconciliation plan ensuring project traceability across all ledgers. The inclusion of a placeholder scan (Revision Warning 9) is an effective quality gate that prevents common AI documentation errors (like shipping `<fill-in>` strings).

### 2. Strengths

- **Static Analysis Soundness:** The AST scanner in 92.1-01 correctly handles both literal chains (`get_client().table(...)`) and local aliases (`c = get_client()`), making it significantly harder to bypass than grep-based guards.
- **Auditability:** The "Disposition Table" in 92.1-01 Task 1 is an exemplary artifact that removes all ambiguity from the migration phase.
- **Rigor in "No Repro" Case:** Blocker 3's evidence checklist (3 successful attempts + logs + Supabase row) effectively prevents the executor from taking the easy path without empirical proof.
- **Ordering:** The requirement for atomic commit of Tasks 2 and 3 in 92.1-01 (Blocker 4) ensures the build never stays RED at a plan boundary.

### 3. Concerns & Risks

- **HIGH — Plan 92.1-02 Task 2 (Stale Token Risk):** If Hypothesis D (captured snapshot) is the fix, there is a risk that a user leaves the dialog open for >1 hour (JWT TTL). If the token is refreshed by another tab in the interim, the captured snapshot becomes invalid/consumed.
    - **Failure Mode:** Using a consumed refresh token will trigger a logout or refresh failure.
    - **Fix:** The handler should *attempt* a live `safe_user_get` first; only use the captured snapshot if the UI-context error is explicitly raised.

- **MEDIUM — Plan 92.1-01 Task 2 (Hardcoded Table Set):** The `BANNED_TABLES` set in the scanner is static.
    - **Failure Mode:** Future user-scoped tables added to the database will not be protected by the scanner unless the test file is updated.
    - **Fix:** Add a comment in `docs/guides/SUPABASE_GUIDE.md` near the RLS section reminding developers to update the `BANNED_TABLES` set when modifying the schema.

- **MEDIUM — Plan 92.1-01 Task 3 (KEEP Decision 711/721):** Keeping `get_profile` anonymous is correct for `TO public` fields, but risks failing silently if private profile fields (e.g., email, settings) are added to the query later.
    - **Failure Mode:** Adding a private field to the profile SELECT will result in 0 rows/None for authenticated users.
    - **Fix:** Update the inline KEEP comments to explicitly state: "Anon-OK for public fields; MUST migrate to `get_user_client` if private fields are added."

- **LOW — Plan 92.1-02 Task 1 (Evidence Friction):** Requiring a "Supabase Studio screenshot" might be high friction for a headless/CLI-driven agent environment.
    - **Fix:** Allow raw SQL output from the Supabase console/logs as a valid alternative to a screenshot.

### 4. Hypothesis Analysis (Symptom 3)

- **Hypothesis D (NiceGUI modal context loss):** **Most Likely.** NiceGUI 2.x dialog overlays often detach from the primary page slot stack, which is the exact scenario where `app.storage.user` access throws the "UI context" error.
- **Hypothesis A (Detached card):** **Strong Contender.** Especially likely if search results use virtualization or `ui.scroll_area` which might dispose of the button's parent before the handler finishes.
- **Hypothesis B (Async loss):** **Correctly deprioritized.** Since `httpx` is synchronous, the event loop isn't yielding, making task-local context loss implausible.

### 5. Risk Assessment: MEDIUM

While the reader migration is straightforward, the UI context-binding fix (Plan 92.1-02) involves the internal event-loop and slot-stack behavior of NiceGUI, which can be OS/environment-dependent. The strict dependency ordering and mandatory refactor mitigate this, but the ultimate validation remains the human smoke test (Run 2).

**Verdict: Approved for Execution.** Proceed with Plans 92.1-01 through 92.1-03.

## Codex Review

### Summary

Plan 92.1-01 has the right core fix: move user-scoped Supabase reads from the anonymous singleton to `get_user_client()`, preserve `set_session()` constraints, and add both static and behavioral guards. The main problem is internal inconsistency: parts of the plan say 13 migrations / 5 KEEP sites, while other parts still say 15 / 3. That must be reconciled before execution.

Plan 92.1-02 is the riskiest plan. The diagnosis direction is too focused on NiceGUI slot context, but `app.storage.user` is gated by NiceGUI's request context, not just slot/client context. The proposed `context.client.run_async(...)` path appears invalid for the installed NiceGUI version, and the planned unit test mocks away the actual failing path.

Plan 92.1-03 is structurally useful as a ledger closeout, but it inherits the 15-vs-13 contradiction and has a workflow bug: it asks the summary to include the docs commit SHA before that commit exists. It also risks marking the P1 issue "Fixed" before the manual SWEEP-05 smoke run 2 validates the real browser path.

### Strengths

- Plan 92.1-01 correctly identifies the root regression: `get_client()` is anonymous post-Phase 90, so `user_lists`, `list_items`, `recent_items`, and `projects` reads must not use it.
- The 5 KEEP decisions are mostly sound: auth API helpers at `web/supabase_client.py:487` and `:499`, public profile/count reads at `:708` and `:718`, and fragment join fallback at `:1326`.
- The AST scanner shape correctly distinguishes `.table(...)` reads from `client.auth.get_user()` / `get_session()` because it only fires on `Attribute.attr == 'table'`.
- The "no repro" gate in Plan 92.1-02 is strong: 3 attempts + clean server logs + Supabase persistence proof is a real evidentiary bar.
- Plan 92.1-03 correctly keeps Phase 92 Plan 92-02 blocked behind SWEEP-05 smoke run 2.

### Concerns

- **CRITICAL — Plan 92.1-01 / 92.1-03 count contradiction.**
  `92.1-01-PLAN.md:180` says 13 migrate / 5 KEEP, and `:791` verifies exactly 5 `client = get_client()` sites. But `:214`, `:796`, `:848`, plus `92.1-03-PLAN.md:123-157` still say 15 migrate / 3 KEEP. This will produce false requirements, false docs, and possibly failed verification.
  **Fix:** choose one. I recommend 13 migrate / 5 KEEP, then update READER-01, done text, commit message, OPEN_ISSUES text, CLAUDE entry, and SUMMARY template.

- **CRITICAL — Plan 92.1-02 proposes a likely invalid NiceGUI fix.**
  `92.1-02-PLAN.md:136`, `:217`, `:297`, and `:336-350` refer to `context.client.run_async(...)` or rebinding with `with _dialog_owner_client:`. In installed NiceGUI, `Client.__enter__` only enters the slot stack (`venv/Lib/site-packages/nicegui/client.py:140`); `app.storage.user` is controlled by `storage.request_contextvar` and raises at `venv/Lib/site-packages/nicegui/storage.py:109-113`.
  **Fix:** diagnose `nicegui.storage.request_contextvar.get()` directly. Do not rely on slot-stack rebinding as the storage fix.

- **HIGH — Plan 92.1-02 regression test does not exercise the bug.**
  The proposed test imports `_create_and_add_handler` and mocks `lists_mgr.create_list` / `add_item` (`92.1-02-PLAN.md:301-306`, `:438+`). That bypasses `web/user_lists.py:234`, `web/supabase_client.py:get_user_client`, and `safe_user_get('auth_session')`, which is the actual failure chain.
  **Fix:** add an integration-style test with a fake `lists_mgr.create_list` that calls the real `get_user_client()` under controlled storage context, or use the existing NiceGUI e2e harness.

- **HIGH — captured `auth_session` snapshot is a stale-token/security footgun.**
  Plan 92.1-02 suggests capturing `_captured_auth_session_at_dialog_entry` and possibly adding `auth_session_override` to `get_user_client()` (`92.1-02-PLAN.md:318-358`, threat model at `:552`). A dialog can outlive logout, token refresh, or tab/session changes.
  **Fix:** avoid token snapshot override. If absolutely necessary, bind to a session UUID/user ID and re-check current auth state at click time.

- **HIGH — Plan 92.1-03 asks for a commit SHA before the commit exists.**
  `92.1-03-PLAN.md:98` says to fill the `docs(92.1-03)` SHA in the summary before writing/committing it. That SHA cannot exist yet.
  **Fix:** use "this commit" for Plan 03, or explicitly require a two-step commit/amend workflow.

- **MEDIUM — AST scanner is useful but not complete.**
  `BANNED_TABLES` is only `{user_lists, list_items, recent_items, projects}` (`92.1-01-PLAN.md:349`). It misses bypasses like module-level aliases, `table = client.table`, wrapper helpers, and partial-auth tables (`corrections`, `comments`).
  **Fix:** add seed traps for helper/wrapper/module-alias patterns, or add a manifest-based function scanner for named reader functions.

- **MEDIUM — some migration rationales overclaim.**
  `get_feed_items` currently filters corrections to `status='approved'` and comments to `is_public=True` in `web/supabase_client.py:1609` and `:1635`, so migrating its top-level client does not make private comments/pending corrections appear. `get_discovery_responses` is described as "Likely public" in `92.1-01-PLAN.md:177`, which is not good enough for P0.
  **Fix:** either keep public-only readers anonymous, or verify live RLS and add tests for the claimed private branches.

- **MEDIUM — Symptom 3 hypotheses miss the most likely NiceGUI mechanism.**
  The likely failure is not "dialog slot stack" alone. NiceGUI event listeners capture the request at registration (`venv/Lib/site-packages/nicegui/element.py:390-398`); if search result cards/dialog buttons are registered while `request_contextvar` is `None`, later storage reads fail.
  **Fix:** instrument request capture, not only `context.client.id` and slot depth.

- **MEDIUM — OPEN_ISSUES may be closed too early.**
  `92.1-03-PLAN.md:21`, `:59`, and `:236` mark the Phase 90 regression fixed before SWEEP-05 smoke run 2. For a P0/P1 production regression, "fixed in code, pending smoke verification" is more accurate until R0 passes.
  **Fix:** close the issue only after smoke run 2 PASS, or use an explicit "Fixed in code; verification pending" status.

- **LOW — planned test skeleton has small quality defects.**
  `92.1-01-PLAN.md:543` imports unused `call`, which fails Ruff F401. The negative control says it asserts `get_client` was called (`:292`) but the skeleton only checks `_apply_user_auth_to_client.call_count == 0` (`:633`).
  **Fix:** remove `call`; make `get_client` a `MagicMock(return_value=anon_sentinel)` and assert it was called.

- **LOW — Plan 92.1-03 test delta is wrong.**
  It says Plan 92.1-02 adds `+2` tests (`92.1-03-PLAN.md:202`), but Plan 92.1-02 specifies 3 tests.
  **Fix:** update the summary template.

### Suggestions

- Add a Plan 92.1-01 behavioral test for `get_corrections(author_id=current_user, status='pending')` and `get_comments(author_id=current_user, is_public=False)`.
- During Symptom 3 diagnosis, log `storage.request_contextvar.get() is None`, `context.client.id`, `Slot.get_stack()` depth, and whether the button EventListener captured a request.
- Test search-results create-list both with and without selecting a project, because `project_id` triggers `_get_cached_data()` in `web/user_lists.py:230`.
- Treat `docs/guides/SUPABASE_GUIDE.md` as useful but verify actual live policies or at least reconcile with `scripts/fix_rls_policies.sql`, which contains additional policy detail for `list_items`, `recent_items`, and `projects`.
- Before execution, fix the local Python/venv invocation path if needed; all plan verification assumes `python -m pytest` works.

### Risk Assessment

Overall risk is **HIGH** until Plan 92.1-02 is corrected. Plan 92.1-01's core reader migration is sound after the 13/5 reconciliation, and Plan 92.1-03 is mostly ledger work. The dangerous part is Symptom 3: the current plan may ship a refactor and a green unit test without actually fixing `app.storage.user` request-context loss. For a P0 regression, that is not acceptable without either a correct request-context fix or a mandatory live browser verification before marking the issue fixed.

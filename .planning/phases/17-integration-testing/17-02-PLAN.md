  <action>
Create `tests/test_responsa_regression.py` with regression tests verifying all existing search modes are unaffected by Responsa additions.

Reuse the `_make_search_engine()` helper pattern from `tests/test_responsa_integration.py`.

**Class 1: TestExistingModesUnchanged** (~6 tests, parametrized)
Use `@pytest.mark.parametrize` to test each non-Responsa mode:
- `exact` with query `"test"`
- `variants` with query `"test"` (mock `var_mgr.get_variants` to return `["test", "tst"]`)
- `fuzzy` with query `"test"`
- `Regex` with query `"test.*"`
- `Shelfmark` with query `"T-S 12.1"` (this mode is metadata-only, test via `parse_query_syntax`)
- `Title` with query `"Genesis"` (also metadata-only, test via `parse_query_syntax`)

For each mode, verify:
1. `build_tantivy_query(terms, mode)` produces a non-empty, valid query string (for search modes that use Tantivy: exact, variants, fuzzy)
2. `build_regex_pattern(terms, mode, gap)` produces a valid compiled regex (for search modes that use regex)
3. Calling with `responsa_components=None` (default) produces the SAME output as before Responsa was added -- this is the key regression test

**How to test "same as before":** Since we can't compare to a pre-Responsa snapshot, test that:
- `build_tantivy_query(['test'], 'exact')` produces query containing `"test"^5` (exact term boosted)
- `build_tantivy_query(['test'], 'variants')` with mock variants `['test', 'tst']` contains both terms
- `build_tantivy_query(['test'], 'fuzzy')` produces query containing `"test"~1` or similar fuzzy syntax
- `build_regex_pattern(['test'], 'exact', 0)` compiles without error and matches "test"
- `build_regex_pattern(['test'], 'exact', 3)` allows up to 3 intervening words between terms

**Class 2: TestParseQuerySyntaxRegression** (~4 tests)
Verify prefix shortcuts still work when NOT in Responsa mode (defense against accidentally breaking them):
- `#T-S 12.1` with `responsa_mode=False` -> mode='Shelfmark', clean='T-S 12.1'
- `?test` with `responsa_mode=False` -> mode='variants' (or similar), clean='test'
- `=test` with `responsa_mode=False` -> mode='exact' (literal match), clean='test'
- `/test.*/` with `responsa_mode=False` -> mode='Regex', clean='test.*' (or original form)
- `$Genesis` with `responsa_mode=False` -> mode='Title', clean='Genesis'

For each, call `engine.parse_query_syntax(query, responsa_mode=False)` and verify the expected (mode, clean) tuple.

Test BEHAVIOR, not implementation details (per research Pitfall 4). Don't assert exact regex strings -- assert that patterns match expected text and don't match non-matching text.

Target: ~8-10 tests.

Each test uses `time.perf_counter()` around `execute_search()` calls.

2. **Responsa with prefix expansion:** `"#shalom"` (Hebrew: `#\u05e9\u05dc\u05d5\u05dd`) with variants=False, ja=False. The ~25 prefix forms should still be fast. Assert < 5 seconds.

3. **Responsa with variants + JA:** `"#shalom"` with variants=True, ja=True, flex_spacing=False. This produces the most term expansion. Assert < 10 seconds for automated test (5s is the manual UAT threshold, use generous 10s for automated per research recommendation).

4. **Two-component query with gap:** `"#\u05e9\u05dc\u05d5\u05dd [3] \u05e2\u05d5\u05dc\u05dd"` (shalom [3] olam) with variants=True, ja=False. Assert < 10 seconds.

5. **Non-Responsa baseline for comparison:** Same `"shalom"` query with plain exact mode (no Responsa). Assert < 3 seconds. This provides a baseline to detect if Responsa adds unreasonable overhead.

For each test, print the elapsed time and result count (using `print()` or `pytest` capsys) so the developer can see actual timings when running manually. Use format: `f"Query '{query}': {elapsed:.2f}s, {len(results)} results"`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| highlight_pattern → snippet_html / snippet_plain / _match_line | A regex pattern string (originating from the engine's `highlight_pattern` on a result dict) is compiled and applied to corpus text for highlighting/centering. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-106-07 | Denial of Service (ReDoS via highlight pattern) | `_match_line` / `htmlify` compiling `pattern` | accept | The `pattern` is the engine-produced `highlight_pattern` for an already-returned result, NOT untrusted external input — it is the same regex the engine itself already compiled and ran to PRODUCE the result. Re-compiling it here adds no new attack surface beyond what the engine already executed. All three functions wrap `re.compile` in `try/except re.error` and degrade to "no highlight"/-1 on a bad pattern, so a malformed pattern cannot raise. The text being scanned is a bounded display fragment (snippet windows of max_lines/max_chars), not the whole corpus. |
| T-106-08 | Information disclosure / XSS via snippet HTML | `htmlify` building HTML for the card view | mitigate | `htmlify` calls `html.escape(text)` on the corpus text AFTER substituting internal MARK sentinels and BEFORE replacing the sentinels with the fixed `<b style=...>` tag — so corpus text containing `<`/`>`/`&` is escaped and cannot inject markup; only the module's own fixed-string tags survive. Verified by TestSnippet::test_html_escapes (`&lt;` present). The Phase 107+ UI renders this in a desktop QLabel / web component that the consuming phase is responsible for treating as the escaped HTML it is. |

No network/auth/crypto/persistence surface in this plan — those STRIDE categories N/A for pure text helpers.
</threat_model>

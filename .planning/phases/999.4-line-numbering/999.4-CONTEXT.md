# Phase 999.4: Line numbering - Context

**Gathered:** 2026-05-15
**Status:** Ready for planning (backlog — promote with /gsd-review-backlog when ready)

<domain>
## Phase Boundary

Display line numbers alongside transcription text so researchers can read,
cite, and cross-reference specific lines. Cosmetic / read-only feature: no
new search behavior, no deep-linking, no interactive line actions in this
phase. Both apps (web + desktop) gain the feature.

In scope:
- Web: Browse page main viewer, PGP transcription dialog / version views,
  Quick View on search results.
- Desktop: Browse tab transcription pane, ResultDialog transcription pane.

Out of scope (see Deferred Ideas):
- Web search-results inline accordion preview.
- Parallels / Composition results.
- Any interaction beyond visual display.

</domain>

<decisions>
## Implementation Decisions

### Scope — Where line numbers appear
- **D-01:** Web targets are Browse page (`web/pages/browse.py:4206 render_text_content`), PGP transcription dialog / version views (same render path, populated by `handle_version_change` at `browse.py:4227`), and Quick View on search results (`web/pages/search_results.py` + `web/pages/search_state.py`).
- **D-02:** Desktop targets are the Browse tab transcription pane (in `genizah_app.py`) and `desktop/result_dialog.py` ResultDialog transcription pane.
- **D-03:** Web search-results inline-accordion text (`web/pages/search_results.py:688 _render_full_text`) is **explicitly excluded** from this phase — see Deferred Ideas.

### Visual presentation
- **D-04:** Fixed gutter on the leading (right) edge of the text — RTL-aware. The gutter is a separate column so line numbers are **not** captured when the user selects + copies the transcription body.
- **D-05:** Gutter styling must match the transcription block's `line-height` (currently `2.2` on browse, `2` on search-results dialogs) so each number sits opposite its line. Number color/size is Claude's discretion (subdued grey, smaller than body text).
- **D-06:** On desktop, mirror the gutter visually using whatever Qt mechanism keeps the numbers selection-safe (e.g. a sibling `QTextEdit` / `QListWidget` / custom left margin) — implementation choice is Claude's discretion, but copy-from-transcription must not include the numbers.

### Visibility default & toggle
- **D-07:** Line numbers are **on by default**.
- **D-08:** A small show/hide toggle lives in the transcription header next to the existing version selector / highlight-terms controls. Pattern mirrors the existing `state.highlight_terms` toggle at `web/pages/browse.py:4212-4214`.
- **D-09:** The setting **persists per user across sessions** via `web/safe_storage.py` (post-Phase 87 chokepoint). Key naming is Claude's discretion (e.g. `ui.show_line_numbers`). On desktop, persist via the existing QSettings / preferences mechanism used for other view toggles.

### Numbering scheme
- **D-10:** A "line" is **one logical newline** in the source text (i.e. `text.split('\n')`). This matches existing Responsa `L<N>:word` search semantics in `genizah_core.py:4976-4994` (`line_constraints`) and `genizah_core.py:7679-7691` (parser). Blank lines DO get a number — preserving 1-to-1 alignment with `L<N>:` queries.
- **D-11:** Numbers are **1-based** and **restart at 1 for each folio/page displayed**. Browse renders one page (recto or verso) at a time; L<N>: search also operates on a single displayed page. No cumulative numbering across folios in this phase.

### Click / interaction
- **D-12:** Line numbers are **display only**. No click handlers, no deep links, no inserting `L<N>:` into the search box. (Each of those is a candidate for a follow-up backlog item — see Deferred Ideas.)

### Claude's Discretion
- Exact gutter width, font-size, and color (must be subdued and not steal focus from the Hebrew text).
- Whether to implement web numbers via a CSS `counter-reset` + `::before` pseudo-element, a parallel column of `<span>`s, or a flex layout — provided the copy-paste invariant in D-04 holds.
- Toggle icon (Material `format_list_numbered` is a natural fit but not mandatory) and its tooltip wording (translated via `tr()`).
- Whether the desktop and web implementations share any code (probably not — Qt vs HTML diverge here).

</decisions>

## Existing Code Insights

### Reusable Assets
- `tr()` translation helper (`web/translations.py`) — use for toggle label & tooltip.
- `web/safe_storage.py` `safe_user_get` / `safe_user_set` — per-user persistence chokepoint (Phase 87 enforced).

### Established Patterns
- Transcription text is rendered with `white-space: pre-wrap` and Hebrew-aware fonts in a `direction: rtl` block. Adding a gutter must respect RTL: visually the numbers should sit on the **right** side of the text block (the "leading" side for RTL).
- Per-user UI prefs are written through `web/safe_storage.py` only. No raw `app.storage.user[...]` access — Phase 87 lint enforces this.
- Desktop already has Qt-style preference toggles via the existing settings infrastructure — line-number visibility joins those.

### Integration Points
- Web: hook into the version-selector row that already exists in `browse.py` and the dialog header rows in PGP / Quick-View paths.
- Desktop: extend `desktop/result_dialog.py` and the browse tab in `genizah_app.py`; coordinate with the existing toolbar/options area each surface already has.

<specifics>
## Specific Ideas

- The Responsa search syntax `L<N>:word` (e.g. `L3:שלום`) already exists in the engine but is invisible in the UI today. Showing line numbers makes that feature *learnable* — users can now see what `L3:` refers to before they type it. This is a strong reason to keep numbering semantics aligned with `text.split('\n')` per D-10.

</specifics>

<deferred>
## Deferred Ideas

These came up as natural extensions but belong in their own future phases. Captured here so they aren't lost when this one ships:

- **Line numbers in search-results inline accordion** — the short preview snippets shown under each hit on `/search`. Excluded for now because previews are intentionally compact and numbering small snippets may add visual noise. Revisit if users ask.
- **Line numbers in Parallels / Composition results** — same reasoning; revisit per user feedback.
- **Click a line number to deep-link / scroll** — generate a shareable URL like `/browse?sys_id=X&p=Y&line=3` and have the page scroll to & highlight that line on load. Useful for citation; deferred to keep this phase small.
- **Click a line number to insert `L<N>:` into the search box** — bridges the existing Responsa per-line syntax. Useful for power users but introduces cross-view state; better as its own backlog item once the basic gutter is shipped.
- **Continuous (cross-folio) numbering** — only useful for citing across pages and isn't how `L<N>:` currently works. Skipped.

</deferred>

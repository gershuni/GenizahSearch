# Phase 999.4 Plan 02 — DESKTOP line-number gutter

## Outcome

Desktop transcription panes (`self.browse_text` on the Browse tab,
`self.text_ms` on the ResultDialog) now render a line-number gutter as a
sibling `QWidget` next to the body widget. Numbers correspond 1:1 with
`text.split('\n')` per D-10 (LINE-NUM-09 shared with Plan 01) and align
with the actual rendered y of each source line via `body.cursorRect(cursor)`
queries. The gutter survives Ctrl+wheel zoom of the body text. Toggle
button (`# Lines`, `checkable=True`, tooltip `tr('Toggle line numbers')`)
persists across desktop app restarts via `load_app_config` /
`save_app_config({'show_line_numbers': bool})`. Default ON per D-07.

D-04 copy-paste invariant achieved trivially by design: `LineNumberArea`
is a SIBLING `QWidget`, NOT part of the body's `QTextDocument`. Qt's
text cursor cannot extend into a sibling widget, so `body.toPlainText()`
and any mouse-drag-selection inside the body contain zero line-number
digits — verified structurally by `test_clipboard_isolation_invariant`.

## Smoke-check revision history (4 rounds with Hillel)

**Round 1 (initial smoke after commits `dbd3b96f..b3a491a9`).** Hillel
reported the desktop gutter painted only "1" on a multi-line manuscript.
Root cause: the painter iterated `QTextBlock`s. When `genizah_app.py`
renders transcription as `<p>line1<br>line2<br>line3</p>` (a single
`<p>` with `<br>` separators), the entire content is ONE QTextBlock —
so `doc.firstBlock()` returned that one block, "1" was painted at its
top, `block.next()` was invalid, loop exited. Fix at `346546ad`:
switched to walking visual `QTextLine`s within each block via
`block.layout().lineAt(i)`. Numbers appeared for every line.

**Round 2 (after `346546ad`).** Hillel reported:
- Numbers visibly drifting below their text lines.
- View All numbered the "Image: N (FL: ...)" page headers too.
- Per-page restart needed for View All (web parity).
- Toolbar button should move to next to Find input.

Fixed at `cbb4a3fb`:
- Switched to `body.cursorRect(cursor)` for accurate y per visual line.
- New `pages=list[str]` keyword for `apply_line_numbered_text`. After
  setHtml, walks QTextBlocks and tags each with `setUserState(page_idx)`
  for matched content blocks or `setUserState(-1)` for separators.
  Painter walks userState marks, resets counter on page tag change,
  skips separators.
- Wired into `browse_load_all` (Full Manuscript) and `_browse_rd_render`
  (Reading Desk) via `pages=raw_text_parts`.
- Moved `# Lines` toolbar button from `community_bar` to `browse_find_row`.

**Round 3 (after `cbb4a3fb`).** Hillel reported:
- Numbers still drifting upward (numbers at the top of each line space
  rather than aligned with body text).
- View All gutter completely empty.

Diagnoses:
1. `AlignTop` was anchoring the small 10pt gutter glyph to the top of
   each line rect (which includes CSS line-spacing leading). Body text
   glyphs sit visually centered in the same rect → numbers appeared
   offset upward.
2. Strict equality `block.text() == page_source` was failing because
   Qt's HTML renderer inserts Unicode bidi control marks (LRM/RLM,
   LRE/RLE/PDF/LRO/RLO, LRI/RLI/FSI/PDI) around `<div dir='rtl'>`
   content. The bidi-augmented block text never matched the raw
   source — so all blocks were marked `-1` and the gutter painted
   nothing.

Fixed at `0c164687`:
- Painter `AlignTop` → `AlignVCenter` so the gutter glyph centers
  vertically within the line rect (matching body text's visual center).
- `_normalize_block_text` now strips all bidi control marks AND trims
  whitespace per `\n`-separated line.
- `_mark_blocks_for_pages` now does three matching passes:
  exact-equality-against-next-unmatched-page, exact-equality-against-
  any-unmatched-page (defensive), substring-fallback. Each transcription
  page is long enough that cross-page substring collisions are
  extremely unlikely.

**Round 4 (after `0c164687`).** Hillel reported:
- (P0) Word-wrap was assigning a separate number to each wrapped
  continuation. A source line that wrapped to 2 visual rows got 2
  numbers instead of 1.
- Reading Desk per-PAGE restart was needed (not just per-fragment).
- Hebrew UI: `# Lines` button should be on the right edge of the find
  row (above the gutter) instead of the left.

Fixed at `05a5740b`:
- Painter walks SOURCE-LINE segments (`block.text().split(' ')`)
  not visual `QTextLayout` lines. Each `<br>`-separated source line
  gets ONE `cursorRect` query at its first-character position;
  wrapped visual continuations share that y because they're never
  re-queried.
- `_browse_rd_render` V0.8 fallback path now emits one `<div>` + one
  `raw_text_parts` entry per page (with a visible "page N" separator
  between pages within a fragment). PGP edition/translation path
  unchanged (no internal page concept).
- `# Lines` button now inserted at index 0 of the find-row layout
  when `CURRENT_LANG == 'he'` (RTL mirroring puts it on the rightmost
  edge, above the gutter). LTR UI keeps the toggle on the right edge
  of the find row, unchanged from prior round.

Hillel approved after `05a5740b`.

## Deliberate scope divergence from web Plan 01

**Continuous numbering in desktop View All vs. per-page restart in web
View All — IDENTICAL behavior across pillars after Round 2.** The
initial executor implementation went with continuous numbering in
desktop View All; smoke-check Round 2 corrected this to per-page
restart matching the web pillar via the `pages=` keyword.

**RTL button placement is RTL-specific on desktop.** Web Plan 01's
toggle is always in the same place per surface (CSS/HTML flow handles
RTL automatically). Desktop's `# Lines` button was moved by a conditional
on `CURRENT_LANG == 'he'` because QHBoxLayout's RTL mirroring put the
last-added widget on the visual left otherwise.

### Plan 92.2-01: Instrumentation-only

#### Strengths
*   **Empirical Baseline:** Committing the JSON artifact guarantees that the "before" state is preserved in source control, preventing historical drift.
*   **Clean Separation:** Emitting instrumentation via JSON logs keeps the telemetry isolated from the business logic layer.
*   **AST Negative-Control:** Excellent foresight to ensure instrumentation doesn't accidentally violate Phase 87 storage chokepoints.

#### Concerns
*   **MEDIUM - Test State Bleed:** The plan suggests wrapping logic in `if _INSTRUMENTATION_ENABLED:` and adding tests. If tests manually mutate `web.supabase_client._INSTRUMENTATION_ENABLED` without a robust teardown (or `mock.patch`), parallel test runners (`pytest -n auto`) will experience race conditions and flaky failures.
*   **LOW - Ambiguous Multi-Sample Aggregation:** Task 3 asks Hillel to collect "3 warm samples", but the JSON schema only validates a single sample in the array (`sample_n: 1`). The plan doesn't specify whether Plan 92.2-02's Task 0 decision tree checks the mean, the median, or just `sample[0]`.

#### Suggestions
*   **Test Isolation:** Explicitly mandate the use of `unittest.mock.patch('web.supabase_client._INSTRUMENTATION_ENABLED', True)` in the test requirements, rather than manual mutation.
*   **Clarify Sample Aggregation:** Update the Baseline JSON schema to explicitly expect 3 samples in the `samples` array. Update Task 0 in Plan 92.2-02 to state: *"Proceed if the **median** `total_wall_clock_ms` of the warm samples is within ±20%."*

### Plan 92.2-02: Fix + Re-measure

#### Strengths
*   **Task-Scoped Memoization:** Using `asyncio.current_task()` as the cache key is a brilliant, NiceGUI-compatible way to achieve request-scoped caching without explicitly modifying the ASGI middleware or `nicegui.context`.
*   **Fanout Eradication:** Shifting the `N` per-list queries into a single `get_list_item_counts` RPC call fundamentally resolves the structural bottleneck.
*   **Graceful Degradation:** The NLI cache retry logic with explicit backoffs is a robust solution to Windows file-locking quirks (`WinError 5`).

#### Concerns

*   **HIGH - The Anonymous / Failure Fallback Bug (Task 6):** As identified, the plan states: `counts = {}` upon RPC failure or for anonymous users. In `_render_list_item`, if `counts` is an empty dictionary, `counts.get(list_id, 0)` evaluates to `0`. It will **never** trigger the legacy fallback `lists_mgr._get_list_item_count(list_id)`. Anonymous users will suddenly see `0` items for all public lists.
*   **HIGH - Redundant & Insecure-Looking RPC Design (Task 3):** The RPC takes `p_user_id` as an argument while running as `SECURITY INVOKER`. If `public.user_lists` has RLS enabled (which it must, per project invariants), the `SECURITY INVOKER` context already enforces that the query only sees the caller's lists. Taking `p_user_id` is an anti-pattern. If an attacker passes another user's UUID, the query yields 0 rows (because RLS blocks the inner select), but passing auth context from the client to the DB when the DB already possesses `auth.uid()` violates zero-trust principles and triggers false-positive security audits.
*   **MEDIUM - Order of Operations & Redundant Reads (Task 1):** The memo logic block calls `_safe_get_uuid('_session_uuid')`. `get_user_client()` already interacts with auth states and session data earlier in its execution to check for token expiration. Fetching the UUID again is redundant I/O and creates a minor risk of data drift if the token refresh logic mutated the session state right before the memo block.
*   **MEDIUM - Missing `service_role` Grant (Task 3):** The plan grants execute to `authenticated`. If any background worker, cron job, or admin script uses the `service_role` key to bypass RLS and fetch list counts, it will crash with a permission denied error.
*   **LOW - Rollback Strategy for Migrations (Task 3 & 4):** Because the project does not use a tracked migration system (like Prisma or Alembic), executing `CREATE OR REPLACE FUNCTION` directly leaves no breadcrumbs for reverting if the RPC causes CPU spikes on the database.

#### Suggestions

*   **Fix the Fallback Logic (Task 6):** The failure handler and anonymous paths MUST set `counts = None`.
    ```python
    # web/pages/lists.py
    counts: Optional[Dict[int, int]] = None  # Initialize to None
    try:
        if GlobalAuthState.is_logged_in():
            user_id = GlobalAuthState.get_user_id()
            if user_id:
                counts = get_list_item_counts(user_id)
    except Exception as _e:
        logger.warning(f"get_list_item_counts failed; falling back: {_e}")
        counts = None # Ensure it stays None to trigger the legacy fallback
    ```
*   **Refactor RPC to use `auth.uid()` (Task 3):** Drop the `p_user_id` parameter entirely. Rely on the `SECURITY INVOKER` context.
    ```sql
    CREATE OR REPLACE FUNCTION public.get_list_item_counts_for_user()
    RETURNS TABLE(list_id bigint, item_count bigint)
    LANGUAGE sql
    SECURITY INVOKER
    AS $$
        SELECT li.list_id, count(*)::bigint AS item_count
        FROM public.list_items li
        WHERE EXISTS (
            SELECT 1 FROM public.user_lists ul
            WHERE ul.id = li.list_id AND ul.user_id = auth.uid()
        )
        GROUP BY li.list_id;
    $$;

    GRANT EXECUTE ON FUNCTION public.get_list_item_counts_for_user() TO authenticated;
    GRANT EXECUTE ON FUNCTION public.get_list_item_counts_for_user() TO service_role;
    ```
*   **Optimize Memo Initialization (Task 1):** Reuse the session identifiers already present in `get_user_client()` rather than invoking `_safe_get_uuid` a second time.
*   **Include Rollback in Migration File (Task 3):** Append the DROP statement as a comment at the bottom of the SQL file so developers know exactly how to revert it in the Supabase Dashboard.
    ```sql
    -- ROLLBACK INSTRUCTIONS:
    -- DROP FUNCTION IF EXISTS public.get_list_item_counts_for_user();
    ```
*   **Refine the HARD GATE criteria (Task 9):** Clarify the verification metric. Specify that the **median** of the 3 warm samples must be `≤ 5000ms`. A single anomalous GC pause or network spike shouldn't necessarily fail the gate if the overall trend is sound.

## Codex Review

### Overall Phase

**Summary**
The direction is sound: measure first, then reduce client builds and Supabase fanout. But as written, the plans can still produce a misleading baseline, miss the selected-list path Hillel complained about, and introduce a visible anonymous/RPC-failure count regression. I would not execute 92.2-02 unchanged after 92.2-01.

**Strengths**
- Separating instrumentation from fix is the right control discipline.
- `asyncio.current_task()` is a better candidate than `nicegui.context.client` for avoiding per-tab caching.
- The RPC avoids PostgREST's row cap problem.
- The plans preserve the Phase 87 storage chokepoint in the proposed memo block.

**Concerns**
- **HIGH:** The phase gate says server-side wall clock "request received → response body flushed," but Plan 92.2-01 instruments only `render_lists_sidebar()` in `web/pages/lists.py:362`. It excludes `lists_page_route()`, `create_layout()`, `render_list_content()`, and actual response flush.
- **HIGH:** The fix plan mostly optimizes sidebar render, but selected-list content still repeatedly calls `state.lists_mgr` and re-fetches data/items in `web/pages/lists.py:397` and `web/pages/lists.py:440`. Hillel reported both `/lists` load and clicking a list as slow.
- **HIGH:** The plan lacks a defined multi-sample gate. "3 warm samples" is collected, but the decision tree and schema effectively read sample 1.
- **MEDIUM:** The memo's safety depends on NiceGUI creating a distinct asyncio task per HTTP/page/event callback. That is plausible, not proven by the plan.
- **MEDIUM:** The RPC security claim is mostly right for `SECURITY INVOKER` if RLS is enabled, but the function still trusts `p_user_id` unnecessarily and does not revoke default `PUBLIC` execute.

**Suggestions**
- Add a route-level timing wrapper or ASGI middleware for `/lists` to satisfy D-VER-02, not just component-level timing.
- Add two separate samples: `warm_lists_initial` and `warm_selected_list`, with the selected sample clicking a real list.
- Define gate as either "all 3 warm samples ≤5000ms" or "median ≤5000ms and max reported as residual risk." Do not leave it implicit.
- Add a NiceGUI runtime probe logging `id(asyncio.current_task())` for initial page render, refresh button, `asyncio.create_task(async_refresh_ui())`, and a list-selection callback.

**Risk Assessment: HIGH**
The planned optimization is likely useful, but current measurement and fix scope can miss the actual user-visible regression.

### Plan 92.2-01

**Summary**
Good forensic intent, but the proposed instrumentation is too narrow and slightly self-distorting. It will be useful only if it is changed to measure the whole `/lists` server path and isolate counters per request/task.

**Strengths**
- Env-gated instrumentation keeps production dormant by default.
- Permanent JSON artifact is valuable for future regression archaeology.
- Query/client-build counters are the right first-order signals.
- The corrected formula is included in the artifact.

**Concerns**
- **HIGH:** Task 2's snippet calls `create_project_tree(lists_mgr=state.lists_mgr, ...)` and then, in `finally`, calls `_lm = state.lists_mgr` again. Because `state.lists_mgr` is a factory property in `web/state.py:28`, this creates a new manager and then `_lm.data` does extra Supabase work after `_t_render_end`. That work is excluded from `total_wall_clock_ms` even though it happens before the function returns.
- **HIGH:** Module-level `_inst_query_count` and `_inst_query_latencies_ms` can be contaminated by concurrent requests or background Supabase calls while instrumentation is enabled. A real Hillel environment is exactly where this matters.
- **HIGH:** Instrumenting only specific reader functions misses any unlisted Supabase query in layout or selected-list content, so `observed_minus_predicted` can be falsely reassuring.
- **MEDIUM:** p50/p95 behavior is undefined for small query counts. Some percentile helpers fail or give surprising interpolation with `n < 2`.
- **LOW:** The artifact records a real email address. If the repo is public, consider whether that is acceptable.

**Suggestions**
- Capture once before render and reuse:
  ```python
  lists_mgr = state.lists_mgr
  if _INSTRUMENTATION_ENABLED:
      _inst_reset()
      _t_render_start = time.perf_counter()

  try:
      create_project_tree(lists_mgr=lists_mgr, ...)
  finally:
      data = lists_mgr.data if lists_mgr is not None else {}
  ```
- Prefer request/task-local instrumentation via `contextvars.ContextVar`, not module globals.
- Put route-level timing around `web/main.py:1171` or add ASGI send-wrapper timing for `/lists`.
- Validate every sample in `92.2-01-BASELINE.json`, not just `samples[0]`.

**Risk Assessment: MEDIUM-HIGH**
The instrumentation can prove a regression exists, but as written it can undercount wall time and misattribute fanout.

### Plan 92.2-02

**Summary**
The mitigation stack is directionally right, but the plan has three blockers: task-scope memo assumptions are not empirically verified, selected-list content remains under-optimized, and `counts={}` breaks the promised fallback path.

**Strengths**
- Memo lookup after proactive refresh is the correct ordering.
- Keying by `(_session_uuid, access_token)` prevents reuse after token rotation.
- Batching counts through RPC is better than Python-side `.in_(...)` aggregation.
- Keeping `data=None` defaults preserves non-hot-path callers.
- NLI lock + replace retry addresses the likely Windows race class.

**Concerns**
- **HIGH:** `counts` fallback is wrong. Task 6 initializes `counts = {}` and passes it to `create_project_tree()`. If anonymous or RPC fails, `_render_list_item` will use `counts.get(..., 0)` and show every count as `0`, never reaching legacy `_get_list_item_count()`.
- **HIGH:** `render_list_content()` is not included in the data/count threading plan. It still does `state.lists_mgr.data`, `state.lists_mgr.get_list_display_color()`, and `state.lists_mgr.get_items_in_list_sync()` via fresh factory managers.
- **HIGH:** `async_refresh_ui()` in `web/pages/lists.py:130` calls `state.lists_mgr.refresh_data()` and discards the fetched data, then renders again. That adds avoidable warm-path queries.
- **MEDIUM:** Use `get_persisted_session_uuid()` for the memo key, not `safe_user_get('_session_uuid')`, so malformed/poisoned UUIDs are not accepted.
- **MEDIUM:** `WeakKeyDictionary` is not thread-safe. Most NiceGUI callbacks are same-loop cooperative, but this repo has `run.io_bound(...)` paths that call list readers, e.g. `web/pages/puzzle.py:2844`. Those will bypass memo because no event-loop task exists, which is probably correct, but should be explicitly tested/documented.
- **MEDIUM:** PostgreSQL functions are commonly executable by `PUBLIC` by default unless revoked. `GRANT EXECUTE TO authenticated` may not mean "authenticated only."
- **MEDIUM:** The RPC should not accept an arbitrary `p_user_id` without also checking `p_user_id = auth.uid()`.
- **LOW:** The NLI concurrency test design with `threading.Barrier(2)` can deadlock if the barrier is inside the locked region.

**Suggestions**
- Fix counts semantics:
  ```python
  counts: Optional[Dict[int, int]] = None
  if GlobalAuthState.is_logged_in():
      counts = get_list_item_counts(user_id)  # return None on RPC failure
  ```
  Then `_render_list_item` should fall back only when `counts is None`.
- Refactor `render_list_content(data=None, lists_mgr=None)` and call it from `refresh_ui()` with the same captured manager/data used by sidebar.
- Change memo UUID read:
  ```python
  from web.safe_storage import get_persisted_session_uuid
  session_uuid = get_persisted_session_uuid()
  ```
- Harden SQL:
  ```sql
  REVOKE ALL ON FUNCTION public.get_list_item_counts_for_user(uuid) FROM PUBLIC, anon;
  GRANT EXECUTE ON FUNCTION public.get_list_item_counts_for_user(uuid) TO authenticated, service_role;

  ... WHERE p_user_id = auth.uid()
      AND EXISTS (...)
  ```
  Better: remove the argument and use `auth.uid()` inside the function.
- Add rollback text to the migration:
  ```sql
  -- ROLLBACK: DROP FUNCTION IF EXISTS public.get_list_item_counts_for_user(uuid);
  ```
- Add an index check/migration if absent:
  ```sql
  CREATE INDEX IF NOT EXISTS idx_list_items_list_id ON public.list_items(list_id);
  ```

**Risk Assessment: HIGH until revised, MEDIUM after fixes**
The memo and RPC are likely to help, but the current plan can pass the sidebar case while leaving selected-list latency and count correctness broken.

## Consensus Summary

Both Gemini (overall MEDIUM, escalating to HIGH on specific items) and Codex (overall HIGH) agree the plan **should not execute unchanged**. They converge on four blocking issues and diverge on instrumentation completeness, which only Codex raises.

### Agreed Strengths (2+ reviewers)
- **Two-wave instrumentation-then-fix discipline** is the right control.
- **`asyncio.current_task()` keyed `WeakKeyDictionary`** is the correct NiceGUI-compatible scope for a per-request memo (avoids Phase 90 D-12 reopen).
- **RPC over Python `.in_(...)` aggregation** is the right call (closes PostgREST row-cap silent undercount).
- **NLI cache `threading.Lock` + retry-on-`os.replace`** is a robust shape for the `WinError 5` race.
- **`data=None` default on `get_lists_by_project` / `get_list_display_color`** correctly preserves non-hot-path callers.
- **Phase 87 chokepoint compliance** preserved by the memo block.

### Agreed Concerns (2+ reviewers — highest priority — MUST-FIX before execution)

**MUST-FIX 1 (HIGH, both reviewers): `counts = {}` fallback bug in Task 6 silently regresses anonymous + RPC-failure paths to "0 items everywhere."**
- Location: `web/pages/lists.py:render_lists_sidebar` (plan Task 6 snippet)
- Symptom: `_render_list_item` calls `counts.get(int(list_id), 0)` — when `counts={}` (anonymous or RPC failure), every list shows 0 items. The advertised legacy fallback `_get_list_item_count(list_id)` is never reached.
- Fix: initialize `counts: Optional[Dict[int, int]] = None`; the failure handler MUST set `counts = None` (not `{}`); `_render_list_item` checks `if counts is None: fall back` else `counts.get(...)`. Update Task 6 acceptance criteria and tests accordingly.

**MUST-FIX 2 (HIGH, both reviewers): RPC `p_user_id` parameter is an anti-pattern AND default `PUBLIC` execute is not revoked.**
- Location: `migrations/add_list_item_counts_rpc.sql` (Task 3) and `web/supabase_client.py:get_list_item_counts` (Task 5)
- Symptom: `SECURITY INVOKER` already exposes `auth.uid()`. Passing `p_user_id` from the client lets a caller request another user's count (returns 0 rows due to RLS, but it's still a zero-trust violation and false-positive trigger for security audits). Separately, PostgreSQL grants `EXECUTE` to `PUBLIC` by default — `GRANT EXECUTE TO authenticated` does NOT restrict to authenticated.
- Fix (both reviewers agree): drop the `p_user_id` argument; use `auth.uid()` inside the function body. Add explicit `REVOKE ALL ... FROM PUBLIC, anon;` before `GRANT EXECUTE`. Codex also wants `service_role` granted; Gemini agrees.
- Cascade: `get_list_item_counts(user_id)` becomes `get_list_item_counts()` (no arg). Update Task 5 helper signature, behavioral tests, and Task 6 call site `get_list_item_counts(user_id)` → `get_list_item_counts()`.

**MUST-FIX 3 (HIGH from Codex; LOW from Gemini): Multi-sample HARD GATE criteria are undefined.**
- Location: Plan 92.2-01 baseline schema + Plan 92.2-02 Task 0 decision tree + Task 9 HARD GATE check.
- Symptom: Procedure collects 3 warm samples but schema validates only `samples[0]`; decision tree reads sample 1; gate verification python one-liner asserts `samples[0]['totals']['total_wall_clock_ms'] <= 5000`. Variance across 3 samples could give an ambiguous PASS or false FAIL on either side.
- Fix: pick ONE explicit aggregation rule (Gemini suggests **median**; Codex offers two alternatives: "all 3 ≤5000" or "median ≤5000 with max reported as residual risk"). Update schema to require `len(samples) == 3`; update validation script to compute aggregate; document the rule in CONTEXT.md D-VER-02 + both plans.

**MUST-FIX 4 (HIGH from Codex; MEDIUM from Gemini implicitly via order-of-operations note): Plan 92.2-01 instrumentation scope undercounts the wall-clock + contaminates the query count.**
- Location: `web/pages/lists.py:render_lists_sidebar` (plan Task 2 snippet, lines 312-383 of 92.2-01-PLAN.md)
- Symptoms:
  1. D-VER-02 defines wall-clock as "request received → response body flushed" but instrumentation wraps only `render_lists_sidebar()` — misses `lists_page_route()`, `create_layout()`, `render_list_content()`, and response-flush time.
  2. Inside the `finally:` block, AFTER `_t_render_end`, the snippet calls `_lm = state.lists_mgr` (factory property — builds a NEW manager) then `_lm.data` (potential Supabase fetch). This work happens before the request returns but is excluded from `total_wall_clock_ms` AND from `snap` (snapshot taken before this re-access). Both metrics are misleading.
  3. Module-level counters can be contaminated by concurrent Supabase calls in background tasks.
- Fix (Codex): add route-level timing at `web/main.py:1171` (ASGI send-wrapper or middleware decorator for `/lists`). Capture `lists_mgr = state.lists_mgr` ONCE before the timed span begins; reuse the same instance for the decomposition AFTER timing. Prefer `contextvars.ContextVar` for per-task counter isolation instead of module globals.

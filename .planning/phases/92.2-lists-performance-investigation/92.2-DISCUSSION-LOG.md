## Fanout-reduction strategy

### Options on the table (before Codex critique)

| Option | Description | Selected |
|--------|-------------|----------|
| Pure refactor only (`.data` threading in /lists hot path) | Cheap, no server-side work, kills 2L of 3L re-fetches. | ✓ (partial) |
| Pure refactor + batched item-count helper (Python aggregation over IN-filter SELECT) | **Recommended by Claude initially.** Adds one helper, no migration. | |
| Pure refactor + batched item-count via Supabase RPC | **Codex's counter-proposal.** Avoids PostgREST row-cap silent undercount. | ✓ |
| Pure refactor + lazy counts on hover | UX regression; defer. | |
| Just lazy counts | UX regression; reject. | |

**Codex Issue 3 (verbatim):** "the proposed refactor misses two real fetch sources: `get_lists_by_project()` re-fetches `.data`, and `web/pages/lists.py` selected-list header calls `state.lists_mgr.data` then `get_list_display_color()` on fresh manager instances. Fix: add `data=None` to `get_lists_by_project()` and `get_list_display_color()`, pass the one `data` object through `project_tree.py`, and capture `lists_mgr = state.lists_mgr` once inside `render_list_content()`."

**Codex Issue 4 (verbatim):** "`select('list_id').in_(...)` transfers every item row and can silently undercount if Supabase/PostgREST row caps apply. Fix: prefer an RPC/security-invoker SQL function returning `{list_id,count}`."

**Resolution:** D-FANOUT-01 captures `lists_mgr` ONCE in render entry, threads `data` through `get_lists_by_project`, `get_list_display_color`, `_render_list_item`. D-FANOUT-02 ships as SQL migration + RPC `get_list_item_counts_for_user(uuid)` with `security invoker` and `grant execute to authenticated`. Lazy counts deferred per D-FANOUT-03. Scope limited to /lists hot path per D-FANOUT-04.

## NLI cache [WinError 5] fix shape

### Options on the table (before Codex critique)

| Option | Description | Selected |
|--------|-------------|----------|
| Retry with exponential backoff (50/100/200ms) | **Recommended by Claude initially.** Simple, no platform-specific code. | |
| File lock (msvcrt.locking / fcntl) | Platform-specific divergence; pre-empts race. | |
| Single-writer queue.Queue + dedicated persist thread | Architectural overkill for one cache. | |
| Skip-on-failure (no retry) | Cache regenerates next save; warns more often. | |
| threading.Lock + retry (100/250/500ms) + skip-on-final | **Codex's counter-proposal.** Handles in-process write contention. | ✓ |

**Codex Issue 6 (verbatim):** "retry-only misses in-process write contention. `_persist_positive_cache_snapshot()` can call `_save_nli_persistent_cache()` concurrently. Fix: add a module-level `threading.Lock` around temp-write + replace, retry `os.replace` on `PermissionError` / WinError 5 with `100ms / 250ms / 500ms`, warn once on final failure, clean temp, do not raise."

**Resolution:** D-NLI-01 adopts threading.Lock + retry with Codex's preferred 100/250/500ms timing. D-NLI-02 specifies the unit test shape (mock os.replace + threading.Lock contention via second thread).

## Structural correction (Codex Issue 7)

Claude's brief estimated per-render query cost as `5 + 3L` (with L=20: ~65 queries × 500ms ≈ 32s, matching 36s observation).

**Codex correction (verbatim):** "Project-contained lists call `_render_list_item(... show_color=False)`, so they do not trigger `get_list_display_color()`. Current cost is closer to `4 + L + 2S`, where `S` is standalone/system rendered with color, not always `5 + 3L`."

For Hillel's likely inventory (most lists in projects, ~4-6 standalone/system): 4 + 18 + 8 = 30 queries × 500ms ≈ 15s. The remaining ~21s of the observed 36s has additional contributions (Client-build overhead, network latency, Tantivy contention, page render).

**Resolution:** D-VER-05 encodes "Plan 92.2-02 SHAPED but not LOCKED until 92.2-01 instrumentation lands. If baseline reveals different bottleneck, 92.2-02 is REVISED before execution."

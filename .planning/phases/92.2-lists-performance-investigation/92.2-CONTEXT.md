## Implementation Decisions

### Verification methodology (D-VER-*)

- **D-VER-01:** Two plans. Plan 92.2-01 = instrumentation-only (commits baseline JSON artifact: per-call query count, Client-build count, p50/p95 round-trip latency, total wall-clock for Hillel's real `/lists` render). Plan 92.2-02 = fix + re-measure against the committed baseline. The pre-fix baseline becomes a permanent forensic artifact in git — grep-discoverable years later to prove the regression existed and closed quantitatively.
- **D-VER-02:** Hard-gate metric = server-side wall-clock, request received → response body flushed. Measured by middleware/decorator around the `/lists` route handler. Client-side DOM-stable is harder to measure deterministically and is mostly downstream of server cost.
- **D-VER-03:** Cold-start excluded from the 5s gate. Cold = first request after `python -m web.main` starts. Tantivy index loading + sidecar DB warmup dominate cold; mixing them confuses the diagnosis. Warm = all subsequent requests within the same web-server lifetime.
- **D-VER-04:** Falsification target = Hillel's real Supabase account inventory (the one that produced the 36s observation). Regression guard = small synthetic CI fixture (e.g., test user with 20 lists across 3 projects + 5 standalone) that runs in CI and asserts query count + wall-clock under a defensible threshold.
- **D-VER-05 (Codex Issue 7):** Plan 92.2-02 is SHAPED at planning time with the fix decisions below, but execution of 92.2-02 waits for 92.2-01's baseline data to land. If the baseline reveals a different bottleneck than the Supabase fanout (e.g., Tantivy index contention, NiceGUI event-loop blocking elsewhere, network jitter to Supabase region), Plan 92.2-02 is REVISED before execution. The 36s observation has more than one cause and Codex correctly notes the query-cost formula in the original brief was wrong (see Code Context below) — instrumentation must precede design lock-in.

### Client memo location (D-MEMO-*) — Codex-adjusted

- **D-MEMO-01 (Codex Issue 1):** Memo storage = module-level `WeakKeyDictionary` keyed by `asyncio.current_task()`. Each task's value is a dict keyed by `(_session_uuid, access_token)`. **Do NOT use `nicegui.context.client`** — Codex confirmed via NiceGUI source reading that `context.client` is the per-page `Client` object that persists across WebSocket events, async continuations, and `ui.timer` callbacks until disconnect/delete. Memoizing on it would create a per-tab long-lived cache, not an intra-request memo — directly reopens the Phase 90 D-12 "no caching" multitenant invariant.
- **D-MEMO-02 (Codex Issue 2):** Key composition `(_session_uuid, access_token)`. Refresh token is not in the key — Supabase client auth state for PostgREST/functions/storage depends only on the bearer access_token. Token rotation changes the key, fresh Client built (preserves Codex H1 safety property from the commit message). Skip memo entirely if `_session_uuid` is absent (anonymous path).
- **D-MEMO-03:** Fallback for non-asyncio contexts — if `asyncio.current_task()` returns `None`, build fresh `Client` without memo. Covers test contexts and any sync caller. The memo dies when the task finishes; no manual cleanup hooks needed. Phase 90 D-12 cross-request invariant preserved by construction (task IS the request scope in NiceGUI).
- **D-MEMO-04:** Code lives inline in `get_user_client()` at `web/supabase_client.py`. The 30+ existing call sites use the unchanged signature. The memo is an internal implementation detail.

### Fanout-reduction strategy (D-FANOUT-*) — Codex-adjusted

- **D-FANOUT-01 (Codex Issue 3):** Pure refactor — capture `lists_mgr = state.lists_mgr` ONCE inside the `/lists` render path entry point (not at each access site), then `data = lists_mgr.data` ONCE, then thread BOTH through helpers. **Critical:** `state.lists_mgr` is a factory-property that returns a NEW `UserListsManager` instance per access (Phase 89 D-03/D-04); calling it from N different places triggers N independent re-fetches. Code changes:
  - `web/components/project_tree.py:create_project_tree()` — accept `data` parameter; pass through to `_render_project_group`, `_render_list_item`, `get_list_display_color`, `get_lists_by_project`.
  - `web/user_lists.py:get_lists_by_project()` — add `data=None` parameter; when None, fall back to existing `_get_cached_data()` call (preserves other callers).
  - `web/user_lists.py:get_list_display_color()` — add `data=None` parameter; same fallback semantics.
  - `web/pages/lists.py:render_list_content()` (or equivalent entry) — capture `lists_mgr` once at the top; pass to `create_project_tree(lists_mgr=lists_mgr, data=data, ...)`. Selected-list header at line 633 (`state.lists_mgr.data.get('lists', {}).get(list_id)`) uses the SAME captured `data`.
  - Both new `data=None` parameters MUST default-to-None (Codex Issue 5 CONFIRM) — do not break other callers in `web/pages/discoveries.py`, `web/api.py`, `web/components/{add_to_list_dialog,comment_dialog,joins_panel}.py`, `web/pages/search.py`. Those callers stay on the existing `.data` fetch path; only the /lists hot path uses threaded data.
- **D-FANOUT-02 (Codex Issue 4):** Batched item-count via Supabase RPC. **Do NOT** use Python aggregation over `client.table('list_items').select('list_id').in_(list_ids)` — PostgREST has a default 1000-row response cap and a power-user with >1000 total items across lists would silently undercount. Ship as:
  - New SQL migration `supabase/migrations/2026-XX-list-item-counts-rpc.sql`:
    ```sql
    create or replace function get_list_item_counts_for_user(p_user_id uuid)
    returns table(list_id bigint, item_count bigint)
    language sql security invoker as $$
      select li.list_id, count(*)::bigint as item_count
      from list_items li
      where exists (
        select 1 from user_lists ul
        where ul.id = li.list_id and ul.user_id = p_user_id
      )
      group by li.list_id
    $$;
    grant execute on function get_list_item_counts_for_user(uuid) to authenticated;
    ```
    The `security invoker` clause + `where exists (... ul.user_id = p_user_id)` keep RLS-equivalent semantics (caller's auth.uid() applies to the inner user_lists select via the existing `user_lists` RLS policy). The `GRANT EXECUTE` follows the CLAUDE.md "Supabase Data API grants" convention (2026-05-30 invariant).
  - Python helper in `web/supabase_client.py`: `def get_list_item_counts(user_id: str) -> Dict[int, int]:` calls `client.rpc('get_list_item_counts_for_user', {'p_user_id': user_id}).execute()`. Returns `{list_id_int: count_int}`. Lists with zero items are absent from the result and default to 0 at the call site.
  - Replace per-list `lists_mgr._get_list_item_count(list_id)` in `_render_list_item` with a single upfront `counts = get_list_item_counts(user_id)` at the render-path entry, then pass `counts.get(int(list_id), 0)` to each item.
- **D-FANOUT-03:** Skip lazy counts (commit message's "OR" alternative). UX regression — placeholder badges that flicker on render. Unnecessary at current scale (<100 lists/user). Reserve for the unlikely future where user has 500+ lists.
- **D-FANOUT-04:** Scope = /lists hot path only (`project_tree.py` + `lists.py`). The other 4 `.data` callers (`api.py`, `add_to_list_dialog.py`, `comment_dialog.py`, `joins_panel.py`, `discoveries.py`, `search.py`) are dialog opens triggered by user clicks — one-shot calls where fanout doesn't compound. Defer to follow-up if 92.2-01 instrumentation surfaces them.

### NLI cache `[WinError 5]` fix (D-NLI-*) — Codex-adjusted

- **D-NLI-01 (Codex Issue 6):** Combined fix:
  - Add module-level `threading.Lock` (`_nli_persist_lock = threading.Lock()`) in the NLI cache module. Wrap the entire temp-write + `os.replace` block under `with _nli_persist_lock:`.
  - Inside the lock, retry `os.replace` on `PermissionError` / `OSError` with WinError 5 using delays `100ms / 250ms / 500ms`.
  - On final failure: log WARNING once, clean up the tmp file (best-effort `os.unlink` in try/except), return False. Do NOT raise — the cache regenerates on next save attempt.
  - Diagnostic logging: DEBUG per retry attempt, WARNING on final failure (matches existing log style).
- **D-NLI-02:** Test = unit test in `tests/test_nli_cache_persist_retry.py`. Mock `os.replace` to raise `OSError` (errno=EACCES for the WinError 5 equivalent) twice then succeed → assert function returns True after 2 retries. Mock to fail all 3 → assert function returns False, WARNING logged, tmp file cleaned up. Mock the threading.Lock contention path via a second thread holding the lock to verify serialization.
- **D-NLI-03:** Inline in the existing cache persistence function — do NOT promote to a shared `shared/atomic_replace.py` utility yet. If more sidecar caches surface the same pattern, promote then. YAGNI applies.

### NiceGUI runtime knowledge (Codex grounded)

- NiceGUI `Client` lifecycle = per-page (per tab), persists until socket disconnect/delete. `nicegui.context.client` therefore is NOT a per-request scope (Codex Issue 1 source).

Returns the same task object for all sync calls reached from the handler. Returns None outside an event loop (test contexts, background threads).

### Reusable Assets

- `safe_user_get('auth_session')` chokepoint at `web/safe_storage.py` — single source of truth for reading auth tokens. D-MEMO-01 uses the same path that `get_user_client()` already uses; no new storage reads introduced.

- Phase 87 lint scanner pattern — model for any new AST guard if 92.2 needs one (probably not — the refactor is to existing call sites, not a new banned pattern).

### Established Patterns

- **Throwaway client builds**: Phase 90 D-09/D-10 use throwaway `Client` instances for auth bootstrap (`sign_in`, `sign_up`, etc.). D-MEMO-01 inverts this for the read path — memoize within a task, throw away at task end.
- **Optional `data=None` parameters**: existing pattern in `genizah_core.py` for caching-aware helpers (e.g., callers that already have a metadata dict pass it through to avoid re-fetch). D-FANOUT-01 follows this idiom.
- **RPC vs table-query for aggregation**: existing FJMS service uses RPCs for aggregate queries (e.g., browse-by-domain count). D-FANOUT-02 follows the same idiom for `list_items` aggregation.
- **Atomic file replace with retry**: similar pattern exists in `shared/puzzle_image_service.py` for IIIF cache writes (concurrent download path). D-NLI-01 follows the same shape (lock + retry + skip-on-failure).

### Integration Points

- `get_user_client()` is the seam — D-MEMO-01 wraps it without changing the signature; the 30+ callers don't know the memo exists.
- `create_project_tree()` is the seam for the /lists hot path — `data` parameter threads from entry through helpers without changing public callers.
- New RPC `get_list_item_counts_for_user` — new public function exposed via Supabase; needs migration + grant. Web-only consumer initially.

### Verified Cost Formula (Codex-corrected)

Per `/lists` render with L lists, where:
- Cp = lists in projects (rendered with `show_color=False` per project_tree.py:275)
- Cs = standalone + system lists (rendered with `show_color=True`)
- L = Cp + Cs
- S = Cs (Codex's notation)

Per-render queries ≈ **4 + L + 2S** = 4 baseline (.data twice + lists_by_project's internal .data + recent_items) + L per-list `get_list_items` count + 2S per-color-list `get_list_display_color` re-fetches.

Original Claude estimate `5 + 3L` overcounted by ~`2(L-S)` because project-contained lists skip the color re-fetch. For a typical Hillel inventory with most lists in projects: e.g., L=18, S=4 → 4 + 18 + 8 = 30 queries × ~500ms ≈ 15s. The remaining 21s of the observed 36s is likely a mix of: (a) Client-build cost per query (~50-100ms × 30 = 1.5-3s), (b) network latency to Supabase region, (c) Tantivy index pressure on the same worker, (d) page render JS execution.

**Implication:** Plan 92.2-01 instrumentation is non-negotiable. The 36s has more than one cause; the fix shape above closes the Supabase fanout dimension but the residual latency might require a separate sub-fix. D-VER-05 captures this.

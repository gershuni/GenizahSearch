    Create `scripts/ec2_fs_test.py` per D-08/D-15 from CONTEXT.md. Addresses review concern #6 -- benchmarks at two scales (50K and 150K) for empirical scaling validation rather than single-point extrapolation.

    **Purpose:** Create a representative directory structure on the target EC2 instance with dummy files and measure performance at two scales. This script is meant to be copied to EC2 via scp and run there -- it has no local dependencies beyond Python 3.8+ stdlib.

    **Function `create_test_structure(base_dir, num_files, file_size_kb=100)`:**
    - Create 2-level hex hash directory structure: `{base_dir}/{xx}/{yy}/{hexname}.jpg`
    - Hash from sequential counter: `hex_str = format(i, '06x')`, dir1 = hex_str[0:2], dir2 = hex_str[2:4]
    - This gives up to 256 x 256 = 65,536 directories
    - At 50K files: ~0.8 files/dir avg, at 150K: ~2.3 files/dir avg, at 300K: ~4.6 files/dir avg (all well under ext4 optimal of 100-500)
    - Write each file with `os.urandom(file_size_kb * 1024)` content
    - Use tqdm if available, fallback to `print()` every 5000 files if tqdm not installed
    - Report: directories created, files created, total size, time elapsed

    **Function `run_benchmarks(base_dir, num_files)`:**
    Run and time the following operations:
    1. **ls single directory**: `os.listdir(base_dir + '/00/00/')` -- measure time (cold + warm: run twice, report both)
    2. **stat single file**: `os.stat(first_file_in_00_00)` -- measure time (cold + warm)
    3. **find count all files**: walk entire tree with `os.walk()`, count .jpg files -- measure time
    4. **du total size**: sum all file sizes via os.walk -- measure time
    5. **Random access**: stat 1000 random files from different directories -- measure avg/median/p95 time per stat
    6. **Sequential read**: read 100 random files fully -- measure avg read time and throughput MB/s
    7. **File creation rate**: create 1000 new files in random directories -- measure creates/sec (simulates ingest)
    8. **Tree walk** (rsync-like): walk full tree listing all files -- measure time (simulates rsync --dry-run)

    Also collect system info:
    - `os.statvfs(base_dir)` for filesystem stats (total inodes, free inodes, block size)
    - Read `/proc/mounts` or run `mount` for filesystem type
    - Try to read from `/sys/block/` or run `lsblk` via subprocess for disk info

    **Function `run_at_scale(base_dir, num_files, file_size_kb, cleanup_after=False)`:**
    Orchestrate create + benchmark + optional cleanup for one scale point.
    Return results dict.

    **Function `compare_scales(results_list)`:**
    Given results from two (or more) scale points, compute:
    - Linear scaling factor for find/du/tree-walk operations
    - Verify stat/ls remain constant (O(1) with htree)
    - Project to 300K files using the empirical scaling factor (not theoretical)
    - Flag if non-linear scaling detected (superlinear growth = concern)

    **Function `report(results_list)`:**
    Print formatted results table comparing scales and write JSON to `{base_dir}/_benchmark_results.json`:

    **Function `cleanup(base_dir)`:** Remove all test files and directories recursively. Called with `--cleanup` flag.

    **CLI (argparse):**
    - `--base-dir` (default: `/tmp/cache_test`)
    - `--scales` (default: `50000,150000` -- comma-separated file counts for multi-scale test)
    - `--file-size-kb` (default: 100 -- approximate average JPEG size)
    - `--cleanup` (remove test files after benchmarking each scale)
    - `--benchmark-only` (skip file creation, just run benchmarks on existing structure)
    - `--json-output FILE` (write results to JSON file; default: `{base_dir}/_benchmark_results.json`)
    - `--single-scale N` (run at only one scale -- for quick tests)

    **Important:** Script must work with Python 3.8+ stdlib only (no pip packages required). EC2 may have minimal Python install. tqdm is a nice-to-have with graceful fallback.

    **Default two-scale test:** Running without --single-scale creates 50K files, benchmarks, cleans up, then creates 150K files, benchmarks, cleans up. Total disk needed: max(50K, 150K) * file_size_kb = ~15GB for 150K at 100KB. If disk space is tight, use `--file-size-kb 10` for structure-only testing.

    ```bash
    scp scripts/ec2_fs_test.py ubuntu@[EC2-IP]:/tmp/
    ```

    **Step 2: SSH and run two-scale benchmark**
    ```bash
    ssh ubuntu@[EC2-IP]
    cd /tmp
    python3 ec2_fs_test.py --scales 50000,150000 --file-size-kb 100 --cleanup --json-output /tmp/fs_benchmark.json
    ```
    This will: create 50K files -> benchmark -> cleanup -> create 150K files -> benchmark -> cleanup -> compare scaling.

    If disk space is limited, use `--file-size-kb 10` for structure testing (100x less disk).

    **Step 3: Collect disk info**
    ```bash
    df -h
    lsblk
    sudo tune2fs -l /dev/xvda1 2>/dev/null | grep -i inode || sudo tune2fs -l /dev/nvme0n1p1 2>/dev/null | grep -i inode
    cat /proc/mounts | grep " / "
    ```

    **Step 4: Verify feasibility**
    From the JSON output, check:
    - `scaling_analysis.scaling_is_linear` = true (find/du scale linearly 50K->150K)
    - `projected_at_300k.feasible` = true
    - `projected_at_300k.estimated_find_sec` < 60 (reasonable for cache management)
    - `free_inodes` > 400K (300K images + 65K dirs + margin)
    - `stat_cold_ms` and `stat_warm_ms` < 10ms at both scales
    - EBS volume has or can be expanded to hold projected cache size (from Plan 02 storage stats)

    **Step 5: Copy results back**
    ```bash
    scp ubuntu@[EC2-IP]:/tmp/fs_benchmark.json _nli_cache_test/
    ```
